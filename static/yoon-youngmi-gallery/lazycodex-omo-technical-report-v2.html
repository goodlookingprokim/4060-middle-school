LazyCodex 개요

LazyCodex는 OmO(Oh-My-OpenAgent) 에이전트 하네스를 OpenAI Codex 환경에 이식한 경량 배포 도구다. OmO 전체를 가져오는 것이 아니라, 핵심 역할인 Hephaestus(자율 딥 워커)를 Codex 플랫폼에 최적화하여 제공한다.

OmO는 두 가지 에디션으로 제공된다: Ultimate Edition(OpenCode용 — 11 에이전트, 54+ 라이프사이클 훅, 5개 내장 MCP, Team Mode 포함)과 Light Edition(Codex CLI용 — LazyCodex로 배포, 이식 가능한 핵심 컴포넌트만 포함).

권장 운영 환경

OS권장도비고

macOS✅ 권장Homebrew + Node.js/npm으로 충분
Windows⚠️ 비권장WSL 내에서 실행 권장, 프로젝트는 WSL 파일시스템에 보관

설치 명령어

npx lazycodex-ai install # LazyCodex 기본 대화형 설치
npx lazycodex-ai install --yes --non-interactive # 완전 자율 설치 (TUI 없음)
npx lazycodex-ai --dry-run install # 실행 전 명령어 미리보기
npx lazycodex-ai doctor # 상태 진단
npx lazycodex-ai uninstall # 제거
⚠️ 주의: npm install -g 또는 bun add -g로 설치하지 말 것. 항상 npx로 실행. 강력 권장: LLM 에이전트에게 설치를 맡길 것 — 구독 감지, 모델 선택, 인증 등을 자동으로 처리한다.

Ultrawork 모드

프롬프트에 ultrawork 또는 ulw를 포함하면 활성화. 핵심 원칙: "에이전트가 완료했다고 말하는 것은 끝이 아니다. 실제 표면에서 캡처한 증거로 결과가 확인될 때 완료다."

구분반복 한도
Ultrawork 모드 ($ulw-loop)500회
일반 모드100회

Hash-Anchored 편집 도구 (Ultimate 전용)

모든 라인에 콘텐츠 해시 태그가 붙는다 (예: 11#VK| function hello() {). 에이전트는 해시로 편집 대상을 참조하므로, 파일이 변경되었다면 해시 불일치로 편집이 거부된다. 스테일 라인 오류 완전 제거.

Team Mode v4.0 (Ultimate 전용)

리드 에이전트 + 최대 8명 병렬 멤버. tmux 레이아웃으로 실시간 시각화. team_create, team_send_message, team_task_create 등 team_* 툴 패밀리 활성화.

핵심 커맨드 4가지

커맨드역할언제 사용
$init-deep프로젝트 메모리 생성레포지토리 첫 작업 전, 계층적 AGENTS.md 컨텍스트 확보
$ulw-plan탐색 우선 계획 수립5단계 이상, 모호한 범위, 여러 모듈, 아키텍처 결정이 필요한 경우
$start-work계획 실행$ulw-plan으로 만든 계획을 Boulder 진행 상태로 실행
$ulw-loop증거 기반 루프 실행단일 태스크, 실패 비용이 크거나 검토가 필요한 경우
📌 전형적인 세션 흐름:
① $init-deep → 레포 컨텍스트 확보
② $ulw-plan → 결정 완전한 작업 계획 생성 (인터뷰 → 탐색 → 계획서)
③ $start-work → 계획 실행 (Boulder 상태로 중단 후 재개 가능)
④ 단일 검증 작업: $ulw-loop 단독 사용 가능

OmO 스킬 23개 완전 목록

GitHub packages/shared-skills/skills/ 기준으로 확인된 OmO 스킬 전체 목록이다. Both = LazyCodex(Light)·Ultimate 공통 / Ultimate = OpenCode 전용 / Light = Codex 전용

1
커맨드$init-deepBoth
📁 계층적 AGENTS.md 컨텍스트 생성
프로젝트 트리를 순회하며 루트 + 복잡도 기준 하위 디렉터리에 AGENTS.md 파일을 생성. 에이전트가 코드에 손대기 전 최우선 실행 권장. 토큰 효율과 에이전트 성능 모두 향상.
2
커맨드$ulw-planBoth
📋 탐색 우선 계획 수립 (Prometheus)
5단계+ 작업, 모호한 범위, 멀티 모듈, 아키텍처 결정에 MUST USE. 코드베이스 탐색 → 해결 불가한 포크만 인터뷰 → 명시적 승인 대기 → 워커가 추가 인터뷰 없이 실행할 수 있는 결정 완전 계획 한 개 생성.
3
커맨드$ulw-loopBoth
🔁 증거 기반 루프 실행
자기참조적 개발 루프. ultrawork 모드로 작업을 체계적·증거 기반 단계로 분해. "완료" 선언 후에도 실제 증거 없으면 종료 안 함. Stop-hook 연속으로 세션 중단 후 재개 가능. Ultrawork: 500회 / 일반: 100회 한도.
4
커맨드$start-workBoth
⚙️ Prometheus 계획 실행기
Boulder 상태·증거 원장·워크트리 규율·병렬 서브에이전트·Stop-hook 연속으로 Prometheus 작업 계획을 실행. 계획 후 사용자가 "start work", "execute plan", "continue plan"을 말할 때 사용.
5
품질보증$review-workBoth
🔍 5레인 병렬 사후 구현 검토
중요 구현 완료 후 MUST USE. 5개 병렬 백그라운드 서브에이전트: ① Oracle(목표·제약 검증) ② Oracle(코드 품질) ③ Oracle(보안) ④ unspecified-high(실습 QA 실행) ⑤ unspecified-high(GitHub/git 컨텍스트 마이닝). 하나라도 실패하면 전체 FAIL.
6
품질보증$visual-qaBoth
🖼️ 듀얼 오라클 시각 QA
웹 UI: 스크린샷 / TUI: tmux capture-pane으로 레퍼런스·실제 캡처. 번들 픽셀 diff 또는 컬럼 폭 스크립트 실행. 두 병렬 읽기 전용 오라클 패스(디자인 시스템·기능 무결성; 시각 충실도·CJK 정밀도) → 단일 good/bad 평결.
7
품질보증$comment-checkerBoth
💬 주석 드리프트 즉각 탐지
편집성 툴 호출 후 자동 실행. 수정된 라인 근처 주석 검사 → 코드와 일치하지 않는 주석(comment drift) 발견 시 수정 또는 근거 제시 강제. 나중 리뷰가 아닌 발생 시점에 잡아냄.
8
코드작업$programmingBoth
💻 4개 언어 엄격 타입·TDD 규율
.py .pyi .rs .ts .tsx .mts .cts .go 파일 편집 시 MUST USE. parse-don't-validate, 철저한 variant 매칭, 타입 오류, any/unwrap/panic 금지, 250 순수 LOC 한도, 필수 TDD(RED→GREEN→REFACTOR). 언어별 참조: Python(uv+basedpyright+ruff), Rust(cargo+clippy+miri), TypeScript(Bun+Biome+tsc), Go(gofumpt+golangci-lint v2).
9
코드작업$debuggingBoth
🐛 가설 주도 런타임 디버깅
크래시, 사일런트 실패, 잘못된 응답, 멈춘 프로세스, 메모리 릭, 비동기 오동작에 MUST USE. 코드 읽기 아닌 런타임 상태 관찰로만 원인 주장. 3개+ 직교 가설 → 병렬 조사 → 2회 실패 시 독립 검증자 → 토글로 근본 원인 확인 → 실패 테스트 잠금 → 최소 수정 → 디버그 아티팩트 전체 정리. pdb·node inspect·lldb·dlv 실제 디버거 연결.
10
코드작업$refactorBoth
🔧 코드맵 인식 구조 개편
접촉 전 코드베이스 먼저 매핑. 테스트 커버리지 평가 → 검증 전략 결정 → 롤백 포인트 있는 원자적 단계 실행 → 각 단계 후 검증. LSP 이름 변경 + AST-grep 구조 재작성. 테스트 실패 시 즉각 중단 및 revert.
11
코드작업$remove-ai-slopsBoth
🧹 AI 코드 스멜 제거 (10개 카테고리)
동작 보존 전제 정리. 삭제 전 회귀 테스트로 동작 잠금. 10개 슬롭 카테고리: 명백한 주석, 과도한 방어 코드, 불필요한 추상화, 데드 코드, 중복, 과대 모듈(250+ 순수 LOC), 성능 동치, 과도한 복잡도 등. 5개씩 병렬 deep 에이전트 배치 처리. 테스트 실패 시 즉각 revert.

코드작업$frontendBoth
🎨 UI·UX·성능·접근성 통합 라우터
모든 프론트엔드·웹 UI·UX·시각 작업에 MUST USE. 4개 룰셋 라우팅: design(12개 taste 스킬 + 69개 브랜드 DESIGN.md ref), perfection(Lighthouse 100, 실제 Playwright Chromium), ui-ux-db(50+ 스타일, 97 팔레트, 57 폰트 페어링), designpowers(접근성·비평·핸드오프).

사용 순서만 기억하면 됩니다 (OPERATING MODEL)

📌 이미지 원문 내용 — "사용 순서만 기억하면 됩니다"
1
스킬을 이름으로 호출한다
omo:frontend, omo:debugging, ulw처럼 목적을 직접 말합니다.
2
작업 표면에 맞는 증거를 남긴다
CLI, 브라우저, GUI, 데이터 산출물마다 검증 surface를 다르게 둡니다.
3
긴 작업은 상태를 분리한다
계획은 ulw-plan, 실행은 ulw-loop와 start-work, 이력은 git-master로 관리합니다.
4
로컬 출처 밖의 사실을 섞지 않는다
이번 발표처럼 신뢰 경계를 먼저 정하면 결과 설명이 흔들리지 않습니다.
로컬 OMO 플러그인은 Codex 작업을 증거 중심 절차로 라우팅하는 레이어입니다.

TDD · 수동 QA · 훅 & 라이프사이클

TDD (테스트 주도 개발)

단계설명
🔴 RED실패 테스트 먼저 작성 — 존재하지 않는 기능에 대한 테스트
🟢 GREEN테스트를 통과시키는 최소한의 코드 작성
🔵 REFACTOR동작을 유지하면서 코드 구조 개선
⚠️ 결정론적 테스트 원칙: 10번 중 9번 통과하는 테스트는 10%의 실패율을 가진 것이다. 시간 의존성 없는 테스트 바디에서 sleep·retry·flaky 금지. LLM 프롬프트를 테스트할 때는 현재 문구가 아닌 구조·의미를 테스트한다.

5가지 증거 게이트 (Evidence Gates)

게이트설명
① 계획 재독 (Plan Reread)실행 전 계획을 다시 읽어 방향 확인
② 자동 검증 (Automated Verification)테스트 자동 실행 및 확인
③ 수동 QA (Manual QA)실제 표면에서 직접 검증
④ 빌드 증거 (Build Proof)실제 아티팩트 캡처
⑤ 작업 검증 (Work Verification)성공 기준 대조 최종 확인

훅 & 라이프사이클

이벤트발동 조건역할
Stop-hook턴 종료 시계획 진행 중이면 다음 턴 재주입하여 루프 유지
PostToolCall편집성 툴 호출 후comment-checker, LSP 진단 등 즉각 피드백
Session start세션 시작 시rules 스킬로 프로젝트 지침 주입
Upgrade플러그인 파일 변경 시훅 재승인 요구 (보안)
🔒 보안: 훅은 승인 전 절대 실행되지 않는다. 설치 후 첫 Codex 실행 시 시작 검토(startup review)에서 반드시 승인해야 한다. 업그레이드 후에도 훅이 Modified로 표시되면 재승인 필요.
