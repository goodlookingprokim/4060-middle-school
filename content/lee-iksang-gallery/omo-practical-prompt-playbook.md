# OMO 실전 프롬프트 플레이북 전체판

이 자료는 이익상님이 보내주신 발표용 PDF 내용을, 글자가 작거나 깨져 보이는 문제 없이 웹에서 읽기 쉽게 정리한 페이지입니다.
강의 흐름을 먼저 훑고, 뒤에서 바로 가져다 쓸 프롬프트를 이어서 볼 수 있게 구성했습니다.

> [!note] 이 자료는 이렇게 보면 편합니다
> 앞부분은 "OMO를 어떤 순서로 쓰는가"를 이해하는 부분이고, 뒷부분은 바로 복사해 쓸 수 있는 프롬프트 모음입니다. 처음 보실 때는 앞의 구조부터 읽고, 실제 작업할 때는 필요한 프롬프트를 찾아 다시 내려오시면 편합니다.

## 먼저 잡아두면 좋은 핵심

- OMO는 명령어 하나가 아니라, 일을 운영하는 방식에 가깝습니다.
- 큰 흐름을 잡는 대표 워크플로와, 품질을 끌어올리는 전문 스킬을 함께 씁니다.
- "끝났다"는 말보다 실제 결과물과 검증 흔적을 더 중요하게 봅니다.
- 계획이 잘 맞는 일과, 반복 검증이 잘 맞는 일은 운영 방식이 다릅니다.

## 이 자료는 두 부분으로 되어 있습니다

### 1부. 발표용 핵심 구조

강의나 소개 자리에서 OMO를 짧고 분명하게 설명할 때 쓰는 흐름입니다.

- OMO가 어떤 방식으로 작업을 쪼개는지
- 조사, 계획, 실행, 검증이 어떻게 이어지는지
- 어떤 일에 어떤 워크플로가 맞는지

### 2부. 선별 프롬프트 라이브러리

바로 복사해서 쓸 수 있는 프롬프트 모음입니다.

- 대괄호 안 변수만 바꿔서 사용할 수 있습니다.
- 조사 → 계획 → 실행 → 검증 순서로 연결해 쓰면 됩니다.
- 완료 조건에는 파일, 렌더링, 테스트, 출처 같은 증거를 함께 적는 것이 핵심입니다.

## OMO를 이루는 두 축

### 대표 워크플로

작업의 큰 흐름을 통제하는 스킬입니다.

- `$init-deep`
- `$ulw-plan`
- `$start-work`
- `$ulw-loop`

### 전문 스킬

각 단계의 품질을 높이는 스킬입니다.

- `$ulw-research`
- `$frontend`
- `$visual-qa`
- `$review-work`
- `$debugging`

## 대표 워크플로 4개의 역할

### `$init-deep`

프로젝트를 이해하는 단계입니다.

- 파일, 코드, 데이터 흐름을 탐색합니다.
- 계층형 `AGENTS.md`를 만들어 작업 지도를 세웁니다.

### `$ulw-plan`

구현 전에 계획을 확정하는 단계입니다.

- 요구사항
- 수정할 파일 경로
- 검증 방법
- 완료 기준

이 네 가지를 먼저 정리합니다.

### `$start-work`

계획을 실제로 실행하는 단계입니다.

- 저장된 계획을 기준으로 작업합니다.
- 체크박스 단위로 실행과 검증을 맞춰 갑니다.
- 실패했거나 막힌 항목은 완료로 처리하지 않습니다.

### `$ulw-loop`

명확한 목표를 두고 자율 반복으로 완성해 가는 방식입니다.

- 계획형 후속 단계가 아니라 별도의 운영 방식입니다.
- 반복 검증이 많이 필요한 과제에 잘 맞습니다.

## 전문 스킬은 무엇을 보강하나

- `$ulw-research`는 넓고 깊은 조사를 맡습니다.
- `$frontend`는 UI, UX, 반응형 구현을 맡습니다.
- `$visual-qa`는 실제 화면이 제대로 보이는지 확인합니다.
- `$review-work`는 내용, 품질, 위험을 다각도로 검토합니다.
- `$debugging`은 재현과 가설, 증거 중심으로 문제를 풉니다.

## 언제 계획형, 언제 루프형일까

### 계획형 실행

`$ulw-plan → $start-work`

이런 일에 잘 맞습니다.

- 요구사항이 비교적 분명한 작업
- 결과물이 어느 정도 정해져 있는 작업
- 단계별 승인이나 커밋 구분이 중요한 작업

예시:

- 웹사이트 제작
- 앱 제작
- PWA 제작
- 슬라이드 제작

### 자율 완성 실행

`$ulw-loop`

이런 일에 잘 맞습니다.

- 목표는 분명하지만 해결 방법이 탐색적인 작업
- 반복 점검과 수정이 많이 필요한 작업

예시:

- 복합 버그 해결
- 환경 의존 문제
- 끝까지 완성해야 하는 자율 과제

## OMO가 권장하는 기본 운영 모델

자료에서 제안하는 대표 순서는 아래와 같습니다.

1. 이해: `$init-deep`
2. 조사: `$ulw-research`
3. 계획: `$ulw-plan`
4. 제작: `$start-work`
5. 검증: `$visual-qa`
6. 리뷰: `$review-work`
7. 버전 관리: `$git-master`

핵심은 간단합니다.

> 작업 종료 선언보다, 실제 산출물과 검증 증거가 먼저다.

자료에서는 다섯 가지 제작 관점을 따로 봐야 한다고 설명합니다.

### 정보 조사

### 프레젠테이션

### 웹사이트

### PWA

## 좋은 OMO 프롬프트의 6가지 요소

자료에서 강조한 프롬프트 뼈대는 아래 여섯 가지입니다.

1. `ROLE / MODE`
   어떤 실행 모드인지 적습니다. 예: `$ulw-plan`, `$visual-qa`
2. `CONTEXT`
   프로젝트, 청중, 기술 스택, 현재 상태를 적습니다.
3. `OBJECTIVE`
   무엇을 결정하거나 완성해야 하는지 적습니다.
4. `SCOPE`
   어디까지 포함하고 무엇을 제외할지 적습니다.
5. `DELIVERABLE`
   `PPTX`, `report.md`, 앱 빌드 같은 구체 결과물을 적습니다.
6. `EVIDENCE`
   브라우저, 렌더링, 테스트, 출처처럼 완료를 확인할 증거를 적습니다.

## 작업별 권장 조합

자료에서 제안한 기본 조합을 읽기 쉽게 다시 적으면 아래와 같습니다.

| 작업 | 권장 흐름 |
|---|---|
| 정보 조사 | `$ulw-research` → 근거 검토 |
| 조사 보고서 | `$ulw-research` → `$ulw-plan` → `$start-work` → 문서 검토 |
| 프레젠테이션 | `$ulw-research` → `$ulw-plan` → `$start-work` → 렌더·내용 검토 |
| 신규 웹사이트 | `$ulw-research` → `$ulw-plan` → `$start-work` → 렌더·내용 검토 |
| 기존 웹사이트 개선 | `$init-deep` → `$ulw-plan` → `$start-work` → `$visual-qa` → `$review-work` |
| PWA | `$init-deep` → `$ulw-plan` → `$start-work` → `$debugging` → `$visual-qa` → `$review-work` |
| iOS·Android 앱 | `$init-deep` → `$ulw-research` → `$ulw-plan` → `$start-work` → `$debugging` → `$visual-qa` → `$review-work` |
| 자율 완성 과제 | `$ulw-loop` + 명확한 목표와 완료 조건 |

## 프롬프트 라이브러리 사용법

자료에서 안내한 사용 순서는 아래 네 단계입니다.

1. 필요한 스킬 프롬프트를 그대로 복사합니다.
2. `[주제]`, `[서비스명]`, `[기술 스택]` 같은 변수만 바꿉니다.
3. 조사 → 계획 → 실행 → QA → 리뷰 순서로 연결합니다.
4. 파일, 렌더링, 테스트 결과 같은 완료 증거를 적습니다.

## 바로 가져다 쓸 수 있는 예시

### `$init-deep` 공통 프롬프트

```text
/init-deep
이 저장소는 [프로젝트 유형] 프로젝트다.
프로젝트 전체를 탐색하여 다음을 수행하라.
1. 실제 Source of Truth가 되는 파일과 디렉터리를 식별한다.
2. 주요 모듈, 데이터 흐름, 빌드 과정, 출력물을 지도화한다.
3. 루트와 주요 하위 디렉터리에 계층형 AGENTS.md를 생성하거나 갱신한다.
4. 각 AGENTS.md에는 해당 영역의 목적, 주요 파일, 수정 규칙, 실행 명령, 테스트 방법, 금지 사항을 기록한다.
5. 문서와 실제 코드가 충돌하면 실제 구현을 우선하되 충돌 내용을 기록한다.
6. 지금은 기능을 구현하거나 파일 구조를 임의로 개편하지 않는다.
프로젝트 유형별 중점 사항:
[아래의 작업별 중점 사항 삽입]
```

### 프로젝트 유형별 중점 사항

| 작업 | 넣어야 할 중점 사항 |
|---|---|
| 정보 조사 | `raw-sources, notes, citations, datasets, reports의 역할과 출처 관리 규칙을 지도화하라.` |
| 슬라이드 | `콘텐츠 원고, 이미지·아이콘, 테마, 차트 데이터, 슬라이드 생성 코드, PPTX/PDF 출력 흐름을 지도화하라.` |
| 웹사이트 | `라우트, 페이지, 컴포넌트, 디자인 토큰, API, 데이터베이스, 인증, 테스트, 배포 흐름을 지도화하라.` |
| PWA | `웹 구조에 더해 manifest, service worker, 캐시, 오프라인 화면, 동기화, 업데이트 흐름을 지도화하라.` |
| iOS·Android | `iOS와 Android 모듈, 네비게이션, 상태 관리, API 계층, 로컬 저장소, 권한, 빌드 설정, 테스트 구조를 지도화하라.` |

### `$ulw-research` 정보 조사 프롬프트

```text
$ulw-research
[조사 주제]를 심층 조사하라.
조사 목적:
[이 조사를 통해 결정하거나 제작할 것]
필수 조사 범위:
1. 공식 문서, 공식 발표, 원본 저장소, 논문을 1차 출처로 우선한다.
2. 최근 변경 사항은 발표일과 실제 적용일을 구분한다.
3. 핵심 개념, 작동 방식, 장점, 한계, 비용, 위험 요소를 조사한다.
4. 실제 사용자 활용 사례와 실패 사례를 구분하여 수집한다.
5. 출처 간 주장이 충돌하면 양쪽 근거와 차이를 명시한다.
6. 확인된 사실, 합리적 추론, 미확인 주장을 명확히 분리한다.
7. 주요 주장마다 출처를 연결한다.
최종 산출물:
- 초보자용 요약
- 핵심 개념 설명
- 기능 및 경쟁 제품 비교
- 실제 활용 사례
- 단계별 튜토리얼
- 한계와 주의사항
- 추천 활용 시나리오
- 출처가 연결된 상세 보고서
추가 조사 가치가 있는 단서를 확장하되 탐색 범위·중단 기준·미확인 항목을 명시하라.
```

### `$ulw-research` 프레젠테이션 조사 프롬프트

```text
$ulw-research
[발표 주제]에 관한 [발표 시간]분 분량의 프레젠테이션을 만들기 위한 근거 자료를 조사하라.
대상 청중:
[초보자 / 실무자 / 경영진 / 학생]
다음을 조사하라.
1. 발표의 핵심 메시지를 뒷받침하는 최신 사실과 통계
2. 발표 초반에 사용할 문제 상황과 강한 사례
3. 핵심 개념을 설명할 수 있는 비유와 실제 사례
4. 전후 비교, 경쟁 제품 비교, 프로세스 비교에 사용할 데이터
5. 차트 또는 다이어그램으로 시각화하기 좋은 자료
6. 저작권과 출처를 확인할 수 있는 이미지·아이콘 후보
7. 반론, 한계, 실패 가능성
8. 마지막 행동 제안으로 연결할 수 있는 실전 활용법
최종 결과는 슬라이드별로 활용할 수 있도록
'주장 / 근거 / 시각화 아이디어 / 출처 / 발표자 설명' 형식으로 정리하라.
```

### `$ulw-research` 웹사이트 사전 조사 프롬프트

```text
$ulw-research
[서비스 또는 브랜드] 웹사이트를 제작하기 전에 필요한 조사를 수행하라.
조사 대상:
- 목표 사용자와 주요 문제
- 유사 서비스와 경쟁 사이트
- 경쟁 사이트의 정보 구조와 전환 흐름
- 신뢰를 형성하는 콘텐츠 요소
- SEO 검색 의도와 핵심 키워드
- 접근성 및 성능 관련 공식 권장사항
- 적합한 기술 스택과 배포 방식
- 개인정보, 쿠키, 결제 등 관련 위험 요소
경쟁 사이트의 디자인을 복제하지 말고,
반복되는 업계 패턴과 차별화 가능한 기회를 추출하라.
결과물:
1. 사용자 페르소나
2. Jobs-to-be-Done
3. 경쟁 분석표
4. 추천 사이트 구조
5. 핵심 전환 흐름
6. 콘텐츠 요구사항
7. 기술적 권장사항
8. 설계 결정에 영향을 주는 근거와 출처
```

### `$ulw-research` PWA 사전 조사 프롬프트

```text
$ulw-research
[서비스]를 PWA로 구현하기 위한 제품·기술 조사를 수행하라.
반드시 조사할 내용:
- 사용자가 오프라인에서 수행해야 하는 핵심 작업
- 설치형 경험이 실제로 필요한 이유
- 브라우저 및 플랫폼별 제약
- manifest와 service worker 구성 원칙
- 캐시 전략별 장단점
```
