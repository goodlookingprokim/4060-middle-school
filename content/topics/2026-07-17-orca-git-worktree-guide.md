# Git worktree와 Orca를 같이 배우면, AI 에이전트를 여러 명 붙일 때 왜 일이 풀릴까

코딩을 조금 하다 보면, 기술보다 먼저 작업 자리가 답답해지는 순간이 옵니다. 한쪽에서는 기능을 만들고 있는데, 갑자기 다른 브랜치에서 급한 버그를 고쳐야 하고, 또 어떤 날은 AI 에이전트 둘셋에게 일을 나눠 맡겨보고 싶어집니다.

그런데 같은 폴더 하나만 붙들고 있으면 일이 자꾸 끊깁니다. 오늘 글은 바로 그 지점에서 왜 `git worktree`가 다시 중요해졌는지, 그리고 Orca 같은 도구가 왜 요즘 많이 거론되는지 아주 쉬운 감각으로 정리한 글입니다.

출처: Orca 소개 영상, Git 공식 문서, Orca 공식 문서와 GitHub 공개 자료를 바탕으로 정리했고, 이번 수정에는 개발자의디자인 글 `비개발자에게 orca를 추천하는 이유`도 함께 참고했습니다. 글 하단에 링크를 함께 남겨둡니다.

## 먼저 결론

- 브랜치를 자주 바꿔야 할수록, 한 폴더 안에서 `git switch`만 반복하는 방식은 금방 피곤해집니다.
- `git worktree`는 저장소 역사는 하나로 두고, 실제 작업 폴더만 여러 개 펼쳐 쓰게 해주는 기능입니다.
- Orca는 그 worktree 위에 여러 AI 에이전트를 병렬로 붙여 한 화면에서 지휘하기 쉽게 만든 도구라고 이해하면 가장 편합니다.

## 왜 브랜치 전환이 자꾸 일을 끊을까

기능 하나를 만들고 있는데, 갑자기 운영 버그를 고쳐야 하는 상황을 떠올리면 이해가 쉽습니다.

- 지금 하던 코드는 아직 덜 끝나서 커밋하기 애매합니다.
- 그렇다고 바로 `main`으로 가면 수정하던 파일이 발목을 잡습니다.
- `stash`를 쓰면 잠깐 편하지만, 나중에 다시 꺼낼 때 충돌이 나거나 흐름을 잊어버리기 쉽습니다.
- 어중간한 상태를 커밋하면 기록이 지저분해집니다.

결국 문제는 단순합니다.

> 같은 저장소 안에서 실제로 손대고 있는 작업 자리가 하나뿐이라, 서로 다른 일을 동시에 다루기 어렵다는 점입니다.

조금 더 생활 쪽 비유로 바꾸면 이런 느낌입니다.

- 책상 위에 수학 숙제를 한창 펼쳐놓고 있는데
- 갑자기 학교에 제출할 가정통신문에 사인을 해야 하고
- 자리가 없으니 수학책과 연습장을 전부 상자에 구겨 넣었다가
- 다시 꺼낼 때 어디까지 풀었는지 감이 끊기는 상황

`git stash`나 어중간한 `WIP` 커밋으로 버티는 순간이 바로 이 감각과 비슷합니다. 기능을 몰라서가 아니라, **일하던 맥락이 통째로 끊기는 것**이 더 피곤한 부분입니다.

## worktree는 무엇을 바꾸는가

`git worktree`는 이 문제를 "브랜치를 더 잘 바꾸는 기술"로 푸는 게 아니라, **작업 자리를 하나 더 펼치는 방식**으로 풉니다.

주방 비유로 보면 쉽습니다.

- 냉장고는 하나입니다. 이게 저장소의 역사입니다.
- 그런데 조리대는 여러 개 둘 수 있습니다. 이게 worktree입니다.
- 한 조리대에서는 찌개를 끓이고, 다른 조리대에서는 계란말이를 만들 수 있습니다.

즉, 원본 저장소를 통째로 또 복제하지 않아도, 서로 다른 브랜치를 각 폴더에서 따로 펼쳐 놓고 일할 수 있습니다.

책상 비유로 말하면 더 단순합니다.

- 거대한 책상 하나가 있습니다. 이게 여러분의 저장소입니다.
- 책상 왼쪽에는 로그인 기능 브랜치가 펼쳐져 있습니다.
- 책상 오른쪽에는 급한 오타 수정용 `main` 브랜치를 펼칠 수 있습니다.
- 왼쪽 종이는 그대로 두고, 몸만 오른쪽으로 살짝 돌려 급한 일을 끝낸 뒤 다시 돌아오면 됩니다.

핵심은 이것입니다.

> worktree는 하던 종이를 치우지 않고, 옆에 새 자리를 하나 더 펴는 방식입니다.

## 가장 자주 쓰는 명령은 이 정도면 충분합니다

```bash
git worktree add ../shop-hotfix -b hotfix/payment
git worktree list
git worktree remove ../shop-hotfix
git worktree prune
```

각 명령은 이렇게 이해하면 됩니다.

- `add`: 옆 폴더에 새 작업 자리를 만들고, 새 브랜치까지 바로 얹습니다.
- `list`: 지금 몇 개의 작업 자리를 펼쳐놨는지 확인합니다.
- `remove`: 끝난 작업 자리를 정리합니다.
- `prune`: 실수로 사라진 worktree의 잔여 기록을 청소합니다.

여기서 중요한 점 하나만 꼭 기억하면 됩니다.

> worktree 폴더는 파일 탐색기에서 그냥 지우기보다 `git worktree remove`로 정리하는 편이 안전합니다.

조금 더 실전 쪽으로 풀면 `add`는 두 가지 감각으로 나눠 기억하면 편합니다.

### 이미 있는 브랜치를 새 폴더에 펼치기

```bash
git worktree add ../my-hotfix main
```

이 명령은 "상위 폴더에 `my-hotfix`라는 새 작업 공간을 만들고, 거기에는 기존 `main` 브랜치를 열어줘"라는 뜻입니다.

### 새 브랜치를 만들면서 새 폴더도 같이 만들기

```bash
git worktree add ../my-new-feature -b feature/login
```

이 명령은 "아직 없던 `feature/login` 브랜치를 새로 만들고, 그 브랜치를 위한 폴더도 같이 열어줘"라는 뜻입니다.

초보자 입장에서는 여기서 가장 많이 씁니다.

- 급한 수정: 기존 `main`을 펼친다
- 새 기능 시작: 새 브랜치를 만들면서 새 폴더를 연다

## clone을 하나 더 뜨는 것과는 무엇이 다를까

비슷해 보여도 차이가 꽤 큽니다.

| 비교 항목 | 저장소를 하나 더 clone | git worktree |
| --- | --- | --- |
| 히스토리 저장 | 저장소 역사까지 통째로 한 벌 더 생김 | 저장소 역사는 하나를 공유 |
| 디스크 사용 | 더 무거움 | 상대적으로 가벼움 |
| 커밋 반영 | push/pull 감각이 더 자주 필요함 | 같은 저장소 안에서 바로 이어짐 |
| 같은 브랜치 중복 위험 | 실수 여지 있음 | 같은 브랜치는 중복 체크아웃을 막아줌 |

정리하면, **clone을 하나 더 뜨는 건 창고를 통째로 하나 더 만드는 느낌**이고, **worktree는 같은 창고에서 작업 책상만 늘리는 느낌**입니다.

그래서 초보자에게는 이 한 줄이 가장 중요합니다.

> clone은 집을 한 채 더 짓는 쪽이고, worktree는 같은 집 안에 방을 하나 더 쓰는 쪽입니다.

둘 다 비슷해 보여도, 손에 익는 속도와 관리 난이도는 꽤 다릅니다.

## 왜 AI 에이전트 시대에 worktree가 다시 중요해졌을까

예전에는 사람이 직접 브랜치를 옮겨 다니며 일했다면, 이제는 AI 에이전트가 대신 코드를 고치고, 문서를 정리하고, 테스트를 돌리는 흐름이 많아졌습니다.

그런데 같은 폴더에서 에이전트 둘셋을 동시에 돌리면 금방 문제가 생깁니다.

- 누가 어떤 파일을 바꿨는지 헷갈립니다.
- 한 에이전트의 결과를 다른 에이전트가 덮어쓸 수 있습니다.
- 결과 비교가 어려워집니다.

그래서 요즘 실전 감각은 이렇게 정리할 수 있습니다.

> 병렬 에이전트는 worktree로 가두고, 최종 선택과 머지는 사람이 한다.

이 한 줄이 정말 중요합니다.

## 이 말을 아주 쉬운 비유로 바꾸면

요리사 세 명에게 동시에 일을 시킨다고 생각해보겠습니다.

- 도마가 하나뿐이면 서로 재료를 덮어쓰고 엉망이 됩니다.
- 도마를 하나씩 주면 각자 자기 요리를 끝까지 만들 수 있습니다.
- 마지막에 헤드 셰프가 세 접시를 보고 어떤 걸 낼지 결정합니다.

AI 에이전트도 비슷합니다.

- 에이전트 A는 쿠폰 기능
- 에이전트 B는 검색 버그 수정
- 에이전트 C는 같은 기능의 다른 구현안

이렇게 나눠 맡기려면, 각자 자기 작업 폴더가 필요합니다. 그 자리를 만드는 기술이 worktree이고, 그 흐름을 보기 쉽게 묶어주는 환경이 Orca입니다.

## Orca는 무엇으로 이해하면 좋을까

Orca를 "새로운 AI 모델"로 이해하면 오히려 헷갈립니다. 더 쉬운 이해는 이쪽입니다.

- Orca는 Claude Code나 Codex 같은 기존 에이전트를 대신하는 모델이 아닙니다.
- worktree 단위로 여러 에이전트를 붙이고
- 진행 상태를 한 화면에서 보고
- diff를 비교하고
- 필요한 경우 모바일로 알림까지 받게 돕는 **지휘 환경**에 가깝습니다.

즉, IDE라기보다 여러 에이전트를 다루는 **작업 본부**라고 보면 편합니다.

## IDE와 ADE는 무엇이 다를까

IDE는 보통 사람 한 명이 코드를 더 잘 쓰게 도와주는 환경입니다.

반면 Orca가 말하는 ADE는 사람 혼자보다, **사람과 여러 에이전트가 같이 일하는 환경**에 더 가깝습니다.

비유로 말하면 이렇습니다.

- IDE: 1인 작업실
- ADE: 팀장이 여러 실무자를 배치해 동시에 일을 굴리는 상황판

그래서 Orca를 쓸 때는 "내가 직접 다 고친다"보다 "누구에게 무슨 일을 맡기고, 어떤 결과를 채택할까"라는 관점이 더 중요해집니다.

## Orca를 쓸 때 눈여겨볼 기능

기능 이름보다 감각을 먼저 잡는 편이 좋습니다.

### 1. 병렬 에이전트 실행

여러 worktree에 서로 다른 에이전트를 붙여 동시에 일을 돌릴 수 있습니다. 하나의 문제를 둘에게 각각 풀게 해 비교하는 것도 가능합니다.

### 2. diff 비교와 코멘트

각 에이전트가 만든 결과를 나란히 보고, 어떤 접근이 더 나은지 사람이 판단하기 좋습니다.

### 3. 모바일 알림과 원격 확인

무거운 작업을 돌려놓고 자리를 비웠다가, 끝났을 때 폰에서 확인하는 흐름이 가능합니다.

### 4. 디자인 모드와 화면 지시

웹 화면에서 특정 요소를 직접 가리키며 수정 요청을 줄 수 있어, UI 작업에서 말로 설명하는 부담을 줄여줍니다.

## 왜 비개발자에게도 Orca가 잘 맞을까

여기서부터는 개발자의디자인 글 `비개발자에게 orca를 추천하는 이유`의 감각을 4060미들스쿨 눈높이로 다시 풀어보겠습니다.

비개발자가 AI 도구를 쓸 때 가장 먼저 막히는 부분은 보통 코드 자체가 아닙니다.

- 어디가 바뀌었는지 확인하는 일이 번거롭고
- 내가 말한 위치를 AI가 자꾸 엉뚱하게 이해하고
- 혹시 원본 파일이 망가질까 불안하고
- 오래 걸리는 작업은 자리에 앉아 기다려야 하는 경우가 많습니다

Orca가 주목받는 이유는 이 불편을 꽤 정면으로 건드리기 때문입니다.

### 1. 시키는 것부터 확인하는 것까지 한 화면에서 끝난다

다른 도구를 쓰다 보면 자주 이런 흐름이 됩니다.

- AI에게 수정 요청
- 폴더 앱으로 가서 파일 확인
- 다시 브라우저로 가서 화면 확인
- 이상하면 다시 돌아와 설명 수정

이 과정이 한두 번이면 괜찮지만, 열 번만 반복해도 피곤합니다.

Orca는 에이전트 터미널, 파일 목록, 브라우저 확인 화면이 한곳에 모여 있어서, "시켰다 → 결과를 봤다 → 다시 고쳤다"가 한 호흡으로 이어집니다.

쉽게 말하면, 주방에서 요리시키고 거실로 가서 확인하고 다시 주방으로 뛰어가는 대신, 조리대 옆에서 바로 맛을 보는 느낌입니다.

### 2. 말로 길게 설명하지 않고, 화면에서 바로 가리킬 수 있다

비개발자에게 제일 답답한 순간은 수정 요청입니다.

> 위에서 두 번째 박스 안에 있는 작은 글씨를 좀 더 진하게 해줘.

이렇게 말하면 사람끼리는 대충 통하지만, AI는 의외로 엉뚱한 곳을 고칠 때가 많습니다.

Orca 디자인 모드는 이 불편을 줄여줍니다.

- 실제 화면에서 고치고 싶은 요소를 클릭하고
- 그 정보를 바로 에이전트에게 넘기고
- 다시 같은 화면에서 결과를 확인할 수 있습니다

즉, "설명"보다 "지목"에 가까운 방식입니다. 4060미들스쿨 기준으로 말하면, 전화로 길 찾기를 설명하는 것보다 지도에서 정확한 건물을 손가락으로 짚어 주는 쪽에 가깝습니다.

### 3. 원본을 바로 망가뜨릴까 봐 덜 불안하다

이 부분이 특히 중요합니다.

많은 비개발자는 작업 전에 폴더를 통째로 복사해 둡니다. 혹시라도 잘못 건드리면 돌아올 곳이 있어야 마음이 놓이기 때문입니다.

Orca는 바로 이 불안을 줄이는 쪽으로 설계돼 있습니다.

- 기본 원본은 따로 두고
- 새 작업은 복사된 작업 공간에서 돌고
- 마음에 드는 것만 마지막에 합칩니다

이 감각은 worktree 설명과 정확히 이어집니다.

> 원본 서류철은 금고 안에 두고, 복사본 서류로 먼저 표시하고 수정한 뒤, 확인된 것만 원본에 반영하는 방식입니다.

그래서 Git을 잘 모르는 사람에게도 "실수하면 다 끝장" 같은 압박이 조금 줄어듭니다.

### 4. 여러 일을 한꺼번에 돌리더라도 덜 헷갈린다

처음부터 병렬 작업이 꼭 필요한 것은 아닙니다. 하지만 조금만 익숙해지면 이런 장면이 생깁니다.

- 한쪽에서는 홈페이지 문구 수정
- 다른 쪽에서는 FAQ 정리
- 또 다른 쪽에서는 모바일 화면 확인

이걸 한 작업 공간에서 모두 섞어 돌리면 누가 뭘 바꿨는지 헷갈립니다.

Orca는 worktree 단위로 작업을 나눠 보기 좋게 보여주기 때문에, 비개발자도 "지금 이건 홈페이지 수정용", "저건 FAQ 실험용"처럼 작업의 주인을 구분하기가 훨씬 쉽습니다.

즉, 하나의 큰 책상에 종이를 마구 쌓는 방식이 아니라, 책상마다 이름표를 붙여놓는 쪽에 가깝습니다.

### 5. 자리에 꼭 붙어 있지 않아도 된다

AI 에이전트 작업은 한 번 시키면 몇 분씩 걸릴 때가 많습니다. 그동안 화면만 멍하니 보고 있는 것은 생각보다 피곤합니다.

Orca는 모바일 연동 흐름까지 제공해서, 작업을 돌려 놓고 잠깐 자리를 비운 뒤 확인하기가 좋습니다.

이건 4060미들스쿨 회원분들께도 꽤 현실적인 장점입니다.

- 집에서는 맥이나 PC에 작업을 돌려놓고
- 밖에서는 폰으로 상태를 보고
- 끝났을 때 다음 지시만 이어서 내릴 수 있습니다

말하자면, 집에 있는 컴퓨터가 조용히 일하고 있고, 나는 외출 중에 진행 상황만 확인하는 셈입니다.

## 비개발자 입장에서 딱 두 가지만 기억하면 된다

Orca를 어렵게 느끼지 않으려면, 아래 두 줄만 먼저 잡아도 충분합니다.

- 프로젝트는 그냥 내가 관리하는 폴더다
- 작업 트리는 그 폴더를 복사해 에이전트에게 맡긴 임시 작업 자리다

이 두 줄만 이해하면, Orca가 왜 단순한 채팅창보다 덜 불안하고 덜 헷갈리는지 금방 감이 옵니다.

처음부터 병렬 에이전트나 복잡한 머지 전략까지 들어갈 필요는 없습니다. 오히려 첫 단계는 이 정도면 충분합니다.

1. 작업 폴더 하나를 프로젝트로 등록한다.
2. 작은 수정 하나를 새 작업 자리에서 시켜본다.
3. 결과를 화면에서 직접 확인한다.
4. 마음에 들면 반영하고, 아니면 버린다.

이 흐름이 손에 익으면, 그다음부터는 Orca를 "개발자만 쓰는 어려운 도구"보다 "AI를 덜 불안하게 부리는 작업 환경"으로 보게 됩니다.

## Orca를 쓴다고 AI가 더 빨라지는 걸까

많이 오해하는 부분이라 짚고 넘어가면 좋겠습니다.

Orca가 모델 자체를 빠르게 만드는 것은 아닙니다. 체감상 빨라지는 이유는, **하나의 긴 줄을 기다리지 않고 여러 작업을 병렬로 굴리기 때문**입니다.

마트 계산대 비유가 잘 맞습니다.

- 계산원 속도는 그대로입니다.
- 그런데 계산대가 4개면 전체 흐름은 훨씬 빨라집니다.

Orca의 속도감은 모델 가속보다, **에이전트와 작업 자리를 병렬로 나눠 굴리는 구조**에서 나옵니다.

## 실제로는 어떤 흐름으로 쓰게 될까

처음에는 아래 4단계만 기억해도 충분합니다.

1. 태스크를 고릅니다.
2. 어떤 에이전트에게 맡길지 정합니다.
3. worktree를 만듭니다.
4. 결과 diff를 비교하고 채택할 것만 머지합니다.

이 흐름은 생각보다 중요합니다. AI를 잘 쓰는 감각은 "많이 시키는 것"보다, **결과를 비교하고 고르는 기준을 갖는 것**에 더 가깝기 때문입니다.

## 언제 worktree를 쓰면 좋을까

아래 정도면 실전에서 바로 판단이 됩니다.

| 상황 | 추천 |
| --- | --- |
| 지금 하던 작업이 있는데 다른 브랜치의 급한 수정이 생김 | worktree |
| 두 브랜치를 동시에 실행하며 비교해야 함 | worktree |
| AI 에이전트 둘 이상에게 병렬로 맡기고 싶음 | worktree + Orca 같은 지휘 환경 |
| 금방 끝나는 단순 브랜치 이동 | 그냥 `git switch` |

## 같이 기억하면 좋은 주의점

좋은 점만 보면 오히려 실수가 생깁니다.

- 병렬 에이전트를 3개 돌리면 사용량도 거의 3배 감각으로 늘어납니다.
- 리뷰 없이 바로 머지하면, 병렬 작업의 장점보다 위험이 커집니다.
- Git 기본 감각이 너무 없으면 Orca도 결국 낯설게 느껴집니다.

즉, Orca는 Git을 없애주는 도구가 아니라, **Git worktree를 더 실용적으로 쓰게 해주는 환경**이라고 보는 편이 맞습니다.

## 바로 떠올려볼 수 있는 5단계 실전 장면

초보자가 가장 자주 맞닥뜨리는 장면으로 한 번 묶어보겠습니다.

상황은 이렇습니다.

- 현재 `feature/login` 브랜치에서 로그인 기능을 만들고 있습니다.
- 그런데 갑자기 메인 화면 오타를 당장 고쳐야 합니다.

이때 worktree를 쓰면 흐름이 이렇게 됩니다.

1. 하던 로그인 기능 폴더는 그대로 둡니다.
2. 새 폴더를 하나 만들면서 `main` 브랜치를 펼칩니다.
3. 그 폴더에서 오타를 고치고 커밋하고 푸시합니다.
4. 다시 원래 로그인 기능 폴더로 돌아옵니다.
5. 급한 수정용 폴더는 작업이 끝나면 정리합니다.

명령으로 쓰면 대략 이런 흐름입니다.

```bash
git worktree add ../emergency-fix main
cd ../emergency-fix
# 오타 수정
git add .
git commit -m "Fix: 메인 화면 오타 수정"
git push origin main
cd ../원래-프로젝트-폴더
git worktree remove ../emergency-fix
```

여기서 제일 중요한 포인트는, **원래 하던 로그인 기능 코드가 전혀 흐트러지지 않는다**는 점입니다. 다시 돌아왔을 때 열어두었던 흐름이 그대로 남아 있는 것이 worktree의 가장 큰 장점입니다.

## 초보자가 꼭 알아둘 주의점 하나

실제로 가장 자주 부딪히는 제약은 이것입니다.

> 이미 다른 폴더에서 열어둔 브랜치를, 또 다른 worktree에서 같은 이름으로 다시 열 수는 없습니다.

왜냐하면 같은 브랜치를 두 작업 공간에서 동시에 수정하기 시작하면, 어느 쪽이 진짜 상태인지 Git이 판단하기 어려워지기 때문입니다.

이럴 때는 보통 아래처럼 정리하면 됩니다.

- 먼저 `git worktree list`로 어디에 어떤 브랜치가 열려 있는지 확인합니다.
- 정말 같은 브랜치를 건드려야 한다면, 이미 열려 있는 그 폴더로 직접 가서 수정합니다.
- 아니면 새 브랜치를 하나 더 따서 거기서 작업합니다.

## 다음에 바로 써볼 체크리스트

<ul class="note-list">
  <li>지금 하는 일이 정말 worktree가 필요한 일인지 먼저 구분합니다. 단순 이동이면 그냥 브랜치 전환으로도 충분합니다.</li>
  <li>병렬 에이전트를 돌릴 때는 각 에이전트가 손댈 폴더를 확실히 분리하고, 마지막 diff 리뷰는 사람이 직접 합니다.</li>
  <li>작업이 끝난 뒤에는 `git worktree list`로 남은 작업 자리를 점검하고, 끝난 것은 `remove`와 `prune`으로 정리합니다.</li>
</ul>

## 남겨둘 판단

Git worktree는 예전부터 있던 기능이지만, AI 에이전트를 여러 명 붙여 일시키는 흐름이 많아진 지금 훨씬 실감나게 중요해졌습니다. 그리고 Orca는 그 감각을 "한 화면에서 지휘하는 방식"으로 보여주는 도구라고 이해하면 무리 없이 들어옵니다.

처음부터 거창하게 시작할 필요는 없습니다. 가장 좋은 첫걸음은 작은 저장소 하나에서 worktree를 두 개 만들어보고, 서로 다른 브랜치를 실제로 열어보는 것입니다. 그 감각이 잡히면 Orca 같은 도구를 볼 때도 훨씬 덜 막막합니다.
