# Graphify와 Obsidian을 같이 쓰면, Claude Code가 왜 같은 질문에 덜 헤매게 될까

Claude Code 같은 AI 코딩 도구를 쓰다 보면 비슷한 질문을 자꾸 다시 하게 됩니다.

- 이 프로젝트는 어디서부터 읽으면 되는지
- HTTP 요청은 어디서 들어와 어디서 끝나는지
- 이 함수와 저 모델은 어떤 파일을 거쳐 연결되는지

작은 프로젝트에서는 괜찮습니다. 하지만 파일 수가 많아지고, 한 파일이 몇천 줄씩 길어지면 이야기가 달라집니다. AI는 질문 하나에 답하려고 관련 파일을 다시 찾고, 읽고, 연결 관계를 다시 추론해야 합니다. 그만큼 응답 시간도 늘고 토큰 비용도 커집니다.

이 문제를 줄이는 방법이 있습니다. **코드베이스를 먼저 구조화해 두고, AI가 그 구조를 보고 필요한 부분을 찾아가게 만드는 것**입니다. 오늘 글은 그 흐름을 Graphify, Obsidian, Claude Code 기준으로 아주 쉽게 정리한 글입니다.

## 먼저 결론

- AI에게 매번 프로젝트를 처음부터 읽히는 대신, **미리 만든 코드 지도**를 보게 하면 반복 탐색 비용을 줄일 수 있습니다.
- Graphify는 코드베이스를 **지식 그래프**로 바꾸고, Obsidian은 그 그래프를 사람이 읽기 쉬운 **제2의 뇌**처럼 보여 줍니다.
- Claude Code는 그 위에서 필요한 관계를 더 짧게 찾을 수 있어, 큰 코드베이스일수록 같은 질문에 덜 헤매게 됩니다.

## 왜 이런 도구가 필요할까

AI 코딩 도구는 세션이 바뀌면 이전 맥락을 잃는 경우가 많습니다. 그래서 다음 세션에서 다시 물어보면, 비슷한 설명을 또 반복하게 됩니다.

예를 들어 Django 프로젝트에서 "HTTP 요청이 들어와 응답이 나가기까지 흐름을 설명해줘"라고 묻는다고 해보겠습니다. AI는 URL 라우팅, 미들웨어, view, 예외 처리, 응답 반환 흐름을 찾기 위해 여러 파일을 다시 읽어야 합니다.

작을 때는 괜찮지만, 프로젝트가 커질수록 이 탐색 비용은 점점 커집니다.

기존 RAG 방식처럼 코드를 조각내 검색하는 방법도 있지만, 코드에서는 단순 텍스트보다 **연결 관계**가 더 중요할 때가 많습니다.

- 어떤 함수가 어디서 호출되는지
- 어떤 클래스가 어떤 모듈과 묶여 움직이는지
- 설정 파일이 실행 흐름에 어떤 영향을 주는지

이런 질문은 단순 검색만으로는 놓치기 쉽습니다. 그래서 코드 분석에는 그래프 기반 접근이 잘 맞습니다.

## Graphify는 무엇을 해 주나

Graphify는 코드와 문서를 그래프 구조로 바꾸는 오픈소스 도구입니다.

쉽게 말하면 프로젝트 안의 파일, 함수, 클래스, 문서, 관계를 **노드와 엣지**로 바꿔 줍니다. AI가 매번 전체 파일을 뒤지는 대신, 미리 만들어 둔 코드 지도를 보고 필요한 부분을 찾아갈 수 있게 되는 셈입니다.

실행 후에는 보통 이런 결과물이 생깁니다.

```text
graphify-out/
  graph.html
  graph.json
  GRAPH_REPORT.md
```

각 파일의 역할은 다음과 같습니다.

- `graph.html`: 코드 구조를 눈으로 보는 시각화 파일
- `graph.json`: AI가 질의할 수 있는 구조화된 그래프 데이터
- `GRAPH_REPORT.md`: 노드 수, 엣지 수, 주요 구조를 요약한 리포트

특히 중요한 점은, 코드 매핑 자체가 **AST 기반 로컬 처리**라는 점입니다. 즉, 구조를 그래프로 바꾸는 단계 자체에는 보통 LLM 토큰을 쓰지 않습니다. 먼저 지도를 만들고, 그 다음에 AI가 그 지도를 활용하는 구조입니다.

## Obsidian은 왜 같이 나오나

Graphify가 AI를 위한 지도라면, Obsidian은 사람을 위한 지도에 가깝습니다.

Graphify가 만든 결과를 Obsidian vault로 열면 코드와 개념이 마크다운 노트처럼 연결됩니다. 사람은 Obsidian의 검색과 그래프 뷰를 통해 "어디가 중심이고 무엇이 어디와 연결되는지"를 더 편하게 볼 수 있습니다.

역할을 나누면 이렇게 이해하면 쉽습니다.

```text
Graphify: 코드베이스를 지식 그래프로 변환
Obsidian: 사람이 이해하기 쉬운 노트와 그래프로 시각화
Claude Code: 그 구조를 바탕으로 필요한 정보를 찾아 추론
```

핵심은 AI와 사람이 **같은 프로젝트 지도**를 본다는 점입니다. AI는 더 빨리 찾고, 사람은 더 잘 이해하며, 둘 사이 대화도 훨씬 짧아집니다.

## 초보 개발자 기준으로 보면 무엇이 제일 좋아질까

초보자에게 가장 큰 변화는 "어디서부터 읽어야 하지?"라는 막막함이 줄어드는 점입니다.

처음 보는 프로젝트에서 막히는 이유는 보통 실력이 부족해서라기보다, **입구를 모르기 때문**인 경우가 많습니다.

그래서 이 질문이 생각보다 중요합니다.

```text
이 프로젝트를 처음 읽는 개발자가 어떤 파일부터 보면 좋을지 순서대로 알려줘.
```

이 질문 하나만 잘 써도, AI가 단순 요약 도구가 아니라 **코드베이스 길잡이**처럼 동작하기 시작합니다.

## 가장 기본적인 사용 흐름

처음부터 회사 전체 저장소에 걸기보다, 작은 개인 프로젝트나 특정 폴더부터 시작하는 편이 좋습니다.

먼저 프로젝트 폴더로 이동합니다.

```bash
cd /path/to/my-project
```

그 다음 Graphify를 설치하고 실행합니다.

```bash
pip install graphifyy
graphify install
graphify .
```

여기서 한 가지 기억할 점이 있습니다. 공식 README 기준으로 현재 PyPI 패키지 이름은 임시로 `graphifyy`를 쓰지만, 설치 후 실제 CLI 이름과 Claude Code 스킬 이름은 `graphify`입니다.

실행이 끝나면 `graphify-out` 폴더가 생기고, 이제 Claude Code나 비슷한 환경에서 이런 질문을 던질 수 있습니다.

```text
/graphify query "이 프로젝트의 핵심 모듈을 설명해줘"
/graphify query "HTTP 요청이 들어와서 응답이 나가기까지 흐름을 알려줘"
/graphify path "LoginView" "User"
/graphify explain "QuerySet"
```

처음에는 이 모든 명령을 다 쓸 필요는 없습니다. 아래 두 개만 기억해도 충분합니다.

```bash
graphify .
```

```text
이 프로젝트를 처음 이해하려면 어떤 파일부터 봐야 해?
```

## Obsidian에서는 어떻게 보면 좋을까

Graphify 결과를 Obsidian vault 형태로 열면, 코드 구조가 노트처럼 보이기 시작합니다.

Obsidian에서는 이런 식으로 활용할 수 있습니다.

- 특정 키워드로 관련 노드만 좁혀 보기
- 메서드와 클래스 링크를 따라가기
- 연결이 많은 핵심 노드 찾기
- 내 메모나 팀 설명을 노트로 덧붙이기

예를 들어 Django 프로젝트라면 `queryset`, `model`, `view`, `middleware` 같은 키워드로 좁혀 보면서 흐름을 잡을 수 있습니다.

초보자 기준으로는 전체 그래프를 한 번에 보려 하기보다, **내가 오늘 이해하려는 기능 주변만 좁혀 보는 것**이 훨씬 낫습니다.

## 코드가 바뀌면 그래프도 다시 갱신해야 한다

코드는 계속 바뀌기 때문에 지도도 다시 그려야 합니다.

가장 단순한 방법은 다시 실행하는 것입니다.

```bash
graphify .
```

매번 수동으로 하기 번거롭다면 Git hook을 설치해 자동으로 갱신하는 방식도 있습니다.

```bash
graphify hook install
```

핵심은 이것입니다.

> 프로젝트 구조가 바뀌었는데 AI가 옛 지도를 보고 있으면, 답변도 낡아질 수밖에 없다.

## 실제 비용과 시간은 어느 정도 차이 날까

원본 영상에서는 Django 코드베이스를 대상으로 같은 프롬프트를 비교했습니다. 질문은 "HTTP 요청이 들어와 응답이 나가기까지의 전체 처리 과정을 설명해 달라"는 내용이었습니다.

영상에서 소개한 비교는 이렇습니다.

| 조건 | 응답 시간 | 비용 | 출력 토큰 |
| --- | ---: | ---: | ---: |
| Graphify 사용 | 약 56초 | 약 `$0.183` | 약 2.0K |
| Graphify 미사용 | 약 1분 53초 | 약 `$0.58` | 약 5.2K |

이 실험에서는 비용이 대략 3분의 1 수준까지 줄었다고 소개됩니다.

물론 이 숫자를 그대로 일반화하면 안 됩니다. 프로젝트 크기, 질문 난이도, 모델, 캐시 상태에 따라 결과는 달라질 수 있습니다. 그래도 방향은 분명합니다.

> 큰 코드베이스일수록, 매번 처음부터 구조를 다시 읽는 비용이 커진다.

그리고 Graphify 같은 구조 지도가 있으면 그 반복 비용을 줄일 가능성이 높아집니다.

## 바로 써볼 자연어 질문 예시

초보자에게는 명령어보다 질문 문장이 더 중요할 때가 많습니다. 아래 정도만 바로 써봐도 충분히 감이 옵니다.

```text
이 프로젝트를 처음 읽는 개발자가 어떤 파일부터 보면 좋을지 순서대로 알려줘.
```

```text
로그인 요청이 들어와 응답이 나가기까지 어떤 파일을 거치는지 단계별로 설명해줘.
```

```text
이 기능을 수정하면 같이 확인해야 할 파일이나 클래스가 어디인지 연결 관계 중심으로 알려줘.
```

```text
이 프로젝트에서 연결이 많은 핵심 노드 다섯 개를 뽑고, 왜 중요한지 설명해줘.
```

좋은 질문의 공통점은 "대충 요약해줘"가 아니라, **읽기 순서, 흐름, 영향 범위, 핵심 연결점**처럼 구조를 묻는다는 점입니다.

## 주의할 점

Graphify가 만든 그래프는 정답지가 아니라 지도입니다. AI가 그래프를 보고 답하더라도, 실제 수정 전에는 관련 코드를 직접 확인해야 합니다.

또 하나는 범위 문제입니다. 코드 AST 분석은 로컬 처리라고 설명되지만, 문서나 PDF, 이미지, 영상 같은 비코드 자료는 사용하는 설정에 따라 외부 모델이나 API가 관여할 수 있습니다. 민감한 자료를 넣을 때는 범위를 꼭 확인해야 합니다.

그리고 `graph.html`은 노드가 너무 많아지면 브라우저에서 무겁게 열릴 수 있습니다. 영상에서도 노드 수가 많아지면 HTML 시각화가 부담될 수 있다고 언급합니다. 이럴 때는 전체를 억지로 한 번에 보기보다, Obsidian이나 특정 폴더 단위로 범위를 줄여 보는 편이 좋습니다.

## 남겨둘 판단

AI 코딩 비용을 줄이는 핵심은 프롬프트를 더 길게 쓰는 것이 아닙니다. **AI가 매번 프로젝트를 처음부터 읽지 않게 만드는 것**입니다.

Graphify는 코드베이스를 지식 그래프로 바꾸고, Obsidian은 그 그래프를 사람이 읽을 수 있는 제2의 뇌처럼 보여 줍니다. Claude Code는 그 위에서 필요한 구조를 더 빨리 찾아갈 수 있습니다.

오늘 바로 하나만 해 본다면 이것부터면 충분합니다.

```bash
graphify .
```

그리고 이렇게 물어보면 됩니다.

```text
이 프로젝트를 처음 이해하려면 어떤 파일부터 봐야 해?
```

그 순간부터 AI는 단순 검색 도구보다, 프로젝트 구조를 함께 탐색하는 개발 파트너에 조금 더 가까워집니다.
