# 2026년 8월 20일(목) AI로 만든 앱이 왜 이렇게 쉽게 털릴까, 4060미들스쿨용 바이브 코딩 보안 체크리스트 1부

AI로 앱을 만들기 쉬워진 건 분명 좋은 일입니다.  
예전보다 훨씬 빠르게 화면을 만들고, 기능을 붙이고, 배포까지 가볼 수 있게 됐습니다.

그런데 속도가 붙을수록 같이 커지는 게 하나 있습니다.

바로 <strong>"기본 보안을 빼먹은 채 배포해 버리는 실수"</strong>입니다.

이번 글은 그 부분을 다룹니다.  
잘생김프로쌤께서 보내주신 영상 정리 자료를 바탕으로, 4060미들스쿨 중급반 회원님들과 나누기 좋은 눈높이로 다시 풀었습니다.

이 글의 성격은 분명합니다.

- 원본 영상 내용을 학습한 뒤
- 스터디 목적으로 다시 정리했고
- 회원분들과 나누는 블로그용 자료로 썼으며
- 실제 적용 전에는 원본 영상과 최신 문서도 다시 확인하는 것을 전제로 합니다

## 먼저 결론

- AI로 만든 앱이 털리는 이유의 상당수는 대단한 해킹 기술보다 **잠금장치를 안 걸고 배포했기 때문**입니다.
- 이번 1부에서 꼭 볼 건 딱 두 묶음입니다. `API 키 5가지`, `데이터베이스 4가지`입니다.
- 회원분들 기준으로는 "어떻게 고치나"보다 먼저 **내 앱에서 이게 열려 있는지 확인하는 습관**을 들이는 것이 중요합니다.

## 왜 이 이야기가 중요한가

원문에서 가장 아픈 부분은 사고가 너무 거창하지 않았다는 점입니다.

- 저장소 설정 하나를 놓쳐서 사용자 이미지 수만 장이 유출된 사례
- 결제용 API 키를 코드에 그대로 넣고 배포했다가 며칠 만에 서비스가 무너진 사례

둘 다 영화 같은 해킹이 아닙니다.  
누가 슈퍼컴퓨터로 뚫은 것도 아닙니다.

그냥

- 브라우저 개발자 도구를 열어 보면 보였고
- 공개 저장소를 뒤져 보면 찾을 수 있었고
- 잠가야 할 문이 열려 있었던 것

에 더 가깝습니다.

그래서 이번 글은 "무서운 이야기"를 하려는 게 아니라,  
<strong>지금 내 프로젝트에서 어디 문을 먼저 잠가야 하는지 보는 글</strong>로 읽으시면 됩니다.

## 먼저 머릿속에 넣어둘 두 가지 비유

### API 키는 신용카드다

API 키는 단순한 문자열이 아닙니다.  
누가 그 키를 주워서 쓰면 **내 비용으로 결제**가 나갑니다.

그러니 화면에 보이게 두거나, 공개 저장소에 올리거나, AI 채팅창에 복사해 넣는 건
"카드 사진을 여러 사람 앞에 펴놓는 것"과 비슷합니다.

### 데이터베이스는 금고다

데이터베이스에는 보통 이런 게 들어갑니다.

- 이메일
- 이름
- 전화번호
- 주소
- 결제 관련 정보
- 업로드 파일 정보

즉, 앱의 가장 중요한 내용물입니다.  
RLS나 정책 설정은 그 금고 문과 칸막이에 다는 잠금장치라고 보면 됩니다.

## API 키 체크리스트 5가지

### 1. `.env` 파일이 깃허브에 올라간 적이 없는가

`.env`는 보통 비밀 메모장입니다.  
테스트 키, 운영 키, 토큰, 비밀번호 비슷한 값이 들어갑니다.

문제는 이 파일이 공개 저장소에 한 번이라도 올라가면,
파일을 나중에 지워도 **기록에는 남을 수 있다**는 점입니다.

여기서 많이 생기는 착각이 있습니다.

> "지금은 안 보이니까 괜찮지 않나?"

그렇지 않을 수 있습니다.  
해커들은 현재 파일만 보는 게 아니라, 커밋 기록까지 자동으로 훑습니다.

### 어떻게 확인하나

1. 저장소 파일 목록에 `.env`가 보이지 않는지 본다.
2. `.gitignore` 안에 `.env`가 들어 있는지 확인한다.
3. 과거 기록에도 있었는지 `git log --all --full-history -- .env`로 본다.

### 여기서 기억할 말

<strong>올렸다가 지우는 것과, 처음부터 안 올리는 것은 전혀 다릅니다.</strong>

### 2. 프론트엔드에 API 키가 노출되지 않았는가

앱은 보통 둘로 나뉩니다.

- 화면단, 즉 사용자가 보는 쪽
- 서버단, 즉 뒤에서 처리하는 쪽

화면단 코드는 누구나 볼 수 있습니다.  
브라우저에서 F12만 눌러도 꽤 많은 걸 확인할 수 있습니다.

그래서 결제 키나 관리자 키 같은 값을 프론트엔드에 넣으면 안 됩니다.

특히 Next.js를 쓰는 분은 `NEXT_PUBLIC_` 접두사를 더 조심해서 봐야 합니다.  
이 이름이 붙은 값은 "브라우저에 공개해도 되는 값"이라는 뜻에 가깝기 때문입니다.

### 어떻게 확인하나

- 크롬에서 F12
- `Sources` 탭
- 키 이름이나 의심되는 문자열 검색

### 여기서 기억할 말

<strong>화면에 내려간 코드는 비밀이 아니다.</strong>

### 3. AI 채팅창에 키를 붙여넣은 적이 없는가

이 부분은 요즘 특히 중요합니다.

AI가 일을 잘 도와주다 보니, 막히면 그대로 복붙하는 습관이 생기기 쉽습니다.

예를 들면 이런 식입니다.

- "이 키로 연결이 왜 안 되지?"
- "이 .env 내용 좀 보고 수정해줘"
- "이 토큰 그대로 넣었는데 왜 에러지?"

이렇게 넣으면 편해 보이지만,  
그 순간 비밀값이 채팅 기록과 모델 문맥 안으로 들어갑니다.

그리고 더 큰 문제는 AI가 실수로

- 화면 코드에 키를 다시 넣거나
- 예제 코드에 그대로 박아 넣거나
- 공개 가능한 값과 비밀값을 섞어버릴 수 있다는 점입니다.

### 어떻게 확인하나

- 예전 대화 기록을 한번 훑어 본다.
- 붙여넣은 적이 있다면 그 값을 더 이상 안전하다고 보지 않는다.
- 가능하면 해당 채팅의 컨텍스트도 지운다.

### 여기서 기억할 말

<strong>AI에게 묻는다고 해서 비밀값이 비밀로 유지되는 것은 아니다.</strong>

### 4. 노출된 적 있는 키는 즉시 폐기했는가

이건 아주 짧게 말할 수 있습니다.

키가 한 번 보였으면,

- 일부만 가리고 계속 쓰는 것으로 끝나면 안 되고
- 완전히 폐기하고
- 새로 발급해야 합니다

신용카드 번호가 새어 나갔는데
"일단 스티커로 좀 가렸으니 계속 쓰자"라고 하지는 않지요.

키도 똑같습니다.

### 여기서 기억할 말

<strong>노출된 키는 숨기는 대상이 아니라 교체하는 대상이다.</strong>

### 5. 키 유효기간이 무제한으로 열려 있지 않은가

유효기간이 무제한인 키는 편합니다.  
하지만 편한 만큼 사고도 오래 갑니다.

나중에 누출을 알아차려도,
그 키가 계속 살아 있으면 계속 쓸 수 있기 때문입니다.

짧은 만료 시간을 두면 최소한 피해가 끝없이 길어지는 건 막는 데 도움이 됩니다.

### 여기서 기억할 말

<strong>영원히 살아 있는 키는, 영원히 불안한 키다.</strong>

## 데이터베이스 체크리스트 4가지

### 6. RLS가 켜져 있는가

RLS는 `Row Level Security`, 우리말로는 행 수준 보안입니다.

이 말이 처음엔 어렵게 들리지만 뜻은 단순합니다.

회원 한 명의 정보가 테이블 한 줄이라고 보면,
RLS는 그 **한 줄 한 줄에 다는 잠금장치**입니다.

이게 꺼져 있으면 어떻게 되느냐.

공개 키만으로도 전체 정보가 통으로 보일 수 있습니다.

문제는 개발 중엔 잠깐 꺼두면 편하다는 점입니다.  
그래서 "나중에 켜야지" 했다가 그대로 나가는 경우가 꽤 많습니다.

### 어떻게 확인하나

- Supabase 테이블 에디터에서 경고 표시 확인
- RLS 꺼짐 알림이 보이면 바로 다시 본다

### 여기서 기억할 말

<strong>RLS를 안 켠 테이블은 금고 문을 반쯤 열어 둔 상태와 비슷하다.</strong>

### 7. 관리자 키 `service_role`이 노출되지 않았는가

이 키는 그냥 키가 아닙니다.

일반 공개 키가 건물 현관 열쇠라면,
`service_role`은 관리실 마스터키에 가깝습니다.

이 키는 RLS도 무시할 수 있어서,  
잘못 노출되면 피해 크기가 훨씬 커집니다.

그래서 이 키는 특히 더 조심해야 합니다.

- 프론트엔드에 있으면 안 되고
- 공개 코드에 있으면 안 되고
- 서버 안에서도 꼭 필요한 곳에서만 써야 합니다

### 어떻게 확인하나

- 프로젝트 전체에서 `service_role` 검색
- 브라우저 `Sources` 탭에서도 같은 문자열 검색

### 여기서 기억할 말

<strong>service_role은 "편하게 쓰는 키"가 아니라 "사고가 가장 크게 나는 키"다.</strong>

### 8. RLS 정책이 네 가지 다 잡혀 있는가

여기서 많이 하는 두 번째 착각이 나옵니다.

> "RLS 켰으니 이제 끝난 것 아닌가?"

아직 아닙니다.

보통은 아래 네 가지를 따로 생각해야 합니다.

- 조회 `Select`
- 추가 `Insert`
- 수정 `Update`
- 삭제 `Delete`

즉, 문만 잠갔다고 끝나는 게 아니라
"누가 들어오고, 무엇을 보고, 무엇을 바꾸고, 무엇을 지울 수 있는가"를 각각 정해야 합니다.

### 어떻게 확인하나

- Supabase 대시보드에서 테이블별 정책을 본다
- 네 가지가 각각 있는지 확인한다
- "내 데이터만 접근 가능" 기준이 들어 있는지 본다

### 여기서 기억할 말

<strong>RLS on은 시작이고, 정책 4종이 실제 운영이다.</strong>

### 9. 파일 저장소 버킷이 공개로 열려 있지 않은가

이 항목은 회원분들이 특히 실감하기 쉬운 부분입니다.

앱에 사진 업로드, 문서 업로드 같은 기능을 붙이다 보면
스토리지 버킷을 많이 씁니다.

여기서 버킷은 쉽게 말해
<strong>파일을 종류별로 넣어 두는 큰 보관함</strong>이라고 생각하면 됩니다.

예를 들면 이런 식입니다.

```text
Storage
├── profile-images
├── student-files
└── documents
```

버킷은 보통 두 가지 상태로 나뉩니다.

| 설정 | 쉬운 뜻 |
| --- | --- |
| Public | 주소를 알면 파일을 볼 수 있음 |
| Private | 권한이 있는 사람만 볼 수 있음 |

그래서 회사 로고, 공개 배너 같은 자료는 Public이어도 큰 문제가 없을 수 있지만,

- 학생 개인정보가 담긴 파일
- 회원 전용 자료
- 내부 문서
- 비공개 사진

같은 것은 기본값을 Private 쪽으로 생각하는 편이 더 안전합니다.

여기서 생기는 대표 사고는 두 가지입니다.

1. 버킷 자체가 공개로 열려 있음
2. 파일명이 `1.jpg`, `2.jpg`처럼 너무 예측 가능함

이 둘이 겹치면,
주소만 조금 바꿔 보면서 남의 파일까지 열어보는 일이 벌어질 수 있습니다.

쉽게 비유하면 이렇습니다.

```text
Public Bucket
→ 창고 문이 열려 있음

1.jpg, 2.jpg, 3.jpg
→ 상자 번호도 너무 규칙적임
```

이 구조에서는 누군가

> `1.jpg`가 열리네?  
> 그럼 `2.jpg`, `3.jpg`도 있지 않을까?

라고 생각하며 주소를 바꿔 볼 수 있습니다.

즉 위험한 조합은 보통 아래처럼 정리됩니다.

```text
Public Bucket
+ 예측 가능한 파일명
↓
파일 접근 위험 증가
```

### 버킷 점검 요청을 쉬운 말로 바꾸면

결국 이 항목은 아래 세 가지를 묻는 것과 같습니다.

1. 지금 공개로 열려 있는 버킷이 있는가
2. 파일 이름이 번호처럼 너무 쉽게 짐작되는가
3. 꼭 필요한 사람에게만 잠깐 열어 주는 구조로 바꿀 수 있는가

### 파일명이 왜 중요할까

예를 들어 파일 이름이 아래처럼 저장된다고 가정해 보겠습니다.

```text
1.jpg
2.jpg
3.jpg
4.jpg
```

이건 사람 입장에서도 패턴이 너무 쉽습니다.

코드에서도 이런 방식이 자주 보입니다.

```javascript
const fileName = `${studentNumber}.jpg`;
```

또는

```javascript
const fileName = `${index}.jpg`;
```

이런 코드가 나쁘다는 뜻이 아니라,
<strong>공개 버킷과 만나면 주소 추측이 쉬워진다</strong>는 점을 봐야 합니다.

### 개선 1. UUID처럼 추측하기 어려운 이름 쓰기

이 문제를 줄이는 첫 번째 방법은
파일 이름을 규칙적인 숫자 대신 추측하기 어려운 값으로 바꾸는 것입니다.

예를 들어 JavaScript에서는 이렇게 만들 수 있습니다.

```javascript
const fileName = `${crypto.randomUUID()}.jpg`;
```

그러면 파일 이름이 아래처럼 바뀔 수 있습니다.

```text
b7602919-facf-4f5d-b951-b7fe9fdc7277.jpg
```

이제 `2.jpg`, `3.jpg`처럼 다음 이름을 짐작하기가 훨씬 어려워집니다.

다만 여기서 꼭 기억할 점이 있습니다.

<strong>UUID는 파일 이름 추측을 어렵게 해줄 뿐이고, 접근 권한 자체를 지켜주는 것은 아닙니다.</strong>

### 개선 2. signed URL처럼 만료되는 주소 쓰기

두 번째 방법은 파일을 아예 공개 주소로 계속 열어두지 않고,
필요할 때만 잠깐 쓸 수 있는 임시 주소를 발급하는 것입니다.

이걸 signed URL이라고 부릅니다.

쉽게 말하면

> 일정 시간 동안만 유효한 임시 열쇠

라고 생각하면 됩니다.

예를 들어 Public URL은 한 번 알면 계속 접근될 수 있지만,
signed URL은 60초, 5분처럼 시간을 정해서 만료되게 만들 수 있습니다.

Supabase 예시는 이런 식입니다.

```javascript
const { data, error } = await supabase.storage
  .from('student-images')
  .createSignedUrl(filePath, 60);
```

이 코드는 해당 파일에 대해
약 60초 동안만 쓸 수 있는 임시 주소를 만들어 주는 뜻입니다.

### 기존 구조와 개선 구조를 나란히 보면

```text
기존 구조
Public Bucket
↓
1.jpg / 2.jpg / 3.jpg
↓
주소를 알면 계속 접근 가능
```

```text
개선 구조
Private Bucket
↓
UUID 파일명
↓
사용자 인증과 권한 확인
↓
필요할 때만 signed URL 발급
↓
일정 시간 후 만료
```

### 어떻게 확인하나

1. 버킷이 `Private`인지 본다.
2. 파일명이 예측 가능한 규칙인지 확인한다.
3. 가능하면 UUID 기반 이름을 쓴다.
4. signed URL처럼 기간 있는 접근 주소를 쓴다.
5. 시크릿 모드에서 파일 주소를 직접 열어 테스트해 본다.

열리면 안 되는 파일이 열리면, 그건 바로 다시 봐야 합니다.

### 여기서 기억할 말

<strong>파일 저장소는 "올렸으니 끝"이 아니라, "누가 어떻게 여는가"까지 봐야 한다.</strong>

### 이 항목에서 딱 기억할 핵심

```text
Private Bucket
+ UUID 파일명
+ 사용자 인증
+ 권한 정책
+ signed URL
↓
보다 안전한 파일 저장 구조
```

## 한눈에 보는 9가지 점검표

| 번호 | 항목 | 바로 볼 것 |
| --- | --- | --- |
| 1 | `.env` 깃 노출 | 저장소, `.gitignore`, 과거 커밋 |
| 2 | 프론트엔드 키 노출 | F12, `Sources`, 공개 변수 이름 |
| 3 | AI 채팅창 키 입력 | 예전 대화와 문맥 |
| 4 | 노출 키 재발급 | 무효화 후 새 키 발급 |
| 5 | 키 유효기간 | 무제한인지 확인 |
| 6 | RLS 설정 | 테이블 경고 표시 |
| 7 | 관리자 키 노출 | `service_role` 검색 |
| 8 | RLS 정책 4종 | Select / Insert / Update / Delete |
| 9 | 버킷 공개 여부 | Private 여부, 파일명, signed URL |

## 회원분들이 바로 써볼 점검 프롬프트

> 실제 키 값 자체는 절대 프롬프트에 붙여넣지 마세요.  
> 아래 프롬프트는 "프로젝트를 점검하게 하는 말"이지, 비밀값을 보여주라는 뜻이 아닙니다.

### 1. `.env`와 키 노출 전수 점검 프롬프트

```text
내 프로젝트 전체 코드를 스캔해서:
1. .env 또는 API 키가 들어있는 파일이 .gitignore에 등록되어 있는지 확인해줘
2. 프론트엔드(클라이언트) 코드에 API 키, 시크릿 키, 서비스 롤 키가
   하드코딩되어 있거나 NEXT_PUBLIC_ 등 공개 접두사가 붙은 채
   노출되어 있는 곳이 있는지 전부 찾아줘
3. 발견되면 파일명과 줄 번호를 알려주고,
   서버 사이드(.env, 백엔드)로 옮기는 방법을 제안해줘
   실제 키 값은 출력하지 마
```

### 2. 관리자 키 사용처 정리 프롬프트

```text
코드 전체에서 SUPABASE_SERVICE_ROLE_KEY 또는 서비스 어카운트 키를
사용하는 부분을 전부 찾아줘.
- 프론트엔드에서 쓰이고 있다면 전부 서버 API 라우트로 옮기고,
  프론트엔드에서는 anon key만 쓰도록 리팩토링 방향을 제안해줘
- 각 변경 사항을 파일별로 요약해줘
```

### 3. RLS 정책 점검 프롬프트

```text
내 Supabase 테이블 목록과 각 테이블의 RLS 활성화 여부,
그리고 Select/Insert/Update/Delete 각각에 대한 정책이 설정되어 있는지
점검할 수 있는 SQL 쿼리를 작성해줘.
정책이 없는 테이블이 있다면
"내 데이터만 접근 가능"하게 만드는 기본 정책 예시도 함께 제시해줘.
```

### 4. 버킷 공개 여부와 파일명 규칙 점검 프롬프트

```text
내 스토리지 버킷 설정을 점검해줘:
1. 어떤 버킷이 public으로 설정되어 있는지 알려줘
2. 업로드되는 파일명이 1.jpg, 2.jpg처럼 예측 가능한 패턴인지
   코드에서 확인해줘
3. UUID 기반 파일명 생성과 signed URL 방식으로
   바꾸는 코드를 제안해줘
```

## 스터디에서 이렇게 나눠 보면 좋습니다

<ul class="note-list">
  <li>먼저 "API 키는 신용카드, 데이터베이스는 금고"라는 비유부터 같이 잡습니다.</li>
  <li>그다음 9개를 외우려 하지 말고, "내 프로젝트에서 지금 어디 문이 열려 있나" 순서로 봅니다.</li>
  <li>실습 때는 실제 키를 보여주지 말고, 점검 프롬프트로 구조만 검사하는 습관을 먼저 들입니다.</li>
  <li>Supabase를 쓰는 분은 RLS와 service_role, 버킷 공개 여부 세 가지만 먼저 봐도 도움이 큽니다.</li>
</ul>

## 남겨둘 판단

이번 1부를 한 줄로 줄이면 이렇습니다.

> 바이브 코딩 보안 사고는 "아주 어려운 해킹"보다 "기본 잠금장치를 안 건 채 배포한 실수"에서 더 자주 시작된다.

그래서 초보자든 중급자든 먼저 필요한 것은

- 더 긴 코드가 아니라
- 더 화려한 도구가 아니라
- 내 앱에서 비밀값, 관리자 키, 데이터 잠금, 파일 공개 여부를
  한 번씩 확인하는 습관

입니다.

2부가 이어지면 인증과 인가, 암호화, 개인정보처리방침까지 같이 보면 좋겠습니다.  
하지만 1부만 잘 챙겨도 이미 큰 사고 몇 가지는 꽤 현실적으로 줄일 수 있습니다.
