# 2026년 8월 22일(토) 해커톤에서 깃허브 협업이 덜 무서워지는 가장 쉬운 순서

해커톤에 처음 가면 코딩보다 먼저 막히는 순간이 있습니다.  
"코드는 어디에 올리지?", "같이 만지다가 꼬이면 어떡하지?", "AI는 어디까지 맡겨도 되지?" 같은 질문이 한꺼번에 몰려올 때입니다.

이번 글은 바로 그 순간을 줄이기 위한 정리입니다.  
잘생김프로쌤께서 보내주신 해커톤 협업 가이드를 바탕으로, 4060미들스쿨 회원분들이 발표 때도 바로 나눌 수 있게 눈높이를 다시 맞췄습니다.

## 출처와 활용 방식

<ul class="note-list">
  <li>이번 글은 사용자가 제공한 원문 <code>해커톤 완전정복: 신입 개발자 민수의 깃허브 협업 성장기</code>를 바탕으로 다시 정리했습니다.</li>
  <li>원문의 이야기 흐름은 살리되, 발표와 스터디에 바로 쓰기 좋게 설명 순서, 표, 체크리스트, 용어집을 다시 구성했습니다.</li>
  <li>GitHub 화면 이름이나 버튼 문구는 이후 조금 달라질 수 있으니, 실제 적용 전에는 현재 화면도 함께 확인해 주세요.</li>

## 먼저 결론

- 팀 협업에서 제일 중요한 건 **완성본은 main에 두고, 사람마다 자기 브랜치에서 따로 작업하는 습관**입니다.
- AI는 "알아서 다 해줘"보다 **스펙 먼저 확정하고, 승인한 뒤에 단계별로 구현시키는 방식**이 훨씬 안전합니다.
- 충돌은 고장이 아니라 **같은 줄을 두 사람이 다르게 고쳤을 때 생기는 정상 신호**입니다. 당황하지 말고 대화로 정리하면 됩니다.

## 먼저 큰 그림부터 잡으면 덜 헷갈립니다

원문에서 가장 좋았던 비유는 이것입니다.

"팀의 진짜 완성본 공책은 한 권이고, 팀원은 각자 자기 연습 노트에 먼저 쓴 뒤, 다 되면 팀장에게 보여준다."

이 비유를 깃허브 용어로 바꾸면 아래처럼 정리됩니다.

| 쉬운 비유 | 깃허브 용어 |
| --- | --- |
| 팀의 진짜 완성본 공책 | `main` 브랜치 |
| 각자 따로 쓰는 연습 노트 | 개인 브랜치 |
| 노트에 한 덩어리 저장하기 | commit |
| 팀장에게 "검토해 주세요" 하고 올리기 | push + Pull Request |
| 팀장이 확인하는 과정 | 코드 리뷰 |
| 팀장이 완성본에 반영하기 | merge |

이 표만 먼저 머리에 넣어도, 명령어가 훨씬 덜 차갑게 보입니다.

## 해커톤 하루 흐름은 이렇게 보면 쉽습니다

### 1. 리더가 팀 공책을 만든다

처음 한 번은 리더가 합니다.

1. GitHub에서 새 리포지토리를 만든다.
2. 팀원을 초대한다.
3. `README.md`에 프로젝트 설명과 실행 방법을 적는다.

여기서 팀원이 굳이 서둘러 할 일은 거의 없습니다.  
초대가 올 때까지 기다리면 됩니다.

### 2. 팀원은 리포를 자기 컴퓨터로 가져온다

```bash
git clone https://github.com/팀리더/hackathon-team4.git
```

이건 "팀 공책을 내 책상으로 복사해 온다"는 뜻입니다.

폴더 이름을 내가 정하고 싶으면 이렇게 쓸 수도 있습니다.

```bash
git clone https://github.com/팀리더/hackathon-team4.git 내작업폴더
```

복사가 끝나면 아래처럼 폴더로 들어가 파일이 보이는지만 확인해도 충분합니다.

```bash
cd 내작업폴더
ls
```

### 3. 큰 일 하나를 통째로 잡지 말고, 작은 일로 나눈다

해커톤에서는 일이 크면 바로 꼬이기 쉽습니다.  
그래서 `Issues`로 작게 나누는 습관이 중요합니다.

예를 들면 이런 식입니다.

- 로그인 화면 구현
- 메인 화면 UI
- API 연동

이렇게 나누면 누가 뭘 맡았는지 바로 보이고, 같은 파일을 여러 명이 동시에 건드릴 가능성도 줄어듭니다.

### 4. 작업 시작 전에는 내 브랜치부터 만든다

```bash
git checkout main
git pull origin main
git checkout -b feature/민수-로그인
```

이 세 줄은 해커톤 협업의 기본 출발점이라고 보셔도 됩니다.

1. `git checkout main`  
지금 기준이 되는 완성본 자리로 간다.

2. `git pull origin main`  
내가 모르는 사이 바뀐 최신 내용을 먼저 받아온다.

3. `git checkout -b feature/민수-로그인`  
내 작업용 새 브랜치를 만들고 바로 그 자리로 이동한다.

현재 내가 어느 브랜치에 있는지 헷갈리면 이렇게 봅니다.

```bash
git branch
```

별표 `*`가 붙은 줄이 지금 내가 서 있는 자리입니다.

## AI는 바로 코딩시키지 말고, 스펙부터 확정하는 편이 낫습니다

원문에서 특히 실무적인 부분은 여기였습니다.  
AI에게 바로 "로그인 화면 만들어줘"라고 하면, 빠르긴 해도 팀이 원하는 모양과 다르게 흘러가기 쉽습니다.

그래서 먼저 스펙을 정합니다.

```text
너는 지금부터 절대 코드를 작성하지 마.
내가 만들려는 기능은 로그인 화면이야.
아래 8가지를 나와 하나씩 대화로 확정해줘. 애매한 건 반드시 질문해.

1. 화면 구성
2. 핵심 기능
3. 데이터 구조
4. 기술 스택
5. 디자인 방향
6. 이번엔 제외할 기능
7. 완료 조건
8. 테스트 방법

다 정해지면 SPEC.md 파일로 정리해서 보여주고,
내가 "승인"이라고 말하기 전까진 파일 수정도, 패키지 설치도 하지 마.
```

이 방식이 좋은 이유는 단순합니다.

- 팀원이 뭘 만들려는지 팀 전체가 보기 쉬워지고
- AI가 중간에 상상으로 채워 넣을 여지가 줄고
- 리뷰할 때도 "SPEC대로 됐나?"라는 기준이 생깁니다

스펙이 정리되면 GitHub 이슈 본문에 붙여 두는 것도 좋습니다.  
그러면 팀원끼리 설명이 줄어듭니다.

## 구현은 한 번에 몰아서 시키지 않는 편이 좋습니다

스펙을 승인한 뒤에도 한꺼번에 다 시키기보다, 단계별로 나누는 쪽이 더 안전합니다.

```text
SPEC.md 승인함. 이제 구현 시작해줘.
단, 한 번에 다 짜지 말고 다음 순서로 나눠서 진행해:
1. 데이터 구조 먼저
2. 핵심 로직
3. 화면 UI
각 단계 끝날 때마다 나한테 확인받고 다음으로 넘어가.
```

이렇게 하면 어디서부터 틀어졌는지 찾기가 훨씬 쉽습니다.  
해커톤은 시간이 짧기 때문에, "빨리 많이"보다 "짧게 끊어서 확인"이 더 효율적일 때가 많습니다.

## 작업 중에는 commit을 자주 하는 편이 훨씬 안전합니다

코드를 조금 고쳤다면 저장하듯이 commit을 남기는 습관이 좋습니다.

```bash
git add .
git status
git commit -m "feat: 로그인 화면 UI 및 유효성 검사 추가"
```

여기서 이렇게 이해하시면 편합니다.

- `git add .` : 바뀐 파일을 장바구니에 담기
- `git status` : 지금 무엇이 담겼는지 확인하기
- `git commit -m "..."` : 이 상태를 한 번 저장하기

커밋 메시지가 막힐 때는 AI를 이렇게 써도 됩니다.

```text
방금 변경한 코드 diff를 보고 커밋 메시지 한 줄로 써줘.
형식: "타입: 내용" (예: feat: 로그인 유효성 검사 추가)
```

해커톤에서는 한 번에 몰아서 저장하기보다,  
"여기까지는 정상"이라는 지점을 자주 남기는 편이 훨씬 든든합니다.

## 다 됐으면 PR로 팀장에게 보여줍니다

작업이 어느 정도 끝났다면 내 브랜치를 올립니다.

```bash
git push -u origin feature/민수-로그인
```

여기서 `origin`은 팀 리포를 가리키는 별명이고,  
`-u`는 "앞으로 이 브랜치는 여기로 올릴게요"라고 한 번 기억시켜 두는 역할입니다.

GitHub에서 `Compare & pull request` 버튼이 뜨면, 그때 PR을 만들면 됩니다.

PR 설명도 AI에게 아래처럼 맡길 수 있습니다.

```text
지금까지 이 브랜치에서 바뀐 파일들을 요약해서
PR 설명을 다음 형식으로 작성해줘:

## 변경 사항
## 테스트 방법
## 스크린샷 (있으면)
```

PR은 쉽게 말해  
**"팀장님, 제 노트를 완성본에 반영해도 되는지 봐 주세요"**  
라고 손드는 과정입니다.

## 리뷰는 AI 1차, 최종 판단은 사람

리더가 PR을 볼 때도 AI가 시간을 줄여줄 수 있습니다.

```text
이 PR의 diff를 검토해줘. 다음 기준으로만 짧게 지적해줘:
1. 명백한 버그
2. 보안 문제 (API 키 노출 등)
3. SPEC.md와 다르게 구현된 부분
칭찬이나 스타일 지적은 하지 마, 시간 없어.
```

이렇게 하면 일단 봐야 할 곳이 좁혀집니다.  
다만 마지막 승인과 병합은 사람 판단이 꼭 필요합니다.

### merge 방식은 초보 팀이면 단순한 쪽이 낫습니다

GitHub에서 보통 아래 셋 중 하나를 고릅니다.

1. `Create a merge commit`  
그대로 합치기

2. `Squash and merge`  
여러 커밋을 한 개로 뭉쳐서 합치기

3. `Rebase and merge`  
기록 순서를 정리해가며 합치기

처음 팀을 꾸릴 때는 `Create a merge commit`이 가장 단순합니다.  
기록도 남고, 중간 흐름도 보기 쉽습니다.

## 충돌은 "망했다"가 아니라 "확인해 달라"는 신호입니다

같은 파일의 같은 줄을 두 사람이 다르게 고치면 충돌이 납니다.

```bash
git pull origin main
```

이후 파일 안에서 이런 표시를 보게 됩니다.

```text
<<<<<<< HEAD
민수가 쓴 코드
=======
영희가 쓴 코드
>>>>>>> feature/민수-로그인
```

이건 고장이 아닙니다.  
컴퓨터가 "둘 중 어느 쪽을 남겨야 할지 모르겠어요" 하고 묻는 상태입니다.

AI에게 도움을 받을 때는 이렇게 묻는 편이 좋습니다.

```text
아래 git conflict를 보여줄게. 두 코드가 각각 뭘 하려는 건지
설명해주고, 두 기능을 다 살리는 합친 코드를 제안해줘.
단, 제안만 하고 파일은 고치지 마. 내가 확인하고 직접 반영할게.
```

여기서 중요한 건 하나입니다.  
AI 제안은 참고용이고, **최종 결정은 관련 팀원끼리 대화해서 정한다**는 점입니다.

충돌을 정리한 뒤에는 이렇게 마무리합니다.

```bash
git add .
git commit -m "충돌 해결: 로그인 설정과 메인화면 설정 병합"
git push
```

커밋 메시지에 `충돌 해결`이라고 적어 두면 나중에 기록을 볼 때 훨씬 편합니다.

## 충돌을 줄이는 팀 습관 네 가지

해커톤에서는 아래 네 가지만 지켜도 충돌이 꽤 줄어듭니다.

1. 같은 파일을 동시에 여러 명이 만지지 않도록 일을 나눈다.
2. 하루 2~3번 정도 `main`을 자주 받아온다.
3. commit과 push를 작은 단위로 자주 한다.
4. 단톡방에 "지금 어떤 파일 작업 중"인지 짧게 공유한다.

큰 문제는 대개 큰 덩어리로 오래 끌다가 생깁니다.  
작게 나누고 자주 맞추면 훨씬 덜 엉킵니다.

## 역할별로 보면 더 선명합니다

| 단계 | 하는 일 | 담당 |
| --- | --- | --- |
| 1 | 리포 생성, 팀원 초대, README 작성 | 리더 |
| 2 | 리포 복사(clone) | 팀원 전원 |
| 3 | 이슈로 작업 나누기 | 리더 + 팀원 |
| 4 | 내 브랜치 만들기 | 팀원 |
| 5 | AI로 스펙 확정 후 구현 | 팀원 |
| 6 | commit + push | 팀원 |
| 7 | PR 생성 | 팀원 |
| 8 | AI 1차 검토 후 사람 리뷰와 merge | 리더 |
| 9 | 충돌 나면 대화로 정리 | 관련 팀원 |
| 10 | 발표 스크립트 정리 | 리더 + 팀원 |

이 표를 보면, "리더만 하는 일"과 "팀원 모두 하는 일"이 분리됩니다.  
처음 협업할 때는 이 구분만 알아도 훨씬 덜 헷갈립니다.

## 발표 전날에는 이 묶음이 특히 유용합니다

### 명령어 치트시트

```bash
# 처음 한 번만
git clone (리포 주소)

# 작업 시작할 때
git checkout main
git pull origin main
git checkout -b feature/내이름-작업내용

# 작업 중 자주
git add .
git commit -m "무엇을 했는지 한 줄"

# 작업이 끝났을 때
git push -u origin feature/내이름-작업내용

# 충돌이 났을 때
git pull origin main
# 파일 열어서 <<<<<<< ======= >>>>>>> 표시 직접 정리
git add .
git commit -m "충돌 해결: 무엇과 무엇을 병합했는지"
git push
```

### AI 프롬프트 치트시트

#### 1. 작업 시작 전 스펙 확정

```text
너는 지금부터 절대 코드를 작성하지 마.
내가 만들려는 기능은 [기능명]이야.
아래 8가지를 나와 하나씩 대화로 확정해줘. 애매한 건 반드시 질문해.
1. 화면 구성
2. 핵심 기능
3. 데이터 구조
4. 기술 스택
5. 디자인 방향
6. 이번엔 제외할 기능
7. 완료 조건
8. 테스트 방법
다 정해지면 SPEC.md로 정리해서 보여주고,
내가 "승인"이라고 말하기 전까진 파일 수정도, 패키지 설치도 하지 마.
```

#### 2. 커밋 메시지 한 줄 만들기

```text
방금 변경한 코드 diff를 보고 커밋 메시지 한 줄로 써줘.
형식: "타입: 내용"
```

#### 3. PR 설명 정리

```text
지금까지 이 브랜치에서 바뀐 파일들을 요약해서
PR 설명을 다음 형식으로 작성해줘:
## 변경 사항
## 테스트 방법
## 스크린샷 (있으면)
```

#### 4. PR 1차 검토

```text
이 PR의 diff를 검토해줘. 다음 기준으로만 짧게 지적해줘:
1. 명백한 버그
2. 보안 문제
3. SPEC.md와 다르게 구현된 부분
칭찬이나 스타일 지적은 하지 마, 시간 없어.
```

#### 5. 충돌 해결 제안 받기

```text
아래 git conflict를 보여줄게. 두 코드가 각각 뭘 하려는 건지
설명해주고, 두 기능을 다 살리는 합친 코드를 제안해줘.
단, 제안만 하고 파일은 고치지 마. 내가 확인하고 직접 반영할게.
```

#### 6. 발표 스크립트 뽑기

```text
지금까지의 커밋 히스토리와 SPEC.md들을 보고
심사위원용 3분 발표 스크립트를 만들어줘.
구조: 문제 정의 → 해결 방법 → 데모 → 기술 스택 → 팀 소개
```

## 나눔 시간 전에 체크하면 좋은 것

<ul class="note-list">
  <li>팀원 모두가 <code>main</code>과 개인 브랜치의 차이를 말로 설명할 수 있는가</li>
  <li>작업 전에 <code>git pull origin main</code>을 먼저 하는지 습관이 잡혀 있는가</li>
  <li>AI에게 구현 전에 스펙부터 확정시키는 순서를 팀 전체가 공유했는가</li>
  <li>PR은 "제 코드 봐 주세요"라는 요청이라는 점을 모두 이해하고 있는가</li>
  <li>충돌이 나도 당황하지 말고, 관련 팀원끼리 먼저 대화하기로 약속했는가</li>
</ul>

## 딱 두 문장만 기억해도 됩니다

> 진짜 완성본인 `main`은 함부로 바로 고치지 않고, 각자 자기 브랜치에서 먼저 작업한 뒤 PR로 보여준다.
>
> AI에게는 "알아서 다 해줘"라고 하지 않고, 반드시 **스펙 확정 → 승인 → 단계별 실행** 순서를 지킨다.

이 두 가지만 팀 전체가 시작 전에 맞추고 들어가면,  
깃허브 협업은 생각보다 훨씬 덜 무섭습니다.

## 용어집

### Git
파일 변경 기록을 남기고, 여러 사람이 같은 프로젝트를 함께 관리하게 도와주는 도구입니다.

### GitHub
Git으로 관리하는 프로젝트를 인터넷에서 함께 보고, 올리고, 검토하는 공간입니다.

### Repository(리포지토리, 리포)
프로젝트 파일과 기록이 들어 있는 작업 상자입니다.

### README.md
이 프로젝트가 무엇인지, 어떻게 실행하는지 적어 두는 첫 안내문입니다.

### main 브랜치
팀의 최종 완성본이 모이는 기본 줄기입니다.

### Branch(브랜치)
완성본을 건드리지 않고 따로 작업하기 위한 개인 작업 줄기입니다.

### Issue
해야 할 일을 잘게 나눠 적어 두는 작업 카드입니다.

### Clone
팀 리포를 내 컴퓨터로 그대로 복사해 오는 일입니다.

### Checkout
원하는 브랜치로 이동하는 명령입니다.

### Pull
원격 저장소의 최신 내용을 내 컴퓨터로 받아오는 일입니다.

### Commit
지금 상태를 한 번 저장하면서 설명 한 줄을 남기는 일입니다.

### Push
내 컴퓨터에서 작업한 내용을 GitHub 쪽으로 올리는 일입니다.

### Pull Request(PR)
내 브랜치 내용을 완성본에 반영해도 되는지 검토해 달라고 요청하는 절차입니다.

### Code Review
다른 사람이 올린 변경 내용을 함께 확인하는 과정입니다.

### Merge
검토가 끝난 변경 내용을 최종 완성본에 합치는 일입니다.

### Conflict(충돌)
같은 부분을 두 사람이 다르게 고쳐서, 무엇을 남길지 직접 정해야 하는 상태입니다.

### Diff
이전 코드와 지금 코드가 어디서 어떻게 달라졌는지 보여주는 비교 내용입니다.

### SPEC.md
기능을 만들기 전에 화면, 기능, 제외 범위, 완료 조건 같은 약속을 먼저 적어 둔 문서입니다.
