# 계획부터 배포·시연까지, AI 개발에 바로 복사해 쓰는 프롬프트 모음

AI로 앱을 만들 때 가장 아쉬운 순간은 코드가 한 줄도 안 나와서가 아닙니다. 코드는 많이 생겼는데 무엇을 만들고 있는지, 어디까지 확인했는지, 다음에 무엇을 해야 하는지 모르게 되는 순간입니다.

이 글의 프롬프트는 그 문제를 줄이기 위한 순서표입니다.

- 먼저 프로젝트의 목적과 범위를 정합니다.
- 그다음 요구사항과 기술 선택을 문서로 남깁니다.
- 가상의 사용자에게 실제로 써 보게 합니다.
- 작은 기능부터 테스트와 함께 구현합니다.
- 마지막에 배포·사용법·소개 영상까지 정리합니다.

## 먼저 결론

- <strong>계획을 설명하고 승인을 받은 뒤에 코드를 작성합니다.</strong> AI가 빠르게 코드를 쓰는 것보다, 잘못된 방향으로 멀리 가지 않는 것이 먼저입니다.
- <strong>PRD·TRD·페르소나·시나리오·와이어프레임은 서로 이어져야 합니다.</strong> 따로 만든 문서가 아니라 같은 프로젝트를 다른 각도에서 보는 지도입니다.
- <strong>프롬프트는 한 번에 길게 던지기보다 단계별로 나눠 사용합니다.</strong> 각 단계의 결과물과 확인 기준을 남겨야 다음 단계에서 덜 헤맵니다.
- <strong>“완료”와 “계획”을 구분합니다.</strong> 문서에 적힌 기능, 자동 테스트 통과, 실제 사람의 사용·청취·현장 확인은 서로 다른 증거입니다.
- <strong>마지막 결과물은 코드만이 아닙니다.</strong> 사용자 가이드, 운영자 가이드, 문제 해결 기록, 소개 영상과 발표 자료까지 있어야 다른 사람이 이어서 쓸 수 있습니다.

## 이 글의 사용법

아래 프롬프트는 그대로 복사해도 되지만, 다음 네 곳은 먼저 바꾸는 편이 좋습니다.

1. `[프로젝트 이름]`
2. `[만들고 싶은 것]`
3. `[사용자와 사용 장소]`
4. `[현재 저장소나 작업 폴더]`

한 프롬프트를 실행한 뒤에는 결과를 읽어 보세요. 결과가 이해되지 않으면 다음 프롬프트로 넘어가지 말고, “어려운 말을 풀어서 다시 설명해 달라”고 요청하면 됩니다.

> [!tip] 안전하게 사용하기
> 비밀번호, API 키, 개인 연락처, 회원 명단, 실제 고객 자료는 프롬프트에 넣지 마세요. 테스트에는 가짜 이름과 가짜 데이터를 사용하고, 공개 글에는 내부 경로·세부 로그·장치 식별 정보도 남기지 않는 것이 안전합니다.

## 1. 처음에는 코딩하지 말고, 프로젝트 지도를 만든다

처음부터 “코드 작성해 줘”라고 하면 AI는 눈앞의 기능부터 만들기 쉽습니다. 먼저 전체 목적과 순서를 문서로 만들게 하는 것이 좋습니다.

### 바로 복사하는 프롬프트

```text
당신은 [프로젝트 이름]의 기획·기술 설계를 돕는 개발 파트너입니다.

지금은 코드를 작성하지 마세요. 먼저 현재 작업 자료와 저장소 구조를 읽고,
제가 이해할 수 있는 말로 프로젝트 전체 계획을 세워 주세요.

프로젝트 목표:
- [무엇을 만들고 싶은가]
- 주요 사용자: [누가 쓰는가]
- 사용 장소와 상황: [어디서, 언제 쓰는가]
- 꼭 지켜야 할 제약: [예: 오프라인 사용, 개인정보 미수집, 특정 운영체제 지원]

Project.md 파일에 다음 내용을 정리해 주세요.
1. 해결하려는 문제
2. 사용자와 사용 장면
3. 이번 범위에 넣을 것과 넣지 않을 것
4. 필요한 문서 목록과 작성 순서
5. 구현을 나눌 단계
6. 각 단계의 완료 조건
7. 위험 요소와 아직 모르는 것
8. 제가 중간에 승인해야 하는 결정
9. 테스트·문서화·배포·시연 영상까지 포함한 전체 흐름

파일을 수정하거나 새 코드를 만들기 전에,
작성한 계획을 먼저 요약해서 설명하고 제 승인을 기다리세요.
승인 전에는 구현을 시작하지 마세요.
```

### 이 프롬프트의 핵심

마지막 두 문장이 중요합니다. “계획을 먼저 설명하고 승인 후 구현”이라는 문장을 매번 넣으면 AI가 곧바로 코드를 쏟아내는 일을 줄일 수 있습니다. 이때 Project.md는 프로젝트의 목차이자 나중에 강의 자료가 되는 기록입니다.

## 2. 구현 전에 이론과 개념을 조사한다

기술 이름을 많이 아는 것보다, 왜 그렇게 설계하는지 설명할 수 있는 것이 중요합니다. 조사한 이론을 모두 적용할 필요는 없습니다. 적용할 것과 보류할 것을 나눠야 합니다.

### 바로 복사하는 프롬프트

```text
[프로젝트 이름]을 구현하기 전에 완성도와 코드 품질을 높이는 데 도움이 되는
이론·개념·설계 원칙을 조사해 주세요.

다음 기준을 지키세요.
- 가능하면 공식 문서, 원 논문, 신뢰할 수 있는 기술 자료를 우선하세요.
- 자료의 제목, 링크, 확인 날짜, 핵심 주장, 우리 프로젝트에 적용할 부분을 기록하세요.
- 이론을 멋있어 보이게 붙이지 말고, 실제 문제와 연결될 때만 제안하세요.
- 적용하지 않는 이론도 이유를 짧게 남기세요.
- 아직 확인하지 못한 내용은 사실처럼 쓰지 마세요.

다음 후보도 검토하되, 억지로 적용하지 마세요.
- 협업에서 각 사람의 기여를 나누어 보는 관점
- 선택지를 언제까지 탐색하고 멈출지 정하는 관점
- 좋은 행동을 강화하고 문제 행동에는 책임을 묻는 운영 관점
- 상태 관리, 재현성, 사용성, 오류 복구, 테스트 주도 개발

결과를 이론적 배경.md에 정리하고,
각 이론마다 다음 표를 포함하세요.
[개념] [쉽게 설명하면] [프로젝트의 어느 문제와 연결되는가]
[적용 방법] [주의할 점] [현재 적용 여부]

문서 작성이 끝나면 적용 우선순위를 설명하고 제 승인을 기다리세요.
```

### 이 프롬프트의 핵심

어려운 이론 이름만 나열하면 개발에는 도움이 되지 않습니다. “이 개념이 우리 프로젝트의 어느 문제를 해결하는가?”까지 연결해야 합니다. 예를 들어 협업 기여를 나누어 보는 관점은 팀 작업의 역할을 정리할 때 도움이 되지만, 혼자 만드는 작은 앱에 억지로 점수표를 붙일 필요는 없습니다.

## 3. PRD와 TRD를 차례대로 만든다

PRD는 “무엇을, 누구를 위해, 왜 만드는가”를 적는 문서입니다. TRD는 “그것을 어떤 기술과 구조로 만들 것인가”를 적는 문서입니다. 두 문서를 한꺼번에 만들면 사용자 요구와 기술 욕심이 섞이기 쉽습니다.

### PRD 작성 프롬프트

```text
이제 [프로젝트 이름]의 PRD를 작성해 주세요.

아직 코드를 작성하지 말고, 제품 관점에서 다음 내용을 정리하세요.
1. 제품 한 문장 소개
2. 해결하려는 사용자 문제
3. 주요 사용자와 사용 상황
4. 핵심 사용자 여정
5. 꼭 필요한 기능과 나중에 넣을 기능
6. 사용자가 입력하고 결과로 받는 것
7. 오류가 났을 때 사용자가 알아야 할 안내
8. 개인정보·저작권·안전상 지켜야 할 원칙
9. 성공을 판단할 수 있는 수치 또는 관찰 기준
10. 기능별 수용 기준과 미완료 조건

각 요구사항에 PRD-001, PRD-002처럼 고유한 ID를 붙이세요.
문서에 없는 기능을 임의로 추가하지 말고,
모호한 요구사항은 질문 목록으로 분리하세요.
결과를 PRD.md로 저장한 뒤, 핵심 내용을 쉬운 말로 설명하고 승인을 기다리세요.
```

### TRD 작성 프롬프트

```text
승인된 PRD.md를 기준으로 [프로젝트 이름]의 TRD를 작성해 주세요.

TRD에는 다음 내용을 포함하세요.
1. 전체 시스템 구조
2. 화면과 주요 모듈의 책임
3. 데이터 구조와 저장·복원 방식
4. 상태 변화와 이벤트 흐름
5. 시간·성능·접근성 기준
6. 오류 처리와 복구 방법
7. 테스트 전략과 테스트 환경
8. 웹·데스크톱·모바일 등 지원 환경
9. 빌드·패키징·배포 방식
10. 보안·개인정보·외부 서비스 사용 원칙
11. PRD 요구사항과 기술 설계의 연결표
12. 아직 검증하지 못한 가정

각 기술 결정에는 “왜 이 방법을 선택했는가”를 한두 문장으로 적으세요.
PRD에 없는 요구사항을 기술 편의를 이유로 추가하지 마세요.
TRD.md로 저장하고, 구현 순서와 가장 먼저 실험해야 할 위험 요소를 설명하세요.
코드는 작성하지 말고 제 승인을 기다리세요.
```

### 두 문서가 잘 연결됐는지 확인하는 질문

- PRD의 모든 핵심 요구사항이 TRD의 어느 구조와 연결되어 있는가?
- TRD에만 있고 PRD에는 없는 기능이 생기지 않았는가?
- 아직 계획인 내용을 이미 작동하는 것처럼 쓰지 않았는가?
- “지원한다”는 말에 운영체제, 오프라인, 실제 장비 같은 조건이 빠지지 않았는가?

## 4. 가상의 참가자와 사용자 시나리오를 만든다

기능 목록만 보고 개발하면 개발자에게 편한 앱이 되기 쉽습니다. 가상의 참가자를 먼저 만들면 “처음 보는 사람이 이 화면에서 무엇을 할까?”를 생각하게 됩니다.

### 바로 복사하는 프롬프트

```text
승인된 PRD.md와 TRD.md를 기준으로 가상의 사용자 페르소나를 만들어 주세요.

서로 다른 상황을 대표하는 3명의 페르소나를 제안하세요.
예를 들어 처음 사용하는 사람, 결과를 다듬는 사람, 현장에서 운영하는 사람처럼
역할과 어려움이 겹치지 않게 구성하세요.

각 페르소나에는 다음을 포함하세요.
- 이름 대신 안전한 별칭
- 역할과 목표
- 디지털 도구 사용 경험
- 가장 걱정하는 지점
- 성공했다고 느끼는 순간
- 도움을 요청할 가능성이 높은 순간

그다음 각 페르소나를 중심으로 사용자 시나리오를 작성하세요.
시나리오는 시작 조건 → 행동 → 화면 반응 → 예외 상황 → 완료 조건 순서로 쓰고,
실제 사람이 말할 법한 문장과 행동을 사용하세요.

결과를 다음 마크다운 파일로 저장하세요.
- personas.md
- user-scenarios.md

각 시나리오에 연결되는 PRD ID와 테스트 아이디어도 붙이세요.
문서가 완성되면 가장 위험한 시나리오 3개를 골라 이유를 설명하고 승인을 기다리세요.
```

## 5. 시나리오에서 와이어프레임을 만든다

와이어프레임은 예쁜 디자인이 아니라 화면의 순서와 버튼의 역할을 확인하는 도면입니다. 처음에는 ASCII 그림이나 표만으로도 충분합니다.

### 바로 복사하는 프롬프트

```text
승인된 user-scenarios.md의 흐름을 기준으로 와이어프레임을 만들어 주세요.

화려한 색상이나 장식보다 다음을 우선하세요.
- 사용자가 어디에서 시작하는가
- 다음에 무엇을 눌러야 하는가
- 현재 상태를 어떻게 알 수 있는가
- 실수했을 때 되돌리거나 다시 시도할 수 있는가
- 처음 사용하는 사람이 읽을 안내가 충분한가
- 키보드·모바일·큰 글자 환경에서도 핵심 행동이 가능한가

각 주요 화면을 다음 형식으로 작성하세요.
1. 화면 이름과 목적
2. 진입 조건
3. ASCII 또는 표 형태의 배치
4. 버튼·입력·상태 표시 목록
5. 정상 흐름과 오류 흐름
6. 연결된 사용자 시나리오와 PRD ID
7. 접근성·가독성 확인 항목

결과를 wireframes.md로 저장하세요.
실제 디자인 코드를 만들기 전에 화면 순서를 쉬운 말로 설명하고,
제가 승인하면 그다음에만 구현 계획을 갱신하세요.
```

## 6. 작은 기능 하나를 테스트 주도로 구현한다

테스트 주도 개발은 모든 코드를 무조건 테스트부터 쓰라는 뜻으로만 이해할 필요는 없습니다. 먼저 “무엇이 성공인가”를 테스트로 적고, 가장 작은 코드로 통과시킨 뒤, 읽기 좋게 다듬는 흐름으로 사용하면 좋습니다.

### 바로 복사하는 프롬프트

```text
승인된 PRD.md, TRD.md, user-scenarios.md, wireframes.md를 기준으로
이번 단계의 가장 작은 기능 하나만 구현해 주세요.

구현 전에 다음을 먼저 보고하세요.
- 이번 단계의 목표
- 이번 단계에 포함하지 않을 것
- 관련 요구사항 ID
- 성공 조건
- 실패할 가능성이 높은 부분
- 필요한 테스트 목록

그다음 순서대로 진행하세요.
1. 실패하는 테스트 또는 검증 절차를 먼저 작성한다.
2. 테스트가 확인하는 행동을 설명한다.
3. 테스트를 통과하는 최소 코드를 작성한다.
4. 테스트를 실행하고 결과를 기록한다.
5. 중복과 읽기 어려운 부분을 정리하되 동작을 바꾸지 않는다.
6. 문서와 개발 일지를 갱신한다.

현재 사용할 수 있는 스킬과 프로젝트 규칙을 먼저 확인하고,
도움이 되는 스킬이 있으면 사용 이유와 결과를 기록하세요.
비밀번호·API 키·개인정보를 테스트 자료로 사용하지 마세요.
큰 구조 변경이나 다음 기능 구현은 제 승인 후에 진행하세요.
```

### 단계가 끝날 때 남길 것

- 어떤 테스트를 먼저 만들었는가
- 실제로 통과했는가
- 화면에서 직접 확인했는가
- 사람의 사용·청취·현장 장비 확인이 필요한가
- 다음 단계로 넘긴 위험은 무엇인가

자동 테스트 통과만으로 실제 공연이나 실제 사용까지 확인했다고 쓰지 않는 것이 중요합니다.

## 7. 개발 단계마다 일지를 누적한다

개발 일지는 실패를 숨기는 반성문이 아닙니다. 다음 개발자가 같은 곳에서 다시 넘어지지 않게 하는 지도입니다. 나중에는 강의나 블로그의 가장 좋은 재료가 됩니다.

### 바로 복사하는 프롬프트

```text
방금 완료한 [단계 이름]의 개발 일지를 작성해 주세요.

다음 항목을 빠짐없이 기록하세요.
- 날짜와 단계 이름
- 이번 단계의 목표
- 실제로 바꾼 내용
- 실행한 테스트와 결과
- 화면·파일·장비에서 직접 확인한 것
- 발생한 문제와 원인
- 시도했지만 버린 방법과 이유
- 새로 내린 설계 결정
- 아직 확인하지 못한 것
- 다음 작업
- 관련 PRD·TRD·시나리오·문서 ID

추측과 확인된 사실을 구분해서 쓰고,
민감한 경로·토큰·개인정보·장치 식별 정보는 기록하지 마세요.
기존 일지를 덮어쓰지 말고 날짜별 기록을 누적하세요.
```

## 8. 사용자·운영자·문제 해결 문서를 함께 만든다

사용자 가이드는 “무엇을 누르는가”를, 운영자 가이드는 “공연이나 업무를 어떻게 준비하는가”를, 문제 해결 문서는 “막혔을 때 어디부터 보는가”를 설명합니다.

### 바로 복사하는 프롬프트

```text
현재까지 구현되고 실제로 확인된 기능만 기준으로 다음 문서를 갱신해 주세요.

1. UserGuide.md
   - 처음 설치하거나 접속하는 방법
   - 첫 작업을 끝내는 순서
   - 저장·내보내기·다시 열기 방법
   - 자주 하는 실수와 쉬운 해결법

2. ManagerGuide.md
   - 공연·행사 전 준비 순서
   - 참가자 자료를 받는 방법
   - 순서와 상태를 확인하는 방법
   - 시작·중지·재시작·비상 상황 절차
   - 현장 전에 반드시 사람이 확인할 항목

3. TroubleShooting.md
   - 증상
   - 확인할 순서
   - 원인
   - 해결 방법
   - 해결되지 않을 때 남길 정보

문서마다 “확인된 기능”, “계획 중인 기능”, “아직 검증하지 못한 환경”을 구분하세요.
작동하지 않는 기능을 작동한다고 쓰지 말고, 사용자가 이해하지 못할 전문용어는 풀어서 설명하세요.
문서 변경 내용은 개발 일지에도 기록하고, 원본 자료와 민감정보는 보존·보호하세요.
```

## 9. 중복을 줄이고 개발 순서를 짧게 만든다

계획이 길어질수록 같은 검사를 여러 문서에서 반복할 수 있습니다. 그렇다고 중요한 검증까지 생략하면 안 됩니다. 중복 문장은 줄이고, 고유한 확인 절차는 남기는 방식이 좋습니다.

### 바로 복사하는 프롬프트

```text
현재 Project.md, PRD.md, TRD.md, personas.md, user-scenarios.md,
wireframes.md, 테스트 계획, 개발 일지를 서로 대조해 주세요.

다음 표를 만들어 주세요.
[단계] [반복되는 작업] [한 곳으로 합칠 문서]
[그대로 유지할 검증] [통합하면 안 되는 이유]
[단축 가능한 단계] [단축했을 때 잃는 증거]

다음 원칙을 지키세요.
- 사용자 요구사항과 안전·보안 검증은 생략하지 않는다.
- 한 번 확인한 사실을 여러 문서에 장황하게 복사하지 않는다.
- 자동 테스트, 화면 조작, 실제 장비·사람 확인을 하나로 합치지 않는다.
- 문서 순서를 줄이더라도 각 단계의 완료 조건은 남긴다.
- 계획을 줄이는 것과 범위를 몰래 줄이는 것을 구분한다.

수정 전에 제안만 먼저 설명하고 승인을 기다리세요.
```

## 10. Mac에서 Windows 작업으로 옮길 때 확인한다

운영체제를 바꾸면 “코드가 같으니 바로 되겠지”라고 생각하기 쉽습니다. 경로, 파일 대화상자, 권한, 글꼴, 오디오 장치, 패키징 방식이 달라질 수 있으므로 먼저 호환성 표를 만드는 편이 안전합니다.

### 바로 복사하는 프롬프트

```text
현재 [프로젝트 이름]을 Mac에서 Windows 개발·공연 운영 환경으로 옮기려 합니다.
바로 코드를 바꾸지 말고, 현재 프로젝트와 문서를 먼저 점검해 주세요.

다음 항목을 비교표로 작성하세요.
- 개발 도구와 버전
- 파일 경로와 구분자
- 환경변수와 비밀값 처리
- 빌드·패키징 방식
- Windows x64와 ARM64 지원 여부
- 오디오 장치와 외부 음악 준비
- 화면 크기·글꼴·권한
- 파일 선택·저장·실행 권한
- 오프라인 동작
- 설치·업데이트·삭제·rollback
- 공연 전 운영자 확인 절차

Mac에서 이미 확인된 것과 Windows에서 새로 확인해야 할 것을 분리하세요.
Windows 실기기에서 확인하지 않은 항목은 PASS라고 쓰지 마세요.
기존 Mac 작업을 깨뜨리지 않는 이동 순서와 최소 실험을 제안하고,
계획 설명 후 제 승인을 기다리세요.
```

## 11. 서비스가 안정되면 소개 영상과 사용법을 만든다

좋은 서비스도 다른 사람이 실제로 어떻게 쓰는지 보지 못하면 전달하기 어렵습니다. 소개 영상은 장식이 아니라 사용 흐름을 보여 주는 설명서입니다.

제공된 공개 프로젝트 중에는 실제 앱 화면을 조작해 데모 영상을 만드는 `demo-video-skill`과, 웹에서 클릭 과정을 기록해 단계별 가이드를 만드는 `ClickGuide Local`이 있습니다. 사용하기 전에는 각 저장소의 최신 README와 라이선스를 확인하고, 현재 환경에 맞는지 먼저 판단해야 합니다.

- <a href="https://github.com/Kminer2053/demo-video-skill" target="_blank" rel="noopener">demo-video-skill 원문 저장소 · 블로그 밖 · 새 창</a>
- <a href="https://github.com/koul777/clickguide-local-private" target="_blank" rel="noopener">ClickGuide Local 원문 저장소 · 블로그 밖 · 새 창</a>

### 바로 복사하는 프롬프트

```text
[프로젝트 이름]이 안정적으로 동작하는 범위 안에서
서비스 소개 영상과 사용자 사용법을 만들 계획을 세워 주세요.

먼저 다음을 구분하세요.
- 실제로 동작하는 화면
- 화면만 준비된 기능
- 아직 검증하지 못한 기능
- 영상에 보여 주면 안 되는 개인정보·토큰·내부 정보

그다음 계획에 다음 결과물을 포함하세요.
1. 60~90초 서비스 소개 영상 대본
2. 주요 기능별 실제 화면 시연 순서
3. 장면마다 들어갈 짧은 자막
4. 사용자 가이드와 운영자 가이드
5. 클릭 과정을 기록한 단계별 안내
6. HTML·PDF 발표 자료
7. 촬영·렌더링·검수·수정 순서

사용 가능한 데모 영상·클릭 가이드 스킬이 있으면 먼저 목록과 사용 조건을 확인하세요.
원본 프로젝트 파일은 보존하고, 복사본 또는 결과물 폴더에서 작업하세요.
민감한 화면은 가짜 데이터로 바꾸거나 영상에서 제외하세요.

대본 → 짧은 시범 장면 → 제 승인 → 전체 장면 → 자막·음향 검수 → 최종 영상 순서로 진행하고,
영상과 문서가 실제 제품의 현재 상태를 과장하지 않도록 확인 기준을 함께 적어 주세요.
지금은 계획만 제시하고 제 승인 후에 제작을 시작하세요.
```

### ClickGuide를 사용할 때의 주의

클릭 기록에는 페이지 제목, URL, 클릭 대상 글자, 화면 캡처가 들어갈 수 있습니다. 설명서에 넣기 전에 비밀번호, 고객 정보, 내부 주소가 보이지 않는지 확인하세요. Chrome 안의 웹 화면과 설치형 Windows 프로그램 화면은 기록 범위가 다를 수 있으므로, 가능한 범위를 과장하지 않는 것도 중요합니다.

## 12. 초보자 세미나 자료를 만든다

개발 과정을 나누는 세미나는 완성품 자랑보다 “왜 이런 순서로 했는가”를 보여 줄 때 도움이 됩니다. 성공한 장면만 보여 주면 초보자는 막혔을 때 무엇을 해야 할지 알기 어렵습니다.

### 바로 복사하는 프롬프트

```text
[프로젝트 이름]을 처음 기획한 순간부터 배포·시연까지의 과정을
초보 개발자와 4060 회원님들이 천천히 이해할 수 있는 세미나로 구성해 주세요.

다음 결과물을 모두 마크다운 파일로 먼저 작성하세요.
- seminar-plan.md: 전체 시간표, 대상, 학습 목표, 준비물
- seminar-script.md: 강사가 실제로 말할 설명과 비유
- seminar-slides.md: 슬라이드별 제목·핵심 문장·시연 화면·발표자 메모
- seminar-demo-script.md: 시연 순서와 예상 문제·복구 방법
- seminar-prompts.md: 각 개발 단계에서 바로 복사할 프롬프트 모음

내용은 다음 순서를 따르세요.
1. 아이디어와 문제 정의
2. Project.md와 이론적 배경
3. PRD·TRD
4. 페르소나·사용자 시나리오·와이어프레임
5. 테스트 주도 방식의 작은 구현
6. 시행착오와 문제 해결
7. 사용자·운영자 문서
8. Mac·Windows와 배포 준비
9. 소개 영상과 사용법 제작
10. 검증 결과와 아직 남은 과제

각 단계마다 “무엇을 했는가, 왜 했는가, 무엇을 확인했는가, 바로 써볼 프롬프트”를 넣으세요.
성공한 일과 계획인 일을 색상이나 표현으로 구분할 수 있게 표시하고,
개인정보·내부 경로·비밀값·보안상 공개하면 안 되는 세부 내용은 제외하세요.
영상과 발표 자료는 문서 초안을 먼저 만들고, 제가 검토한 뒤 제작하도록 순서를 제안하세요.
```

## 13. 마지막 검수와 배포를 맡긴다

배포 직전에는 새로운 기능을 더하기보다, 지금 있는 결과물을 정직하게 확인하는 일이 중요합니다.

### 바로 복사하는 프롬프트

```text
[프로젝트 이름]의 배포 전 최종 검수 계획을 세워 주세요.
아직 코드를 고치거나 배포하지 말고, 다음 표를 먼저 작성하세요.

[검수 항목] [확인 방법] [통과 기준] [실패 시 조치] [증거 위치]

반드시 포함할 항목:
- 요구사항과 구현의 연결
- 자동 테스트와 회귀 테스트
- 빈 상태·잘못된 입력·중복 실행·재시작
- 데이터 저장·복원과 다른 환경 재현
- 접근성·큰 글자·대비·모바일 화면
- 개인정보·비밀값·내부 정보 공개 여부
- 라이선스와 외부 자료 출처
- Mac·Windows·오프라인·현장 장비 검증 범위
```

## 문서가 서로 이어지는 전체 흐름

```text
아이디어
  ↓
Project.md ───────→ 전체 계획과 승인 지점
  ↓
이론적 배경 ─────→ 설계 판단의 근거
  ↓
PRD ─────────────→ 사용자에게 필요한 것
  ↓
TRD ─────────────→ 기술로 구현하는 방법
  ↓
페르소나
  ↓
사용자 시나리오 ─→ 실제 사용 흐름
  ↓
와이어프레임 ────→ 화면 순서와 상태
  ↓
테스트·작은 구현 ─→ 확인 가능한 기능
  ↓
개발 일지·가이드 ─→ 다시 쓰고 운영하는 기록
  ↓
배포 검수 ───────→ 어디까지 확인했는지 구분
  ↓
소개 영상·발표 자료 → 다른 사람에게 전달
```

이 순서가 반드시 모든 프로젝트에 똑같이 필요한 것은 아닙니다. 작은 도구라면 문서를 짧게 합칠 수 있고, 이미 검증된 부분은 다시 반복하지 않아도 됩니다. 다만 <strong>무엇을 생략했는지와 왜 생략했는지는 기록</strong>해 두는 것이 좋습니다.

## 다음 개발에서 바로 쓰는 짧은 공통 문장

긴 프롬프트가 부담스러울 때는 아래 문장을 각 요청의 앞이나 뒤에 붙여도 좋습니다.

```text
바로 구현하지 말고 현재 상태를 먼저 확인하세요.
확인한 사실과 추측을 구분하세요.
이번 단계의 범위와 완료 조건을 먼저 설명하세요.
사용 가능한 프로젝트 규칙과 스킬을 확인하고 필요한 것만 사용하세요.
민감정보와 비밀값은 읽거나 출력하거나 저장하지 마세요.
테스트 결과와 아직 검증하지 못한 항목을 기록하세요.
계획을 설명한 뒤 제 승인을 기다리세요.
```

```text
이번 작업을 끝낸 뒤에는 변경된 파일, 실행한 검증,
실패한 검증, 남은 위험, 다음 작업을 짧게 보고하세요.
문서와 개발 일지를 함께 갱신하되 기존 기록을 덮어쓰지 마세요.
```

## 남겨둘 판단

AI 개발에서 좋은 프롬프트는 AI를 더 세게 몰아붙이는 문장이 아닙니다. 사람이 확인해야 할 순간을 남겨 두고, 결과물을 문서와 테스트로 이어 주는 약속에 가깝습니다.

특히 다음 네 가지는 프로젝트가 커져도 계속 쓸 만합니다.

1. 계획을 먼저 설명하고 승인받기
2. 요구사항·기술·사용자 흐름을 문서로 연결하기
3. 작은 기능을 테스트와 함께 만들기
4. 실제로 확인한 것과 아직 모르는 것을 구분하기

이 네 가지만 지켜도 AI가 만든 코드가 어디서 왔는지, 무엇을 믿어도 되는지, 다음에 무엇을 해야 하는지 훨씬 선명해집니다.
