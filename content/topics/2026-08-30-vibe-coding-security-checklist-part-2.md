## 먼저 결론

- 로그인 기능은 <strong>화면</strong>보다 <strong>서버 쪽 검사</strong>가 더 중요합니다.
- 비밀번호는 그냥 저장하면 안 되고, 되돌릴 수 없게 해시로 저장해야 합니다.
- 개인정보를 받는 순간부터는 기술 문제만이 아니라 <strong>운영과 문서의 책임</strong>도 함께 시작됩니다.

## 왜 2부가 특히 중요한가

1부가 "열쇠와 금고를 아무 데나 두지 말자"였다면,  
2부는 "문지기와 출입 규칙을 제대로 세우자"에 가깝습니다.

여기서 자주 생기는 착각은 이렇습니다.

- 회원가입이 되니까 보안도 된 줄 아는 경우
- 관리자 버튼을 숨겼으니 일반 사용자는 못 쓸 거라 생각하는 경우
- HTTPS만 켜면 개인정보 문제도 다 끝난 줄 아는 경우

하지만 실제 사고는 보통 더 단순합니다.

- 로그인은 됐는데 남의 정보도 열리는 경우
- 주소 숫자 하나 바꿨더니 다른 주문서가 보이는 경우
- 비밀번호를 평문으로 저장해 두어 유출 피해가 커지는 경우
- 개인정보처리방침을 빼먹어 법적 책임까지 함께 생기는 경우

그래서 이번 글은 "설정 하나 더 붙이기"보다  
<strong>내 서비스가 누구에게 무엇을 어디까지 허용하는지 다시 점검하는 글</strong>로 보시면 좋습니다.

## 머릿속에 먼저 넣어둘 두 가지 비유

### 인증은 신분 확인이다

인증은 "이 사람이 누구인가"를 확인하는 절차입니다.  
회사 건물 1층 경비실에서 신분증을 확인하는 장면을 떠올리면 쉽습니다.

즉,

- 로그인 성공
- 본인 확인 완료

까지가 인증입니다.

### 인가는 출입 범위 제한이다

인가는 "들어온 뒤 어디까지 허용할 것인가"를 정하는 절차입니다.

같은 회사 직원이어도

- 어떤 사람은 5층까지만
- 어떤 사람은 임원층까지

올라갈 수 있듯이, 서비스에서도 사용자마다 볼 수 있는 데이터와 할 수 있는 기능이 달라야 합니다.

이 둘을 구분해 두면 이번 글 절반은 이미 이해한 셈입니다.

## 인증·인가 체크리스트 3가지

### 9. 서버에서 권한 검사까지 하고 있는가

여기서 중요한 건 "로그인 화면이 있다"가 아닙니다.  
<strong>서버가 매 요청마다 이 사용자가 정말 그 데이터의 주인인지 확인하느냐</strong>입니다.

AI에게 "로그인 기능 만들어 줘"라고 하면 그럴듯한 회원가입 화면과 로그인 화면은 금방 나옵니다.  
문제는 그다음입니다.

인가 처리를 제대로 안 하면,

- 로그인만 한 일반 사용자가
- 다른 사람의 정보나
- 관리자용 데이터에

접근할 수 있는 상황이 생길 수 있습니다.

### 어떻게 확인하나

1. 권한이 없는 일반 계정을 하나 따로 만든다.
2. 관리자 화면, 관리자 API, 다른 사람 데이터 주소에 직접 접근해 본다.
3. 조회뿐 아니라 수정, 삭제 요청도 같은 기준으로 막히는지 본다.

### 여기서 기억할 말

<strong>로그인 성공과 권한 검사는 다른 일이다.</strong>

### 10. 주소 숫자만 바꿔도 남의 페이지가 열리지는 않는가

이건 회원별 주문내역, 상담 기록, 문서 보기 화면에서 자주 나오는 문제입니다.

예를 들어 URL이 이런 식이라고 해 보겠습니다.

`/orders/1024`

여기서 누군가 숫자를 `1025`로 바꿔서 엔터를 쳤을 때,

- "권한이 없습니다"
- "주문 정보가 존재하지 않습니다"

처럼 막혀야 정상입니다.

그런데 다른 사람 주문이 그대로 열리면, 그건 거의 바로 사고라고 봐야 합니다.

### 어떻게 확인하나

1. 내 계정으로 로그인한다.
2. 내 문서나 주문 주소의 마지막 숫자나 ID를 바꿔 본다.
3. 다른 사람 자료가 열리지 않고 거절되는지 확인한다.

### 여기서 기억할 말

<strong>내 주소와 남의 주소를 서버가 구분해 주지 않으면, 로그인은 껍데기일 뿐이다.</strong>

### 11. 숨김 처리를 프론트엔드만 믿고 있지 않은가

관리자 버튼이 화면에서 안 보인다고 안심하면 안 됩니다.

브라우저 개발자 도구를 열어 보면

- 어떤 주소로 요청하는지
- 어떤 API가 호출되는지

생각보다 쉽게 보입니다.

그래서 프론트엔드에서 버튼만 숨기고, 서버는 그냥 요청을 받아 주는 구조라면  
일반 사용자도 그 주소를 직접 호출해 볼 수 있습니다.

### 어떻게 확인하나

- 관리자 기능 URL이나 API가 일반 사용자 요청에서 `403`, `401`처럼 거절되는지 본다.
- "화면에서 안 보임"이 아니라 "서버가 거절함"이 확인돼야 통과다.

### 여기서 기억할 말

<strong>화면에서 안 보인다고 해서, 못 하는 것은 아니다.</strong>

## 12. 로그인 관련 체크리스트 5종 세트

이 부분은 한 항목처럼 보이지만 실제로는 다섯 가지를 한꺼번에 봐야 합니다.

### 1. 로그인 시도 횟수를 제한했는가

시도 횟수 제한이 없으면 프로그램이 비밀번호를 수십만 개 넣어 보는 방식의 공격을 버티기 어렵습니다.

우리가 여러 서비스에서 보는

- 5회 이상 실패 시 잠시 잠금
- 일정 시간 후 다시 시도

같은 규칙이 그래서 필요합니다.

### 2. 토큰에 만료 시간을 두었는가

토큰은 일종의 출입증입니다.  
만료가 없으면 한 번 발급된 출입증이 너무 오래 살아남습니다.

그러면

- 탈퇴 후에도 세션이 살아 있거나
- 원래 끊겨야 할 접속이 계속 유지되거나
- 탈취된 토큰이 오래 악용되거나

하는 문제가 생길 수 있습니다.

### 3. 관리자 토큰을 브라우저 저장소에 심어 두지 않았는가

테스트 편의를 위해 관리자 토큰을 `localStorage` 같은 곳에 저장해 두는 경우가 있습니다.

그 코드가 남은 채 배포되면,

- 그 서비스를 쓰는 모든 사용자가
- 관리자 수준 기능을 쓸 수 있는 길

이 열릴 수 있습니다.

이건 "잠깐 테스트하려고 올려둔 사다리"를 안 치운 채 문을 열어 두는 것과 비슷합니다.

### 4. 너무 쉬운 관리자 계정을 쓰고 있지 않은가

`admin / admin`, `test1234` 같은 계정은  
직접 설명이 필요 없을 정도로 위험합니다.

운영자 계정일수록 더 길고, 더 예측하기 어려워야 합니다.

### 5. 관리자 계정에 2단계 인증을 걸었는가

관리자 계정은 한 번 뚫리면 피해가 큽니다.  
그래서 이메일 인증, 문자 인증, OTP 같은 추가 확인 장치를 두는 편이 훨씬 안전합니다.

### 어떻게 확인하나

<ul class="note-list">
  <li>로그인 실패가 반복될 때 잠금이나 지연이 생기는지 본다.</li>
  <li>토큰 만료 시간과 재발급 규칙이 있는지 확인한다.</li>
  <li>브라우저 저장소에 관리자 토큰이 남지 않는지 본다.</li>
  <li>운영 계정의 기본 ID·비밀번호가 쉬운 문자열이 아닌지 점검한다.</li>
  <li>관리자 계정에 2단계 인증이 실제로 켜져 있는지 확인한다.</li>
</ul>

### 여기서 기억할 말

<strong>로그인 기능은 "들어오게 하는 기능"이 아니라, 이상한 들어옴을 막는 기능까지 포함해야 한다.</strong>

## 암호화·개인정보 체크리스트 3가지

### 13. HTTPS가 실제로 적용되어 있는가

HTTP 뒤에 붙는 `S`는 보안 통신이라는 뜻입니다.

이게 꺼져 있으면 로그인할 때 입력한

- 아이디
- 비밀번호
- 기타 전송 데이터

가 암호화되지 않은 채 오갈 수 있습니다.

요즘 배포 플랫폼은 자동으로 붙여 주는 경우가 많지만,  
직접 서버를 운영하면 따로 챙겨야 할 수 있습니다.

### 어떻게 확인하나

- 주소창에 자물쇠 표시가 보이는지 본다.
- URL이 `http://`가 아니라 `https://`인지 확인한다.

### 여기서 기억할 말

<strong>로그인 창이 있어도, 통신이 잠기지 않으면 내용물은 새어 나갈 수 있다.</strong>

### 14. 비밀번호를 평문이 아니라 해시로 저장하는가

비밀번호는 되돌릴 수 있게 저장하면 안 됩니다.

여기서 핵심은 구분입니다.

- 암호화: 다시 풀 수 있다
- 해시: 다시 원문으로 되돌릴 수 없다

비밀번호는 두 번째여야 합니다.

서비스 운영자도 사용자의 원래 비밀번호를 알 수 없게 저장되는 것이 정상입니다.

데이터베이스를 열어 봤을 때 비밀번호가 그대로 읽힌다면, 바로 고쳐야 합니다.

그리고 이 부분은 AI가 대충 짠 자체 방식보다  
`bcrypt`처럼 검증된 방식을 쓰는 쪽이 훨씬 안전합니다.

### 어떻게 확인하나

1. 사용자 테이블의 비밀번호 저장값을 확인한다.
2. 사람이 읽을 수 있는 원문이면 바로 위험 신호로 본다.
3. 검증된 해시 방식으로 바뀌어 있는지 확인한다.

### 여기서 기억할 말

<strong>비밀번호는 숨겨 저장하는 것이 아니라, 알아볼 수 없게 저장해야 한다.</strong>

### 15. 법이 정한 민감 정보는 더 엄격하게 다루고 있는가

영상에서는 특히 이런 항목을 짚습니다.

- 고유식별 정보
- 비밀번호
- 생체 정보
- 계좌번호나 카드번호 같은 금융 정보

중요한 건 두 가지입니다.

첫째, 이런 정보는 저장 방식이 더 엄격해야 합니다.  
둘째, <strong>애초에 안 받아도 되는 정보는 받지 않는 편이 더 안전합니다.</strong>

회원가입에 꼭 필요하지도 않은데 습관처럼 더 많이 받는 순간, 지켜야 할 책임도 같이 늘어납니다.

### 어떻게 확인하나

- 우리 서비스가 실제로 수집하는 개인정보 항목을 전부 적어 본다.
- 그중 없어도 되는 항목은 지운다.
- 꼭 필요한 항목만 남기고 저장 방식과 접근 권한을 다시 확인한다.

### 여기서 기억할 말

<strong>많이 모을수록 유능해지는 것이 아니라, 많이 지켜야 할 의무가 늘어난다.</strong>

### 16. 개인정보처리방침을 보이는 곳에 게시했는가

이건 선택이 아니라 기본 의무에 가깝습니다.

이메일 주소 하나만 받아도,

- 무엇을 수집하는지
- 왜 수집하는지
- 얼마나 보관하는지

를 적은 개인정보처리방침이 필요합니다.

그리고 바이브 코딩에서 특히 놓치기 쉬운 게 하나 더 있습니다.

바로 외부 서비스 위탁입니다.

예를 들면

- AI 서비스
- 클라우드 저장소
- 문자 발송 서비스
- 결제 서비스

같은 외부 도구를 쓰고 있다면, 그 사실도 방침 안에 드러나야 합니다.

### 어떻게 확인하나

1. 로그인 화면이나 회원가입 화면에서 개인정보처리방침 링크가 실제로 보이는지 본다.
2. 수집 항목, 이용 목적, 보유 기간, 외부 위탁 항목이 들어 있는지 확인한다.
3. 서비스에서 쓰는 외부 도구 목록과 방침 문구가 서로 맞는지 대조한다.

### 여기서 기억할 말

<strong>개인정보를 받는 순간, 코드만이 아니라 설명 책임도 함께 생긴다.</strong>

## 회원분들이 바로 써볼 만한 AI 점검 프롬프트

<ul class="note-list">
  <li>`조회·수정·삭제 API마다 로그인한 사용자가 해당 데이터의 주인인지 서버에서 검사하는지 찾아서 표로 정리해줘.`</li>
  <li>`일반 사용자 권한으로 접근하면 안 되는 페이지와 API를 모두 찾아서, 프론트엔드 숨김만 있는지 서버 거절까지 있는지 구분해줘.`</li>
  <li>`브라우저 저장소(localStorage, sessionStorage)에 관리자 토큰이나 장기 세션 토큰을 남기는 코드가 있는지 찾아줘.`</li>
  <li>`사용자 비밀번호를 평문으로 저장하는 지점이 있는지 찾고, bcrypt 같은 검증된 해시 방식으로 바꿔야 할 위치를 알려줘.`</li>
  <li>`우리 서비스가 수집하는 개인정보 항목, 외부 위탁 서비스, 개인정보처리방침에 들어가야 할 항목을 한 번에 정리해줘.`</li>
</ul>
