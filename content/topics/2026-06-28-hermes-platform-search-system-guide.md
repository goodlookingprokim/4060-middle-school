# 2026년 6월 28일(일) Hermes에 검색 기능을 붙일 때 왜 플랫폼별 서랍부터 나눠야 할까

AI 에이전트를 조금 쓰다 보면 이런 마음이 생깁니다.

- 웹도 찾고
- 유튜브도 보고
- GitHub도 읽고
- 필요하면 X 같은 플랫폼도 훑어보는

그런 만능 검색 도우미 같은 걸 하나 만들고 싶어집니다.

처음 생각은 보통 이렇습니다.

> 검색 기능 하나를 크게 만들면 되지 않을까?

그런데 실제로 해보면, 한 덩어리로 크게 만드는 방식보다  
<strong>플랫폼별로 도구를 나눠 붙이는 방식</strong>이 훨씬 덜 막히고, 나중에도 손이 덜 갑니다.

오늘은 그 이유를 4060 회원분들도 감 잡기 쉽게 풀어보겠습니다.
특히 Hermes에 직접 붙일 때와 OpenClaw 안에서 운영할 때가 어떻게 다른지도 함께 보겠습니다.

글 끝에는 참고한 자료 출처도 함께 적어두겠습니다.

## 먼저 결론

- 검색기를 하나 크게 만들기보다, 플랫폼별 도구를 나눠 붙이는 방식이 훨씬 현실적입니다.
- Hermes는 직접 구조를 만드는 쪽이고, OpenClaw는 이미 있는 도구 흐름을 정리하는 쪽에 더 가깝습니다.
- 처음에는 `web`, `github`, `youtube`만 안정적으로 붙이고, 그다음에 `Unified Search`를 올리는 순서가 좋습니다.

## 먼저 아주 쉽게 말하면

> Hermes 검색 시스템은 “검색기 하나를 똑똑하게 만드는 일”보다, “플랫폼마다 맞는 도구를 서랍처럼 나눠 두고 필요할 때 꺼내 쓰게 만드는 일”에 가깝습니다.

이 한 줄이 오늘 글의 핵심입니다.

## 1. 왜 하나의 만능 검색기로 만들면 금방 복잡해질까

겉으로 보면 검색은 다 비슷해 보입니다.

- 웹페이지 읽기
- 유튜브 영상 내용 보기
- GitHub 저장소 설명 읽기
- X 글이나 커뮤니티 반응 보기

하지만 실제로는 플랫폼마다 읽는 방식이 다릅니다.

- 웹문서는 일반 URL 읽기나 리더 변환이 잘 맞고
- 유튜브는 자막이나 메타데이터 추출이 중요하고
- GitHub는 `gh` 같은 전용 CLI가 훨씬 정확하고
- 어떤 플랫폼은 로그인이나 쿠키가 있어야 읽히기도 합니다

즉, 겉보기에는 다 검색이지만 속으로 들어가면 도구가 전부 다릅니다.

### 생활 비유로 바꾸면

이건 부엌 정리와 비슷합니다.

숟가락, 젓가락, 칼, 국자는 전부 “주방 도구”입니다.  
그런데 이걸 한 통에 다 섞어 넣으면 찾을 때마다 불편해집니다.

그래서 보통은 이렇게 나눕니다.

- 수저 서랍
- 칼 서랍
- 조리도구 통

Hermes에 검색 기능을 붙일 때도 이 감각이 잘 맞습니다.

- 웹은 웹 서랍
- GitHub는 GitHub 서랍
- YouTube는 YouTube 서랍

이렇게 나눠 둬야 찾기도 쉽고, 새 도구를 더 붙이기도 쉽습니다.

## 2. 그래서 기본 방향은 “플랫폼별 직접 호출”이 좋다

이번에 참고한 Agent-Reach 스타일의 장점도 여기에 있습니다.

핵심은 이것입니다.

- 플랫폼마다 잘 맞는 도구를 정한다
- 가능하면 중간 래퍼를 많이 두지 않는다
- 에이전트가 바로 그 도구를 호출하게 만든다

예를 들면 이런 식입니다.

- GitHub는 `gh`
- YouTube는 `yt-dlp`
- 공개 웹문서는 리더형 URL이나 웹 fetch
- RSS는 피드 파서

이렇게 해두면 좋은 이유가 분명합니다.

- 어느 플랫폼에서 막혔는지 찾기 쉽다
- 성격이 다른 플랫폼을 한 줄로 억지로 묶지 않아도 된다
- 새 플랫폼을 붙일 때 기존 구조를 크게 안 흔들어도 된다

쉽게 말하면  
“큰 기계 하나를 고치는 방식”보다  
“모듈을 하나씩 갈아 끼우는 방식”에 가깝습니다.

## 3. 첫 번째로 만들어야 할 것은 검색기가 아니라 Platform Registry다

많은 분이 먼저 검색 함수부터 만들고 싶어합니다.

그런데 실무에서는 보통 반대가 더 낫습니다.

먼저 만들어야 하는 것은  
<strong>어느 플랫폼을 어떤 도구로 읽을지 정리한 표</strong>입니다.

이걸 여기서는 `Platform Registry`라고 부를 수 있습니다.

예를 들어 이런 정보를 한곳에 모아두는 겁니다.

| 플랫폼 | 기본 도구 | 대체 도구 | 직접 호출 여부 |
| --- | --- | --- | --- |
| web | reader/fetch | rss/raw | 예 |
| github | gh | 웹 열기 | 예 |
| youtube | yt-dlp | 자막 추출 도구 | 예 |
| rss | feed parser | raw xml | 예 |

이 표가 왜 중요할까요?

에이전트가 검색을 하다 막혔을 때,
사람이 머릿속으로 “그럼 이걸로 바꿔보자”를 매번 떠올리지 않아도 되기 때문입니다.

즉, Platform Registry는  
에이전트의 검색 습관을 정리해 둔 운영표라고 보면 됩니다.

## 4. 그다음은 `invoke()`처럼 부르는 창구 하나를 두는 게 좋다

플랫폼별 도구를 다 따로 붙였다고 해도,  
부르는 방식까지 제각각이면 나중에 더 복잡해집니다.

그래서 보통은 이런 공통 창구를 하나 둡니다.

```text
invoke(platform, action, args)
```

겉으로는 한 문장처럼 보이지만,
안에서는 플랫폼마다 다른 도구를 타게 됩니다.

예를 들면 이런 느낌입니다.

- `invoke("github", "search", "agent reach")`
- `invoke("youtube", "read", "<영상 URL>")`
- `invoke("web", "read", "<문서 URL>")`

이 구조가 좋은 이유는 간단합니다.

- 바깥에서는 부르는 법이 비슷하다
- 안에서는 플랫폼별 특성을 살릴 수 있다

자동차로 비유하면
운전자는 핸들과 페달만 쓰면 되지만,
엔진 안쪽 구조는 차종마다 다를 수 있는 것과 비슷합니다.

## 5. 여러 플랫폼을 한 번에 찾고 싶다면 Unified Search를 나중에 얹는다

많은 분이 제일 먼저 “한 번에 다 검색하고 싶다”고 생각합니다.

물론 그것도 가능합니다.
다만 순서는 조금 늦추는 편이 좋습니다.

왜냐하면 멀티 플랫폼 검색은  
각 플랫폼이 최소한 한 번씩은 제대로 돌아간 뒤에 붙여야 덜 꼬이기 때문입니다.

이때 붙이는 것이 `search_across()` 같은 함수입니다.

이 함수의 역할은 단순합니다.

- GitHub에서도 찾고
- YouTube에서도 찾고
- 웹에서도 찾고
- 결과를 한 표준 형식으로 묶는다

예를 들어 결과를 아래처럼 통일할 수 있습니다.

- `title`
- `url`
- `snippet`
- `source_platform`

이렇게 해두면 나중에 에이전트가 정리할 때 편합니다.

즉,
GitHub에서 왔든 유튜브에서 왔든  
일단 같은 상자에 넣어 놓고 나중에 비교할 수 있게 되는 겁니다.

여기서 실제 구축 사례를 보면 한 가지가 더 분명해집니다.

단순히 “여러 플랫폼을 같이 찾는다”가 아니라,  
결과를 아래처럼 같은 형식으로 맞춰 두는 것이 중요합니다.

- `title`
- `url`
- `snippet`
- `source_platform`

이 부분이 정리돼 있어야 나중에 Hermes든 OpenClaw든 검색 결과를 다시 요약하거나 비교할 때 덜 꼬입니다.

## 6. 새 플랫폼을 쉽게 붙이려면 add_platform 같은 스크립트가 생각보다 중요하다

처음에는 그냥 손으로 추가해도 됩니다.

그런데 한두 개 붙이고 나면 금방 이런 일이 생깁니다.

- config 파일에도 한 줄 추가해야 하고
- invoker에도 분기 추가해야 하고
- 문서도 고쳐야 하고
- 테스트용 샘플도 넣고 싶어집니다

이럴 때 `add_platform.py` 같은 작은 스크립트가 있으면 편합니다.

이 스크립트는 거창할 필요가 없습니다.
딱 아래 정도만 해줘도 충분합니다.

- config에 플랫폼 항목 추가
- invoker에 빈 stub 생성
- docs에 새 항목 자리 만들기

이건 집에 새 서랍장을 들일 때,
이름표와 위치를 같이 정해두는 것과 비슷합니다.

나중에 “이 도구 어디에 붙였더라?” 하고 다시 헤매는 일이 줄어듭니다.

이번에 받은 구축 사례를 보면,
이 단계가 단순한 편의 기능이 아니라
실제로 확장 속도를 좌우하는 부분이라는 점도 확인됩니다.

즉,

- 새 플랫폼 이름을 등록하고
- 기본 도구와 fallback을 적고
- invoker 쪽에 빈 연결부를 만들고
- 문서에도 흔적을 남기는 흐름

이 한 번에 돌아가야
“새 플랫폼을 붙일 때마다 구조가 흐트러지는 문제”를 줄일 수 있습니다.

## 7. 문서화는 마지막 일이 아니라 중간부터 같이 해야 한다

기술 작업을 하다 보면 문서는 늘 뒤로 밀립니다.

그런데 이런 구조는 오히려 문서가 빨리 있어야 합니다.

왜냐하면 나중에 본인도 헷갈리기 때문입니다.

문서에는 최소한 아래가 들어가면 좋습니다.

- 지금 지원하는 플랫폼 목록
- 각 플랫폼의 기본 도구
- fallback 규칙
- 검색할 때 자주 쓰는 예시 문장
- 새 플랫폼 추가 순서

특히 다른 에이전트가 읽을 수 있게 만들려면,
문서는 “설명서”이면서 동시에 “운영 규칙” 역할도 해야 합니다.

## 8. Hermes에서 세팅할 때와 OpenClaw에서 세팅할 때는 무엇이 다를까

여기서 한 가지는 꼭 나눠서 봐야 합니다.

겉으로 보기에는 둘 다 “에이전트에 검색 기능 붙이기”처럼 보이지만,  
Hermes에서 세팅할 때와 OpenClaw에서 세팅할 때는 출발점이 조금 다릅니다.

### Hermes에서 세팅할 때 참고할 점

Hermes 쪽은 보통  
<strong>내가 직접 플랫폼 도구를 붙이고, 그 호출 흐름을 설계하는 쪽</strong>에 더 가깝습니다.

즉, 아래 질문이 중요해집니다.

- GitHub는 어떤 CLI로 읽을까
- YouTube는 자막을 어떤 방식으로 가져올까
- 웹문서는 그냥 fetch로 볼까, 리더형 URL을 쓸까
- 이 도구들을 어느 파일에서 어떻게 부를까

Hermes에서는 특히 아래가 중요합니다.

- `Platform Registry`를 먼저 만든다
- `invoke()` 같은 공통 호출 창구를 만든다
- 각 플랫폼별 도구를 직접 연결한다
- 새 플랫폼을 붙일 때 수정해야 할 파일 수를 줄인다

쉽게 말하면 Hermes는  
<strong>내가 서랍장 자체를 조립하는 쪽</strong>에 가깝습니다.

그래서 Hermes에서 작업할 때는  
“어떤 플랫폼을 어떤 도구에 매핑할까”가 제일 먼저 나옵니다.

### OpenClaw에서 세팅할 때 참고할 점

OpenClaw 쪽은 조금 결이 다릅니다.

OpenClaw는 원래부터

- 여러 도구 연결 구조
- 세션 관리
- 메시지 흐름
- 브라우저나 웹 도구

같은 운영판이 어느 정도 이미 깔려 있는 경우가 많습니다.

그래서 OpenClaw에서는  
<strong>새 검색 구조를 바닥부터 전부 다시 짓는다</strong>기보다,  
<strong>이미 있는 도구 흐름 안에서 어떤 것을 우선 쓰게 만들지 정리하는 쪽</strong>이 더 중요합니다.

즉, OpenClaw에서는 이런 질문이 더 중요해집니다.

- 이미 있는 웹 검색이나 fetch 도구로 어디까지 가능한가
- 굳이 새 도구를 붙이지 않아도 되는 플랫폼은 무엇인가
- 세션 안에서 어떤 순서로 검색을 시도하게 할 것인가
- fallback 규칙을 어느 수준까지 자동화할 것인가

OpenClaw에서는 특히 아래가 중요합니다.

- 먼저 기존 도구부터 점검한다
- 정말 필요한 플랫폼만 추가한다
- 검색 순서와 fallback 규칙을 문서로 분명히 적는다
- 에이전트가 어떤 도구를 먼저 시도해야 하는지 운영 기준을 정한다

쉽게 말하면 OpenClaw는  
<strong>이미 있는 서랍장 안에 이름표와 사용 순서를 다시 붙이는 쪽</strong>에 더 가깝습니다.

### 아주 짧게 구분하면

| 구분 | Hermes | OpenClaw |
| --- | --- | --- |
| 출발점 | 직접 구조를 만드는 쪽 | 이미 있는 구조를 정리하는 쪽 |
| 먼저 할 일 | 플랫폼-도구 매핑 설계 | 기존 도구 점검과 우선순위 정리 |
| 핵심 질문 | 무엇을 어떤 CLI/MCP에 붙일까 | 어떤 도구를 먼저 쓰게 할까 |
| 잘 맞는 작업 | 전용 검색 레이어 만들기 | 운영 규칙과 fallback 흐름 다듬기 |

그래서 4060 회원분들 입장에서는 이렇게 생각하면 편합니다.

- Hermes는 “내 검색 시스템을 직접 만드는 쪽”
- OpenClaw는 “있는 도구를 더 똑똑하게 운영하는 쪽”

둘 다 맞는 길이지만, 시작 질문이 다릅니다.

## 9. 이번에 받은 실제 구축 사례에서 특히 확인된 점

이번에 받은 사례 자료를 이 글 흐름과 비교해 보면,
방향 자체가 크게 달라지는 부분은 없었습니다.
오히려 지금 정리한 순서가 실제 구축에서도 꽤 잘 맞았다는 쪽에 가깝습니다.

특히 다시 확인된 포인트는 아래 세 가지입니다.

### 1) Platform Registry가 정말 첫 단계라는 점

사례 자료에서도 제일 먼저 나온 것이
플랫폼 이름, 기본 도구, fallback, direct call 여부를 정리하는 표였습니다.

즉,
검색 함수부터 달려드는 것보다  
<strong>플랫폼 운영표를 먼저 만드는 순서가 실제로도 유효했다</strong>는 뜻입니다.

### 2) `invoke()` 창구가 있어야 구조가 덜 흔들린다는 점

GitHub는 `gh`,
YouTube는 `yt-dlp`처럼
안쪽 연결은 달라도
겉에서는 비슷한 방식으로 부르게 만드는 구조가 실제 사례에서도 핵심이었습니다.

이건 나중에 도구를 바꾸거나 늘릴 때도 유리합니다.

### 3) Unified Search는 “검색 한 번에 다 하기”보다 “결과 형식 통일”이 더 중요하다는 점

사례 자료에서 결과를
`title`, `url`, `snippet`, `source_platform`
형식으로 맞춘 것도 의미가 큽니다.

회원분들 입장에서는 이걸 이렇게 이해하면 됩니다.

> 여러 플랫폼을 동시에 찾는 기술보다, 찾은 결과를 같은 모양으로 정리하는 습관이 먼저 중요하다

이렇게 해두어야
나중에 비교, 요약, 재정리까지 자연스럽게 이어집니다.

즉,
이번 사례는 이 글의 방향을 뒤집는 자료라기보다  
<strong>지금 정리한 구조가 실제로도 꽤 실용적이라는 확인 자료</strong>에 가깝습니다.

## 10. 4060 회원 기준으로는 어디까지 먼저 만들면 좋을까

처음부터 X, Reddit, GitHub, YouTube, RSS, 각종 커뮤니티를 한 번에 붙일 필요는 없습니다.

오히려 아래 정도로 시작하는 게 현실적입니다.

### 1단계

- `web`
- `youtube`
- `github`

이 세 가지만 붙여도 꽤 많은 일이 됩니다.

- 웹문서 요약
- 유튜브 자막 읽기
- GitHub 저장소 설명 확인

### 2단계

- `rss`

이걸 붙이면 반복 자료 수집이 편해집니다.

### 3단계

- 그다음에만 다른 플랫폼 검토

즉, 처음에는 넓게보다 자주 쓰는 것부터 안정적으로가 훨씬 중요합니다.

## 11. 결국 이 구조의 장점은 무엇일까

정리하면 세 가지입니다.

### 첫째, 새 플랫폼 추가가 쉬워집니다

처음 구조를 잘 잡아두면
나중에는 “도구 하나를 어디에 꽂을지”만 정하면 됩니다.

### 둘째, 직접 호출이라 제어가 좋습니다

GitHub는 GitHub답게,
YouTube는 YouTube답게 읽게 만들 수 있습니다.

중간에서 억지로 모두 같은 방식으로 처리하지 않아도 됩니다.

### 셋째, 나중에 멀티 플랫폼 검색으로 확장하기 쉽습니다

플랫폼이 각각 잘 정리돼 있으면
그 위에 `Unified Search`를 올리는 것도 훨씬 자연스러워집니다.

즉,
처음부터 거대한 만능 검색기를 만들려 하지 말고,  
작은 서랍을 잘 나눈 뒤 나중에 서랍장을 연결하는 방식이 더 현실적입니다.

## 먼저 이렇게 시작해보면 좋습니다

당장 Hermes에 붙여보고 싶다면,
아래 순서가 가장 무난합니다.

1. `platforms` 표부터 만든다  
2. `invoke()` 창구 하나를 만든다  
3. `web`, `github`, `youtube`만 먼저 붙인다  
4. 결과 형식을 통일한다  
5. 그다음에만 `search_across()`를 붙인다  

이 순서를 지키면 처음부터 너무 큰 시스템을 만들다가 지치는 일을 꽤 줄일 수 있습니다.

## 마무리

Hermes 검색 시스템을 만든다는 건  
AI에게 “검색 좀 잘해봐”라고 말하는 일이 아닙니다.

그보다 더 정확하게는,

> 플랫폼마다 맞는 도구를 잘 나눠 두고, 에이전트가 그 서랍을 헷갈리지 않게 꺼내 쓰도록 길을 만들어주는 일

에 가깝습니다.

이 감각만 잡아도 구조가 훨씬 단순해집니다.
