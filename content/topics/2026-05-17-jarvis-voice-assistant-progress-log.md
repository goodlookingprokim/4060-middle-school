# 2026년 5월 17일(일) 자비스형 음성 비서, 여기까지 실제로 만들어보니

요즘 AI를 조금만 만져봐도 이런 생각이 듭니다.

“텍스트로 묻고 답하는 건 이제 되는데, 진짜 비서처럼 말로 자연스럽게 주고받을 수는 없을까?”

이번에는 바로 그 질문에서 출발했습니다. 목표는 단순한 음성 챗봇이 아니었습니다. <strong>짧게 반응하고, 차분하게 말하고, 필요 이상으로 떠들지 않는 인간 비서형 음성 인터페이스</strong>를 만드는 쪽이었습니다.

그리고 여기서 중요한 건 결과만 보여주는 게 아니었습니다.

이번 작업은 나중에 4060미들스쿨 실습 매뉴얼로 다시 쓸 예정이라서,
- 무엇이 됐는지
- 어디서 막혔는지
- 왜 방향을 바꿨는지
- 초보자는 어디서 가장 많이 헷갈리는지
이 흐름 자체를 남기는 것이 더 중요했습니다.

## 먼저 한 줄 요약

지금은 아직 완성형 자비스는 아닙니다.
하지만 <strong>마이크 입력 → STT → 로컬 LLM → TTS → GUI 재생</strong>까지 이어지는 기본 파이프라인은 실제로 돌아가기 시작했습니다.

그리고 그 과정에서 꽤 중요한 사실도 분명해졌습니다.

<strong>“말을 하는 것”과 “질문에 제대로 답하는 것”은 전혀 다른 단계</strong>라는 점입니다.

## 이번에 목표로 잡은 기본 구조

이번 버전은 무료·로컬 우선으로 구성했습니다.

- STT: `faster-whisper`
- LLM: `Ollama`
- TTS: `Supertonic`
- GUI: `tkinter` 기반 작은 창

왜 이렇게 잡았냐면, 멋진 데모보다 <strong>계속 켜두고 시험해볼 수 있는 구조</strong>가 먼저 필요했기 때문입니다.

쉽게 말해,
클라우드 요금이 계속 나가는 구조보다
로컬에서 계속 만져보고 바꿔볼 수 있는 작업형 비서가 먼저였습니다.

## 처음엔 터미널에서만 돌아갔습니다

맨 처음은 아주 단순했습니다.

- 엔터 누르기
- 몇 초 녹음
- STT 변환
- LLM 응답
- TTS 재생

이 흐름만 이어도 사실 꽤 감동적입니다.
내가 말하면 컴퓨터가 듣고, 짧게 정리해서 다시 사람 목소리처럼 읽어주니까요.

그런데 곧 불편함이 드러났습니다.

터미널은 테스트용으로는 괜찮아도,
실제로 계속 만지려면 너무 불편합니다.
버튼도 없고, 지금 어디까지 진행 중인지도 한눈에 안 보이고,
조금만 대화가 쌓여도 흐름이 금방 끊깁니다.

그래서 바로 작은 GUI 창으로 방향을 바꿨습니다.

## GUI를 붙이니 비로소 “앱” 같아졌습니다

지금 GUI에서는 아래가 보입니다.

- 질문하기 버튼
- 중지 버튼
- 다시 듣기 버튼
- 현재 상태
- 가장 최근 질문과 답변
- 이전 대화 기록
- 로컬 LLM 선택 박스

여기서 중요한 건 모양보다 순서였습니다.

처음엔 질문과 답이 아래로 계속 쌓이는 구조였는데, 이러면 다시 질문하려고 할 때 자꾸 아래로 내려가야 했습니다. 그래서 지금은 이렇게 바꿨습니다.

- 버튼은 맨 위 고정
- 가장 최근 질문과 답변은 맨 위
- 이전 기록은 시간 역순으로 아래 정렬

이건 작은 차이 같아 보여도, 실제로 써보면 체감이 꽤 큽니다.

## 테스트용 맥 환경에서 처음 크게 막힌 지점

가장 당황스러웠던 문제는 이거였습니다.

TTS 파일은 잘 만들어지는데, 전체 앱을 돌리면 마지막 재생 구간에서 파이썬이 죽었습니다.

정확히 보면,
- STT는 됨
- LLM은 됨
- TTS 파일 생성도 됨
- 그런데 마지막 재생에서 세그폴트 발생

이걸 하나씩 나눠서 확인해보니, 원인은 Supertonic이 아니라 <strong>`simpleaudio` 재생 구간</strong> 쪽일 가능성이 높았습니다.

그래서 방향을 바꿨습니다.

복잡한 추측보다 먼저,
macOS 기본 재생기인 `afplay`로 바꿔보자는 쪽으로 갔습니다.

결과는 좋았습니다.

- `afplay` 수동 재생 성공
- `playback.py`를 `afplay` 기반으로 교체
- 이후 전체 파이프라인 한 바퀴 성공

이 경험은 초보자 매뉴얼에서 아주 중요합니다.
겉으로는 “음성 비서가 안 된다”처럼 보여도,
사실은 <strong>마지막 오디오 재생 라이브러리 하나가 문제</strong>일 수 있다는 걸 보여주기 때문입니다.

## 설치와 환경은 깨끗하게 가야 한다는 것도 다시 확인했습니다

실험 중에는 이런 경고도 나왔습니다.

- `numpy` 충돌
- `protobuf` 충돌
- `tensorflow`, `mediapipe`, `streamlit` 등과의 버전 충돌 경고

이럴 때 흔히 “일단 돌아가니까 넘어가자” 하기 쉽습니다.
하지만 이번 프로젝트는 초보자 실습 매뉴얼로 다시 쓸 계획이라서, 여기서 방향을 분명히 잡았습니다.

<strong>초보자용 매뉴얼이라면, 경고를 안고 가기보다 전용 환경을 깔끔하게 정리하고 가는 편이 맞다.</strong>

그래서 이번에는
- 호환되는 Python 버전 기준 정리
- 전용 `.venv`
- `.env` 우선 로드
- 설치 확인 단계 분리
- 어디서 막히는지까지 같이 기록
이 기준으로 문서를 다시 잡기 시작했습니다.

## 공개 글로 남길 때 따로 조심한 것

이번 글은 공개 블로그에 올릴 글이라서, 기술 내용과 별개로 아래 기준도 같이 잡았습니다.

- 개인 이름이나 대화 상대 정보는 넣지 않기
- 로컬 경로, 토큰, 키, 계정값은 그대로 싣지 않기
- 장비를 너무 정확히 짚는 식별 정보는 줄이기
- 보안 경고 전문을 그대로 붙이지 않고, 의미만 설명하기

이런 기준은 글을 예쁘게 보이게 하려는 목적보다, 나중에 같은 실습을 따라 하는 분들이 불필요한 개인정보나 운영 정보를 그대로 공개하지 않게 하려는 목적이 더 큽니다.

## 영어 단어가 섞이면 생각보다 잘 흔들립니다

실제 음성 테스트를 해보면 이런 일이 자주 생깁니다.

- `AI news`가 어색하게 들어감
- `Supertonic`이 흔들림
- `Codex`, `Hermes`, `Ollama` 같은 단어가 틀어짐

문장 전체는 얼추 맞아도, 이런 핵심 단어 하나가 바뀌면 LLM은 전혀 다른 질문으로 받아들일 수 있습니다.

그래서 이번엔 설명만 하지 않고, STT 뒤에 간단한 후처리 보정도 붙였습니다.

예를 들면 이런 식입니다.

- `AI news` → `AI 뉴스`
- `오픈 ai` → `오픈AI`
- `슈퍼 토닉` → `슈퍼토닉`
- `코덱 스` → `코덱스`
- `올 라마` → `올라마`

완벽한 해결은 아니지만, 현장에서는 이런 작은 보정이 생각보다 체감이 큽니다.

## 녹음 시간도 조금 줄였습니다

처음엔 6초로 잡았는데, 실제로 눌러보면 약간 길게 느껴졌습니다.
그래서 지금 기본은 5초로 줄여두었습니다.

아주 작은 차이 같지만,
음성 비서는 단계가 많아서 1초가 은근히 크게 느껴집니다.

- 듣기
- STT
- LLM
- TTS
- 재생

이 흐름이 연달아 있으니,
앞단에서 1초 줄어드는 것도 사용자가 받는 체감엔 꽤 영향을 줍니다.

## 다시 듣기 버튼과 로컬 모델 선택도 붙였습니다

여기까지 오면서 작은 편의 기능도 같이 들어갔습니다.

### 다시 듣기 버튼
방금 나온 답을 한 번 더 들을 수 있습니다.
현장에서는 “방금 뭐라고 했지?”가 자주 나오기 때문에 이 기능이 꽤 유용합니다.

### Ollama 로컬 모델 선택
GUI에서 내려받아 둔 로컬 모델을 바로 고를 수 있게 만들었습니다.

이 기능이 왜 중요하냐면,
이제 문제는 단순히 “말이 나오느냐”가 아니라 “질문에 실제로 답하느냐” 쪽으로 넘어왔기 때문입니다.

가벼운 모델은 빠르지만 답이 얕을 수 있고,
큰 모델은 조금 느려도 훨씬 낫게 답할 수 있습니다.

그래서 앞으로는
- 빠른 테스트용 모델
- 실제 답변 품질 확인용 모델
을 구분해서 비교해보려 합니다.

## 지금 단계에서 가장 중요한 깨달음

이번 테스트를 하면서 제일 분명해진 건 이겁니다.

<strong>“오, 말을 하네” 단계와 “정말 질문에 답하네” 단계는 다르다.</strong>

지금은 첫 번째 문턱은 넘었습니다.
실제로 음성 파이프라인은 연결됐고, GUI도 붙었고, 다시 듣기와 모델 선택도 들어갔습니다.

하지만 아직 두 번째 문턱은 더 남아 있습니다.

### 아직 남아 있는 문제
- 질문을 다른 단어로 인식하는 경우가 있음
- 질문 의도와 다른 답이 나올 때가 있음
- 로컬 소형 모델의 한계가 빨리 드러날 수 있음
- 최신 정보나 실제 업무 질문은 검색/메모 연결이 필요함

즉, 지금부터의 과제는
<strong>음성을 예쁘게 만드는 것보다, 정확히 듣고 실제로 답하게 만드는 것</strong>입니다.

## 다음 단계는 이렇게 갈 생각입니다

이제부터는 아래 순서가 가장 현실적입니다.

### 1. STT 정확도 더 올리기
- Whisper 설정 계속 조정
- 자주 틀리는 단어 사전 확장
- 질문 예시도 한국어 뼈대 중심으로 다듬기

### 2. 로컬 LLM 비교 테스트
- `qwen2.5:3b`
- 더 큰 로컬 모델

같은 질문을 넣고 어느 쪽이 더 실제 답을 잘하는지 봐야 합니다.

### 3. 실제 질문 세트로 평가
예를 들면 이런 질문입니다.

- 오늘 AI 뉴스 한 줄로 정리해줘
- 이 문장을 카톡 공지 말투로 바꿔줘
- 오늘 해야 할 일 3가지만 정리해줘
- 블로그 첫 문단만 시작해줘

이런 질문으로 테스트해야 진짜 실사용 감각이 나옵니다.

### 4. 나중에는 검색과 메모 연결
최신 정보나 개인 작업 맥락이 필요한 질문은,
나중에 웹 검색과 로컬 메모 연결이 붙어야 훨씬 쓸 만해질 겁니다.

## 오늘 여기까지 해보니

예전 같으면 “음성 비서 만들기”를 들었을 때,
그냥 멋진 데모 한 번 돌리고 끝나는 느낌이 강했습니다.

그런데 실제로 해보니 전혀 다릅니다.

- 환경 충돌을 어떻게 피할지
- 어디서 막히는지
- 재생은 왜 죽는지
- GUI는 어떤 구조가 덜 불편한지
- 영어 단어는 왜 흔들리는지
- 로컬 모델은 어디까지 버텨주는지

이런 문제를 하나씩 풀어가야 비로소 “쓸 만한 비서”로 가까워집니다.

그래서 이번 글은 완성 자랑보다,
<strong>실제로 여기까지 오면서 무엇을 확인했고 무엇을 바꿨는지 남기는 기록</strong>에 더 가깝습니다.

이게 쌓여야 나중에 정말 초보자도 따라올 수 있는 자비스 실습 매뉴얼이 됩니다.

## 마무리

오늘 기준으로 보면,
자비스형 음성 비서는 아직 테스트 버전입니다.

하지만 중요한 건 “아직 멀었다”가 아니라,
이제는 막연한 아이디어가 아니라 <strong>실제로 켜지고, 듣고, 말하고, 조금씩 더 좋아지고 있는 작업물</strong>이 되었다는 점입니다.

다음 글에서는 아마 두 갈래 중 하나로 이어질 것 같습니다.

- 질문 인식 정확도를 더 올리는 쪽
- 실제 답변 품질이 더 좋은 로컬 모델을 비교하는 쪽

어느 쪽이든 기준은 하나입니다.

<strong>멋있어 보이는 비서보다, 실제로 도움이 되는 비서에 더 가까워지는 것.</strong>
