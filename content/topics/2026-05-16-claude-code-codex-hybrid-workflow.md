# 2026년 5월 16일(토) Claude Code와 Codex를 같이 쓸 때 일이 편해지는 순간

AI 도구 이야기를 하다 보면 자꾸 이런 질문으로 흘러갑니다.

“그래서 Claude Code가 더 좋아요, Codex가 더 좋아요?”

그런데 실제로 일을 해보면 이 질문이 그렇게 중요하지 않을 때가 많습니다. 망치와 드라이버 중 누가 더 훌륭하냐를 따지는 것과 조금 비슷합니다. 더 중요한 건, <strong>지금 내가 박아야 하는 게 못인지 나사인지</strong>입니다.

이번 글은 시민개발자 구씨가 이야기한 흐름을 바탕으로, Claude Code와 Codex를 비교하기보다 <strong>어떻게 역할을 나눠 같이 쓰면 일이 더 편해지는지</strong>를 4060미들스쿨 멤버들이 바로 떠올릴 수 있게 풀어본 메모입니다.

참고 링크: [Lilys AI 요약 링크](https://lilys.ai/digest/9610643/11106030?s=1&noteVersionId=7630182)

## 먼저 한 문장으로 정리하면

- <strong>Claude Code는 판단과 방향 잡기</strong>에 더 잘 어울리고
- <strong>Codex는 시킨 일을 묵묵히 수행</strong>하게 붙이기 좋습니다.

이렇게 역할을 나누면 훨씬 덜 헷갈립니다.

즉,

- Claude Code = "어떻게 할지 정하는 사람"
- Codex = "정해진 일을 손발처럼 처리하는 사람"

이 감각으로 보면 됩니다.

## 왜 비교보다 역할 분담이 더 중요할까

많은 분들이 AI 도구를 처음 쓸 때 이런 실수를 합니다.

- 한 도구에게 처음부터 다 시킨다
- 기획, 판단, 실행, 정리, 보고서까지 한 번에 맡긴다
- 중간에 뭐가 잘못됐는지 모르겠는데 일은 점점 길어진다

그러다 보면 이런 느낌이 옵니다.

“얘가 똑똑한 것 같긴 한데, 이상하게 내가 더 피곤하다.”

이럴 때 필요한 게 역할 분담입니다. 사람하고 일할 때도 그렇습니다.

- 한 명은 전체 흐름을 보고
- 한 명은 손이 많이 가는 작업을 처리하고
- 중간중간 기록을 남기고
- 서로 어디까지 했는지 확인해야
일이 덜 꼬입니다.

AI 도구도 비슷합니다.

## 아주 쉽게 비유해보면

동네 작은 가게를 운영한다고 생각해보겠습니다.

### Claude Code는 이런 사람에 가깝습니다

- 오늘 뭘 먼저 해야 할지 정리해줍니다
- 메뉴판을 어떻게 바꿔야 할지 판단합니다
- 손님이 왜 줄었는지 가설을 세웁니다
- 여러 선택지 중 어느 방향이 나은지 같이 따집니다

즉, <strong>사장 옆에서 같이 고민해주는 실장</strong> 같은 느낌입니다.

### Codex는 이런 사람에 가깝습니다

- 시킨 형식대로 문서를 정리합니다
- 필요한 표를 만듭니다
- 대시보드 초안을 만듭니다
- 반복 작업을 묵묵히 처리합니다

즉, <strong>구체적인 작업을 빠르게 해주는 실무 담당자</strong>에 가깝습니다.

둘 다 필요하지만, 맡기는 일이 같을 필요는 없습니다.

## 구씨 방식의 핵심은 “협업 프로토콜”입니다

이번 내용에서 제일 중요한 건 도구 이름보다도 <strong>협업 프로토콜</strong>이라는 말입니다. 말이 조금 어려워 보이지만 뜻은 간단합니다.

> 일을 맡길 때, 누구에게 무엇을 어떤 순서로 맡길지 미리 정해두는 약속

이 약속이 없으면 AI를 여러 개 써도 금방 뒤엉킵니다.

구씨 방식에서 나온 핵심 재료는 이런 것들입니다.

- 프로젝트 현황판
- 작업 지침서
- 비즈니스 문서
- 진행 상황 공유
- 작업 로그 기록

쉽게 말하면, <strong>AI 둘을 같이 쓰더라도 서로 딴소리하지 않게 중간 기준판을 세워두는 것</strong>입니다.

## 4060미들스쿨 버전으로 바꾸면 어떻게 쓸 수 있을까

이제 이걸 생활에 붙여보겠습니다.

## 1. 모임 준비할 때

예를 들어 잘생김프로쌤이 다음 모임 주제를 준비한다고 해보겠습니다.

### Claude Code에게 맡길 일

- 이번 모임 주제를 3가지로 정리해줘
- 지난번 모임과 자연스럽게 이어지는 흐름을 짜줘
- 참가자들이 부담 없이 따라올 수 있는 순서를 만들어줘
- 공지문 톤은 너무 딱딱하지 않게 잡아줘

이건 판단과 구조화가 필요한 일입니다.

### Codex에게 맡길 일

- 정해진 구조대로 공지문 초안 파일 만들어줘
- 시간표 형식으로 정리해줘
- 참가자용 한 장 요약문 만들어줘
- 블로그용 목차 초안 뽑아줘

이건 정해진 기준에 맞춰 손을 많이 써야 하는 일입니다.

이렇게 나누면 머리가 덜 복잡합니다.

## 2. 동네 모임 후기나 강의 정리할 때

모임이 끝나면 늘 이런 일이 생깁니다.

- 기억은 많은데 정리는 안 된다
- 어떤 내용을 블로그에 남길지 헷갈린다
- 카톡용 요약, 블로그용 글, 내 개인 메모가 다 달라야 한다

이럴 때도 역할을 나눌 수 있습니다.

### Claude Code

- 오늘 모임에서 핵심이 된 질문이 뭔지 뽑아줘
- 이 후기를 어떤 흐름으로 쓰면 읽기 좋을지 정리해줘
- 참가자들이 실제로 얻어갈 만한 포인트를 골라줘

### Codex

- 블로그용 초안 문서 생성
- 카톡용 짧은 요약문 생성
- 제목 후보 10개 뽑기
- 이미지용 문구 후보 정리

이 방식이 좋은 이유는, <strong>생각과 손작업을 분리할 수 있기 때문</strong>입니다.

## 3. 작은 사업이나 개인 업무 정리할 때

예를 들어 보험, 교육, 상담, 컨설팅, 판매처럼 사람을 자주 만나고 문서를 자주 다루는 일을 한다고 해보겠습니다.

### Claude Code에게 먼저 묻기

- 이번 달 반복되는 고객 질문이 뭔지 정리해줘
- 안내문을 어디부터 손봐야 덜 헷갈릴지 판단해줘
- 고객 응대 흐름에서 병목이 생기는 지점을 짚어줘

### Codex에게 이어서 맡기기

- 자주 묻는 질문 정리표 만들기
- 응대 문구 3종 버전 만들기
- 보고서 틀 만들기
- 대시보드 초안 만들기

즉, <strong>먼저 생각을 정리한 뒤에 실행을 붙이는 구조</strong>입니다.

## “프로젝트 현황판”은 어렵게 생각하지 않아도 됩니다

구씨가 말한 프로젝트 현황판이라는 것도 사실 거창한 게 아닙니다.

생활 버전으로 바꾸면 아래 정도만 있어도 충분합니다.

- 지금 하고 있는 일은 무엇인가
- 누가 맡고 있는가
- 어디까지 진행됐는가
- 다음 할 일은 무엇인가
- 막힌 것은 무엇인가

예를 들어 이렇게 적어둘 수 있습니다.

- 모임 공지 초안: 작성 중
- 참가자 질문 정리: 완료
- 카드뉴스 문안: 검토 필요
- 블로그 초안: 초안 완료, 제목 수정 필요
- 카톡 전송: 최종 승인 대기

이게 있으면 Claude Code도, Codex도 같은 판을 보고 움직이게 됩니다.

## “작업 지침서”도 우리 식으로 바꾸면 훨씬 쉽습니다

작업 지침서라고 하면 너무 회사 문서처럼 느껴질 수 있습니다. 그런데 사실은 이런 정도면 충분합니다.

### 예시: 모임 공지 작업 지침서

- 말투는 자연스럽게
- 과한 AI 말투 금지
- 첫 문단은 부담 없이 읽히게
- 시간, 장소, 준비물은 빠짐없이
- 카톡용 문구는 짧게
- 블로그용 글은 조금 더 자세하게

이런 지침이 있으면, Codex 같은 실행형 도구는 훨씬 안정적으로 움직입니다.

반대로 이 기준이 없으면 같은 내용을 시켜도 매번 결과가 흔들릴 수 있습니다.

## CLI 환경과 앱 환경을 나눠 쓰는 감각

구씨 내용에서 또 흥미로운 지점은 <strong>CLI 환경의 Claude Code와 앱 환경의 Codex를 조합</strong>하는 방식입니다.

이 부분도 초보자 눈높이로 바꾸면 이렇게 이해하면 됩니다.

- Claude Code는 조금 더 작업실 같은 느낌
- Codex 앱은 조금 더 바로 시켜보는 작업창 같은 느낌

예를 들어,

- Claude Code에서 전체 방향을 정하고
- Codex에서 구체적인 결과물을 뽑고
- 다시 Claude Code로 가져와 검토하거나 수정 방향을 정하는 식입니다.

마치,

- 주방장(방향 결정)
- 조리 담당(실행)
- 마지막 맛보기(검토)

처럼 돌리는 느낌이라고 보면 쉽습니다.

## 안전하게 같이 쓰려면 꼭 필요한 것

도구를 두 개 이상 붙이면 편해지는 만큼, 엉키는 속도도 빨라질 수 있습니다. 그래서 아래 세 가지가 중요합니다.

### 1. 워크트리처럼 작업 공간을 나눠 쓰기

쉽게 말하면, 본 작업판과 실험판을 섞지 않는 것입니다.

- 지금 운영 중인 파일은 그대로 두고
- 새 시도는 별도 작업 공간에서 해보고
- 괜찮으면 옮겨오는 방식입니다.

이건 주방에서 본 반찬통 옆에 시험 요리를 안 쏟는 것과 비슷합니다.

### 2. 진행 상황을 계속 공유하기

AI에게 일을 맡겨도, 지금 어디까지 했는지 보여주는 기준이 필요합니다.

- 초안 완료
- 검토 중
- 수정 필요
- 발행 준비 완료

이 정도 표시만 있어도 훨씬 덜 불안합니다.

### 3. 작업 로그를 남기기

이건 나중에 정말 중요해집니다.

- 어떤 지시를 했는지
- 어떤 결과가 나왔는지
- 무엇을 고쳤는지
- 왜 방향을 바꿨는지

이 기록이 있어야 다음에 같은 실수를 덜 합니다.

우리 모임에서도 결국 강한 사람은 천재처럼 한 번에 다 하는 사람이 아니라, <strong>자기 작업 흐름을 다시 꺼내 쓸 수 있게 남겨두는 사람</strong>입니다.

## 비교보다 조합이 중요한 이유

Claude Code와 Codex를 굳이 싸움 붙일 필요는 없습니다.

오히려 이렇게 보는 편이 더 실용적입니다.

- 판단이 필요하면 Claude Code
- 반복 실행이 많으면 Codex
- 구조를 짜는 건 Claude Code
- 결과물 초안 생산은 Codex
- 다시 다듬고 우선순위 정하는 건 Claude Code

물론 사람마다 손에 맞는 감각은 다를 수 있습니다. 중요한 건 고정된 정답보다 <strong>내 일에 맞게 워크플로를 계속 조정하는 태도</strong>입니다.

## 4060미들스쿨 멤버라면 이렇게 시작해보면 좋겠습니다

처음부터 거창하게 하지 않아도 됩니다.

### 아주 쉬운 시작

1. 내가 자주 하는 일을 하나 고른다
   - 모임 공지
   - 상담 정리
   - 보고서 초안
   - 블로그 글 정리

2. 그 일에서 판단과 실행을 나눈다
   - 판단: 방향, 구조, 우선순위
   - 실행: 정리, 생성, 초안 만들기

3. 판단은 Claude Code에 맡기고
4. 실행은 Codex에 맡겨본다
5. 마지막으로 다시 내가 확인한다

이 정도만 해도 충분히 체감이 옵니다.

## 이제 진짜로 해보는 실습 순서

여기서부터는 나눔 시간에 바로 같이 해볼 수 있게, 가능한 한 순서를 잘게 나눠보겠습니다.

처음부터 복잡하게 하지 말고, <strong>모임 공지 하나 만들기</strong>를 예시로 잡는 게 가장 좋습니다. 이유는 간단합니다.

- 다들 어떤 결과물이 나와야 하는지 쉽게 이해할 수 있고
- 판단이 필요한 부분과 손작업이 필요한 부분이 분명하고
- 결과를 바로 카톡 문구, 블로그 초안, 한 장 요약으로 바꿔볼 수 있기 때문입니다.

## 실습 전에 준비할 것

아래 네 가지만 있으면 됩니다.

1. 오늘 다룰 주제 메모 5줄
2. 모임 시간, 장소, 대상 같은 기본 정보
3. Claude Code를 켤 수 있는 환경
4. Codex를 켤 수 있는 환경

메모는 길 필요가 없습니다. 예를 들면 이 정도면 충분합니다.

- 주제: Claude Code와 Codex 역할 나누기
- 대상: 4060미들스쿨 중급반
- 목표: 비교보다 역할 분담 감 잡기
- 결과물: 공지문, 카드뉴스 문안, 블로그 초안
- 톤: 쉬운 말, 생활 예시, 부담 없는 문장

이 메모가 오늘 실습의 씨앗입니다.

## 실습 1단계: Claude Code에게 먼저 방향을 잡아달라고 하기

첫 단계에서는 Claude Code에게 바로 결과물을 시키지 말고, <strong>일의 구조를 먼저 잡아달라</strong>고 하는 편이 좋습니다.

예를 들면 이렇게 말할 수 있습니다.

```text
다음 모임 공지를 준비하려고 합니다.
주제는 Claude Code와 Codex를 비교하지 말고 역할을 나눠 쓰는 방법입니다.

대상은 4060미들스쿨 멤버들이고,
너무 기술적으로 어렵지 않게,
생활 예시가 들어가야 합니다.

먼저 아래 4가지를 정리해 주세요.
1) 이번 모임에서 꼭 전달해야 할 핵심 3가지
2) 참가자들이 가장 헷갈릴 지점 3가지
3) 공지문에 반드시 들어가야 할 순서
4) 카드뉴스로 바꾸기 좋은 짧은 문장 5개
```

이 단계에서 기대하는 건 완성본이 아닙니다.
<strong>방향표와 뼈대</strong>입니다.

## 실습 2단계: Claude Code 결과를 작업 지침서로 바꾸기

Claude Code가 방향을 주면, 그걸 바로 다음처럼 짧은 작업 지침서로 바꿔둡니다.

예시:

```text
[작업 지침서]
- 말투는 자연스럽고 쉬워야 함
- 비교 싸움처럼 쓰지 말 것
- Claude Code는 판단, Codex는 실행으로 설명
- 예시는 모임 준비, 상담 정리, 보고서 초안 중심
- 결과물은 공지문 / 카드뉴스 문안 / 블로그 초안 3종
- 첫 문단은 부담 없이 읽히게 시작
```

이 작업 지침서가 있어야 Codex가 흔들리지 않습니다.

쉽게 말하면,
Claude Code가 회의에서 방향을 정한 뒤,
Codex에게 넘길 <strong>업무 메모</strong>를 만든다고 생각하면 됩니다.

## 실습 3단계: Codex에게 첫 결과물을 맡기기

이제 Codex에게는 방향 설명을 길게 하기보다, 정리된 지침과 형식을 줍니다.

예를 들면 이렇게 보낼 수 있습니다.

```text
아래 작업 지침서를 기준으로 4060미들스쿨 모임 공지 초안을 작성해 주세요.

[작업 지침서]
- 말투는 자연스럽고 쉬워야 함
- 비교 싸움처럼 쓰지 말 것
- Claude Code는 판단, Codex는 실행으로 설명
- 예시는 모임 준비, 상담 정리, 보고서 초안 중심
- 첫 문단은 부담 없이 읽히게 시작

형식:
1) 공지 제목
2) 모임에서 다룰 핵심 3가지
3) 참가자들이 얻어갈 수 있는 점
4) 가볍게 읽고 올 질문 3개
```

이 단계에서 Codex는 의외로 잘합니다. 왜냐하면 이미 판단은 앞 단계에서 끝냈기 때문입니다.

## 실습 4단계: 다시 Claude Code로 검토하기

초안이 나오면 그걸 다시 Claude Code에게 가져갑니다.

이때는 이렇게 물으면 좋습니다.

```text
이 공지 초안을 검토해 주세요.

1) 초보자가 읽기에 어려운 표현이 있는지
2) 생활 예시가 부족한 부분이 있는지
3) 핵심은 좋은데 문장이 딱딱한 부분이 있는지
4) 모임 흐름상 순서를 더 다듬으면 좋은 부분이 있는지

수정 이유를 짧게 설명하고,
개선본도 함께 제안해 주세요.
```

이렇게 하면 Claude Code가 다시 “생각 담당”으로 돌아옵니다.

즉, 한 바퀴가 이렇게 돌아갑니다.

- Claude Code: 방향 설정
- Codex: 초안 생산
- Claude Code: 검토와 조정

이 흐름이 익숙해지면 일이 훨씬 덜 무너집니다.

## 실습 5단계: 같은 재료로 결과물 3개 만들기

이제부터가 재미있습니다. 같은 내용을 가지고 결과물을 세 갈래로 나눠볼 수 있습니다.

### 1. 카톡용 짧은 공지

Codex에게 이렇게 맡길 수 있습니다.

```text
방금 만든 공지 초안을 기준으로,
카카오톡 방에 올릴 짧은 안내문 버전으로 줄여 주세요.

조건:
- 첫 문장은 부담 없이
- 너무 길지 않게
- 읽고 한번 와보고 싶게
- 기술 용어는 최소화
```

### 2. 카드뉴스 문안

```text
같은 내용을 카드뉴스 6장 분량으로 나눠 주세요.

구성:
- 표지 1장
- 뉴스/주제 카드 5장

조건:
- 각 장 제목은 짧게
- 핵심 한 줄이 눈에 띄게
- 장 순서가 분명히 보이게
```

### 3. 블로그 초안

```text
같은 내용을 블로그 글 초안으로 바꿔 주세요.

조건:
- 생활 예시 중심
- 초보자도 읽히게
- 소제목 구조 분명하게
- 마지막에는 실습 포인트 정리
```

이렇게 하면 하나의 생각이 세 가지 결과물로 바뀝니다.

이게 바로 하이브리드 방식이 주는 힘입니다.

## 나눔 시간에 바로 해볼 수 있는 30분 실습안

실제로 모임에서 시연하려면 아래처럼 가면 부담이 적습니다.

### 0~5분
- 오늘 주제 설명
- Claude Code와 Codex를 누가 더 낫다고 보지 말고 역할을 나눠보자고 안내

### 5~10분
- Claude Code에 방향 설정 질문 넣기
- 핵심 3가지, 참가자 질문, 글 구조 받기

### 10~15분
- 그 결과를 짧은 작업 지침서로 정리하기
- 현황판에 "방향 설정 완료"라고 적기

### 15~20분
- Codex에 공지문 초안 맡기기
- 같은 재료로 카드뉴스 문안도 시도하기

### 20~25분
- Claude Code로 다시 검토하기
- 어려운 표현, 어색한 흐름, 부족한 생활 예시 손보기

### 25~30분
- 최종본 비교하기
- 참가자들과 같이 "어디서 Claude Code가 좋았고, 어디서 Codex가 편했는지" 이야기 나누기

이 정도만 해도 실습 시간이 꽤 살아납니다.

## 실습 중 꼭 보여주면 좋은 포인트

나눔 시간에는 결과물만 보여주면 감탄은 있지만 감은 잘 안 남습니다. 아래를 같이 보여줘야 도움이 됩니다.

### 1. 같은 요청을 한 번에 다 시켰을 때와 나눠서 시켰을 때 차이

- 한 번에 다 시키면 결과가 길어지고 흔들릴 수 있음
- 역할을 나누면 덜 흔들리고 수정 이유가 분명해짐

### 2. 작업 지침서가 있을 때와 없을 때 차이

- 지침이 없으면 톤이 들쭉날쭉함
- 지침이 있으면 결과가 안정적임

### 3. 사람이 마지막에 확인해야 하는 이유

- 말투
- 사실관계
- 순서
- 공개 가능한 표현인지 여부

결국 AI 둘을 잘 쓰는 사람은,
둘 다 똑똑하다고 감탄하는 사람이 아니라,
<strong>둘 사이에서 기준을 잡아주는 사람</strong>입니다.

## 처음 실습할 때 흔히 생기는 실수

### 1. 방향도 Codex에게, 검토도 Codex에게 다 맡기는 경우

이러면 빨리 나오긴 해도 중심이 흔들릴 수 있습니다.

### 2. Claude Code에게 처음부터 최종 결과물까지 다 요구하는 경우

이러면 생각과 실행이 한 덩어리로 붙어서 수정 포인트가 흐려질 수 있습니다.

### 3. 작업 지침서를 안 만들고 바로 다음 단계로 가는 경우

그러면 같은 주제를 여러 형식으로 바꿀 때 일관성이 깨집니다.

### 4. 현황판과 로그를 안 남기는 경우

다음에 뭘 어떻게 했는지 다시 못 꺼내게 됩니다.

## 초보자용 아주 간단한 실습 체크리스트

- [ ] 오늘 다룰 주제를 한 줄로 적었다
- [ ] Claude Code에게 핵심 구조를 먼저 물었다
- [ ] 결과를 작업 지침서로 짧게 정리했다
- [ ] Codex에게 형식을 정해 초안을 맡겼다
- [ ] 다시 Claude Code로 검토했다
- [ ] 사람이 마지막 문장을 확인했다
- [ ] 다음에 재사용할 수 있게 로그를 남겼다

## 마무리

Claude Code와 Codex를 놓고 “누가 더 낫다”로 가면 금방 지칩니다. 그런데 “누구에게 어떤 일을 맡기면 덜 피곤할까”로 보면 훨씬 현실적인 답이 나옵니다.

이 관점이 참 좋았습니다.

결국 중요한 건 도구 이름보다도, <strong>내 일의 흐름을 나누고 연결하는 감각</strong>입니다.

- 생각은 어디서 할지
- 실행은 누가 맡을지
- 중간 기록은 어디에 남길지
- 마지막 확인은 어떻게 할지

이 네 가지만 잡혀도 AI 도구는 훨씬 덜 부담스럽고, 훨씬 내 편처럼 느껴집니다.

다음 나눔 시간에는 이 주제를 그냥 설명만 하지 않고, 실제로
<strong>모임 공지 만들기 → 카드뉴스 문안 정리 → 블로그 초안 만들기</strong>
같은 흐름으로 한 번 시연해봐도 재미있겠습니다.
