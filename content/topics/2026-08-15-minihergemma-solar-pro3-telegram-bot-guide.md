# 2026년 8월 15일(토) Hermes와 섞지 않고 Solar Pro 3 텔레그램 봇 하나만 따로 만들고 싶다면

Hermes를 조금 만져보다 보면 이런 마음이 한 번쯤 생깁니다.

"큰 운영 봇은 그대로 두고, 실험용 텔레그램 봇 하나만 따로 빼서 가볍게 돌려보고 싶다."

특히 모델을 나눠 보고 싶을 때 더 그렇습니다.  
Hermes는 Hermes대로 두고, 별도 봇은 `Solar Pro 3`로 붙여서 반응을 보거나, 구조를 더 단순하게 유지하고 싶을 때가 있습니다.

이번 글은 바로 그 경우를 위한 정리입니다.  
사용자께서 보내주신 `MiniHerGemma_bot` README를 바탕으로, 4060미들스쿨에서 바로 따라가기 좋게 줄기를 다시 잡았습니다.

## 먼저 결론

- Hermes와 별도 텔레그램 봇을 **같은 폴더와 같은 환경변수로 섞지 않는 것**이 가장 중요합니다.
- 초보자 기준으로는 `bot.py`, `config.json`, `.env`, `run.sh`, `status.sh` 정도만 먼저 안정적으로 잡아도 충분합니다.
- 문제가 생기면 코드부터 뒤지기보다 `logs/bot.log`, 프로세스 상태, `.env`, `config.json` 순서로 보는 편이 훨씬 덜 헤맵니다.

## 왜 굳이 따로 빼는가

Hermes는 운영 구조가 넓습니다.  
세션, 메모리, 여러 도구 연결, 다른 채널 운영까지 함께 생각하게 됩니다.

그런데 지금 하고 싶은 일이 아주 단순할 수도 있습니다.

- 텔레그램에서 질문을 보내면
- Solar Pro 3가 답하고
- 로그를 확인하면서
- 필요한 만큼만 조용히 운영해 보는 것

이럴 때는 구조를 단순하게 분리하는 편이 좋습니다.

쉽게 말하면,

- Hermes는 큰 사무실
- `MiniHerGemma_bot`은 옆방에 따로 둔 작은 실험실

처럼 보는 편이 자연스럽습니다.

## 처음에 꼭 잡아둘 구조

원문에서 가장 좋은 점은 폴더 구조를 처음부터 투명하게 보여준다는 점이었습니다.

```text
MiniHerGemma_bot/
├── bot.py
├── config.json
├── .env
├── .env.example
├── requirements.txt
├── run.sh
├── stop.sh
├── status.sh
├── logs/
│ └── bot.log
└── README.md
```

이 구조가 좋은 이유는 단순합니다.

- 실제 동작 코드는 `bot.py`
- 모델과 요청 설정은 `config.json`
- 민감 정보는 `.env`
- 실행과 정지는 스크립트로 분리
- 문제 생기면 로그는 `logs/`

즉, 어디를 봐야 할지가 처음부터 정리되어 있습니다.

## 제일 중요한 원칙은 키를 코드에 넣지 않는 것

이런 봇을 처음 만들 때 가장 많이 생기는 실수는 토큰과 API 키를 코드 안에 바로 적어 넣는 것입니다.

그렇게 시작하면 처음에는 빨라 보이지만,

- 나중에 키를 바꿀 때 번거롭고
- 파일을 잘못 공유하면 위험하고
- Git에 실수로 올라갈 가능성도 커집니다

그래서 이 구조에서는 민감 정보는 `.env`에만 둡니다.

```bash
TELEGRAM_BOT_TOKEN=본인이_BotFather에서_발급받은_토큰
UPSTAGE_API_KEY=본인이_Upstage에서_발급받은_API_키
```

그리고 권한도 바로 잠가 둡니다.

```bash
chmod 600 ~/MiniHerGemma_bot/.env
```

이 한 줄이 사소해 보여도 꽤 중요합니다.  
최소한 "아무나 읽을 수 있는 파일" 상태는 피하게 해 주기 때문입니다.

## bot.py는 길어 보여도 역할은 네 가지다

처음부터 전체 코드를 외우려고 하면 부담스럽습니다.  
하지만 역할만 나누어 보면 생각보다 단순합니다.

1. 환경변수에서 텔레그램 토큰과 Upstage API 키를 읽는다.
2. `config.json`에서 모델과 요청 설정을 읽는다.
3. 텔레그램 메시지를 받으면 Solar Pro 3에 전달한다.
4. 받은 답을 다시 텔레그램으로 보낸다.

핵심만 보면 이런 구조입니다.

```python
TELEGRAM_BOT_TOKEN = os.environ.get("TELEGRAM_BOT_TOKEN")
UPSTAGE_API_KEY = os.environ.get("UPSTAGE_API_KEY")

CONFIG = json.load(open("config.json"))
MODEL = CONFIG["model"]
BASE_URL = CONFIG["base_url"]
```

여기서 중요한 건 "복잡한 마법"이 아니라,
<strong>어디서 값을 읽고 어디로 보내는지가 분리되어 있다는 점</strong>입니다.

## 실행 스크립트는 초보자일수록 꼭 두는 편이 낫다

원문처럼 `run.sh`, `stop.sh`, `status.sh`를 따로 두는 방식은 초보자에게 특히 좋습니다.

왜냐하면 실제 운영에서는 명령을 외우는 것보다,  
"지금 실행 중인가", "멈췄나", "로그는 어디서 보나"가 더 자주 필요하기 때문입니다.

예를 들어 `run.sh`는 이런 역할을 합니다.

- `.env` 읽기
- 가상환경이 없으면 만들기
- 가상환경 활성화
- 필요한 패키지 설치
- `bot.py` 실행

이렇게 되면 다음부터는 긴 명령을 다시 조립할 필요 없이 아래처럼 실행해도 됩니다.

```bash
cd ~/MiniHerGemma_bot
./run.sh
```

## 막히면 어디부터 봐야 하나

이런 봇은 "안 된다"는 현상은 비슷해 보여도 원인은 꽤 다릅니다.  
그래서 확인 순서를 정해 두는 편이 좋습니다.

### 1. 프로세스가 살아 있는가

```bash
pgrep -af "python3 bot.py"
```

아무 것도 안 나오면, 답을 안 하는 문제가 아니라 **애초에 실행이 안 된 것**일 수 있습니다.

### 2. 로그에 뭐가 남았는가

```bash
tail -50 ~/MiniHerGemma_bot/logs/bot.log
```

처음엔 코드보다 로그가 더 친절합니다.  
토큰 문제인지, API 호출 문제인지, 시작 직후 죽었는지 방향을 먼저 보여주기 때문입니다.

### 3. `.env`와 `config.json`이 맞는가

이 두 파일만 틀려도 겉보기 증상은 비슷하게 보일 수 있습니다.

- 토큰이 비어 있음
- API 키가 잘못됨
- 모델 이름이 맞지 않음
- 엔드포인트가 다름

그러니 초보자일수록 "코드가 이상한가?"보다  
`설정 파일이 먼저 맞는가`를 먼저 보는 편이 낫습니다.

## 이런 오류는 어떻게 읽으면 좋을까

원문에서 실무적으로 좋았던 부분이 오류 코드를 함께 적어 둔 점입니다.

| 상태 코드 | 뜻 | 먼저 할 일 |
| --- | --- | --- |
| `401` | 인증 실패 | API 키 다시 확인 |
| `403` | 권한 없음 | 해당 키 권한 확인 |
| `429` | 요청 제한 | 잠시 기다렸다 재시도 |
| `500` | 서버 오류 | 잠시 후 다시 시도 |

특히 `429`는 초보자가 당황하기 쉬운 오류입니다.  
코드가 완전히 잘못된 것이 아니라, 너무 짧은 시간 안에 요청이 몰렸을 수도 있기 때문입니다.

이럴 때는 먼저

- 잠시 기다리고
- 너무 빠르게 연속 메시지를 보내지 말고
- 대시보드에서 할당량을 보는 편이 맞습니다.

## 처음에는 여기까지만 되면 충분하다

모든 기능을 한 번에 붙일 필요는 없습니다.  
처음 한 번은 아래만 되면 성공으로 봐도 됩니다.

1. 폴더가 분리되어 있다.
2. `.env`와 `config.json`이 읽힌다.
3. `python3 bot.py` 또는 `./run.sh`로 실행된다.
4. 텔레그램에서 `/start`나 일반 메시지에 답한다.
5. `logs/bot.log`에서 상태를 확인할 수 있다.

이 다섯 개가 되면 그다음부터는

- 응답 말투 조정
- 모델 변경
- 백그라운드 실행
- 운영 자동화

같은 확장으로 가면 됩니다.
