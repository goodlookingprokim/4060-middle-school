# 2026년 5월 23일(토) AI에게 소스코드 폴더를 통째로 던지지 말아야 하는 이유, 그리고 CodeGraph

AI 코딩 도구를 쓰다 보면 한 번쯤은 이런 식으로 말하게 됩니다.

- 이 프로젝트 전체 분석해줘
- 이 폴더 다 보고 리팩토링해줘
- 구조를 파악해서 어디가 문제인지 알려줘

겉으로 보기엔 시원한 요청입니다.
그런데 실무에서는 이 방식이 생각보다 비쌉니다.
토큰이 많이 들고, 시간이 오래 걸리고, AI도 자꾸 같은 파일을 다시 열어봅니다.

쉽게 말하면,
지도 없이 큰 창고 안으로 사람을 들여보낸 뒤
"알아서 필요한 부품 찾아서 조립해줘"라고 말하는 것과 비슷합니다.

그래서 요즘 더 흥미롭게 보이는 도구가 있습니다.
바로 <strong>CodeGraph</strong>입니다.

## 먼저 아주 쉽게 말하면

> CodeGraph는 AI에게 소스코드 뭉치를 던지는 대신, 코드 사이의 연결 관계를 미리 그려 둔 지도를 쥐여주는 방식에 가깝습니다.

이 감각 하나만 먼저 잡아도,
왜 이 도구가 실무에서 반가운지 금방 이해됩니다.

## 1. 왜 "폴더 통째로"가 문제일까

원래 방식은 이렇습니다.

- AI가 파일 목록을 훑고
- grep으로 찾고
- 비슷한 파일을 열어보고
- 다시 다른 파일로 넘어가고
- 관계를 머릿속에서 하나씩 이어 붙입니다

이 과정은 사람이 봐도 번거롭고,
AI에게도 똑같이 비용이 듭니다.

특히 큰 프로젝트에서는 아래 문제가 금방 커집니다.

- 같은 파일을 다시 읽는다
- 호출 관계를 찾느라 검색을 많이 한다
- 어디가 핵심 파일인지 파악하는 데 시간이 걸린다
- 정작 중요한 작업 전에 토큰을 많이 써버린다

### 공급망 비유로 바꾸면

예전 방식은 이런 느낌입니다.

> 공장 창고에 부품 상자를 전부 쏟아 놓고, "알아서 필요한 것 찾아서 조립해"라고 하는 것

반면 CodeGraph 방식은 이렇습니다.

> 부품 목록표와 연결 다이어그램을 먼저 보여주고, "이 부분만 고치면 돼"라고 말하는 것

이 차이는 꽤 큽니다.
AI가 덜 헤매고,
토큰도 덜 쓰고,
사람도 결과를 더 빨리 받게 됩니다.

## 2. CodeGraph는 실제로 무엇을 하나

CodeGraph는 GitHub의 `colbymchenry/codegraph` 프로젝트로 공개된 오픈소스 도구입니다.

참고 저장소:
- <https://github.com/colbymchenry/codegraph>

이 도구가 하는 핵심 일은 아래와 같습니다.

- 소스코드를 tree-sitter로 파싱한다
- 함수, 클래스, 변수 같은 요소를 뽑아낸다
- 호출, 상속, import 관계를 선으로 연결한다
- 그 구조를 SQLite 기반 로컬 데이터베이스에 저장한다
- MCP 방식으로 Claude Code, Codex, Cursor, OpenCode, Hermes Agent 같은 도구에서 불러 쓸 수 있게 한다

즉,
단순 검색기가 아니라 <strong>코드 사이 관계를 미리 정리해 둔 지도</strong>에 가깝습니다.

게다가 공식 저장소 설명 기준으로,
<strong>100% 로컬</strong>로 동작하고,
외부 서비스로 코드를 내보내지 않는 흐름을 강조합니다.

## 3. 실제로 얼마나 차이가 나나

공식 저장소에는 7개 오픈소스 프로젝트를 기준으로 한 비교 수치가 함께 나와 있습니다.
요약하면 이렇습니다.

- 평균 비용 35% 절감
- 평균 토큰 59% 절감
- 평균 시간 49% 단축
- 평균 tool call 70% 감소

프로젝트별로 차이는 있지만,
특히 코드베이스가 커질수록 격차가 더 커진다는 설명이 붙어 있습니다.

예를 들어 저장소 설명에는 VS Code 같은 큰 코드베이스에서
도구 호출 수와 토큰 사용량이 크게 줄었다는 비교가 함께 나옵니다.

이 수치는 "무조건 다 반 토막 난다"는 약속처럼 볼 필요는 없지만,
적어도 방향은 분명합니다.

> AI가 코드를 이해하는 데 쓰는 탐색 비용을 줄여준다.

바로 이 점이 실무에서 제일 중요합니다.

## 4. 설치는 생각보다 어렵지 않다

CodeGraph의 장점 중 하나는 설치가 생각보다 가볍다는 점입니다.
공식 저장소 안내 기준으로, Node.js가 없어도 설치할 수 있는 경로가 있습니다.

### macOS / Linux
```bash
curl -fsSL https://raw.githubusercontent.com/colbymchenry/codegraph/main/install.sh | sh
```

### Windows PowerShell
```powershell
irm https://raw.githubusercontent.com/colbymchenry/codegraph/main/install.ps1 | iex
```

### Node.js가 이미 있다면
```bash
npx @colbymchenry/codegraph
```

공식 저장소 설명에 따르면 설치 과정에서 아래 같은 흐름을 도와줍니다.

- 어떤 AI 에이전트를 쓰는지 감지
- Claude Code, Cursor, Codex CLI, OpenCode, Hermes Agent용 MCP 설정
- 권한 설정 보조
- 지시 파일(CLAUDE.md, rules 파일 등) 작성 보조

설치 뒤에는 사용 중인 AI 도구를 한 번 재시작하는 편이 안전합니다.

## 5. 프로젝트 안에서는 어떻게 시작하나

프로젝트 폴더 안에서 아래처럼 시작합니다.

```bash
cd /path/to/your-project
codegraph init -i
```

그러면 `.codegraph/` 폴더와 인덱스가 만들어집니다.

이 감각을 쉽게 말하면 이렇습니다.

- 아직은 AI가 미로에 들어가 있는 상태
- `codegraph init -i`를 하면 미리 지도부터 그려 두는 상태

공식 설명에는 파일 변경을 자동으로 반영하는 감시 흐름과,
`.gitignore`를 존중해 불필요한 폴더를 자동으로 빼는 방식도 함께 소개되어 있습니다.

즉,
처음 한 번만 해두면 이후엔 생각보다 손이 덜 갑니다.

## 6. 진짜 중요한 건 AI에게 어떻게 말하느냐다

설치만 하고 끝내면 효과를 다 못 봅니다.
실무에서는 AI에게 <strong>CodeGraph를 먼저 쓰라</strong>고 분명히 알려줘야 합니다.

예를 들어 이런 차이가 있습니다.

### 아쉬운 방식
```text
이 프로젝트 전체 분석해서 user authentication 리팩토링해줘
```

### 더 나은 방식
```text
이 프로젝트는 CodeGraph가 초기화되어 있습니다 (.codegraph/ 존재).
user authentication 관련 symbol을 먼저 찾고,
CodeGraph 도구를 우선 사용해서 관련 소스와 관계 맵을 파악한 뒤 리팩토링 계획을 세워주세요.
```

핵심은 이것입니다.

- 전체를 막연하게 읽으라고 하지 않는다
- 관련 심볼과 관계를 먼저 찾게 한다
- 검색보다 그래프 탐색을 우선하게 만든다

이렇게 해야 AI가 괜히 탐색 비용을 많이 쓰지 않습니다.

## 7. 실무에서 자주 떠올릴 수 있는 장면

### 1) 대형 리팩토링
```text
payment module을 새 라이브러리로 바꾸고 싶다.
먼저 영향 범위를 분석하고,
어디를 먼저 건드려야 하는지 정리해줘.
```

### 2) 버그 수정
```text
login 함수에서 500 에러가 난다.
호출 체인을 먼저 따라가서 어디서 깨지는지 보여줘.
```

### 3) 신규 기능 추가
```text
새 API endpoint를 추가할 건데,
기존 auth middleware와 어떤 식으로 연결되는지 관련 코드만 먼저 모아줘.
```

이럴 때 중요한 건,
AI가 무작정 폴더를 훑기 전에 <strong>관련 맥락만 빠르게 모으게 하는 것</strong>입니다.

## 8. 주의할 점도 있다

좋은 도구지만, 몇 가지는 미리 알아두는 편이 좋습니다.

- 여러 언어가 섞인 프로젝트도 가능하지만, 처음엔 작은 프로젝트로 감을 잡는 편이 좋다
- 큰 파일은 자동으로 스킵될 수 있다
- monorepo는 서브프로젝트별로 따로 초기화하는 편이 안정적이다
- 동시에 여러 에이전트가 건드리면 잠금 이슈가 생길 수도 있다
- 파일 구조가 크게 바뀌면 재인덱싱이 필요할 수 있다

그리고 가장 흔한 오해는 이것입니다.

> 작은 프로젝트에는 굳이 필요 없지 않을까?

오히려 작은 프로젝트는 초기화 비용이 거의 부담이 없어서,
효과를 시험해보기 더 좋을 수 있습니다.

## 9. 이게 왜 실무에서 진짜 가치가 있나

CodeGraph의 진짜 가치는 "신기하다"에 있지 않습니다.
실무에서는 아래가 더 크게 느껴집니다.

- 토큰 비용이 줄어든다
- AI가 코드 구조를 이해하는 시간이 줄어든다
- 잘못 짚은 리팩토링이 줄어든다
- 팀이 같은 코드 지도를 공유할 수 있다

결국 이 도구는 코딩을 대신해주는 마법이라기보다,
<strong>AI가 헤매는 시간을 줄여주는 정리된 작업 환경</strong>에 가깝습니다.

이 차이가 쌓이면,
사람도 덜 피곤하고 AI도 덜 돌아갑니다.

## 한 번 더 짧게 정리하면

- 폴더 통째로 던지는 방식은 토큰과 시간을 많이 쓴다
- CodeGraph는 함수, 클래스, 호출 관계를 미리 인덱싱한 코드 지도에 가깝다
- 설치와 초기화는 생각보다 간단하다
- 효과를 보려면 AI에게 CodeGraph를 우선 쓰라고 분명히 알려줘야 한다
- 리팩토링, 버그 수정, 신규 기능 추가에서 특히 유용하다

즉,
<strong>AI를 더 똑똑하게 만드는 도구라기보다, AI가 덜 헤매게 만드는 도구</strong>라고 보면 가장 이해가 쉽습니다.

## 마무리

코드 폴더를 통째로 던져주는 방식은 얼핏 편해 보이지만,
실제로는 AI를 계속 창고 안에서 헤매게 만드는 경우가 많습니다.

반대로 CodeGraph를 붙이면,
AI는 필요한 길을 조금 더 빨리 찾게 됩니다.

처음부터 거대한 레포에 겁먹지 않아도 됩니다.
작은 프로젝트 하나에서 먼저 `codegraph init -i`를 해보고,
그 다음 AI에게 "이 프로젝트는 CodeGraph가 초기화되어 있다"고 알려주는 것부터 시작해보면 됩니다.

그 한 번만 해봐도,
아마 금방 이런 느낌이 올 겁니다.

> 아, 이제 AI가 진짜 코드를 좀 이해하면서 들어오는 것 같네.
