# 실시간 퀴즈, 투표, 채팅은 어떻게 만들어질까

실시간 퀴즈, 실시간 투표, 실시간 채팅 같은 것을 만들고 싶은데 `웹소켓`이라는 단어에서 자꾸 멈추는 분들이 있습니다. 이 글은 잘생김프로쌤이 정리한 원고를 바탕으로, 원래 설명의 힘은 살리되 4060미들스쿨 블로그 형식에 맞게 다듬어 올린 글입니다.

코드를 조금 돌려봤지만 왜 되는지 설명하기 어렵거나, 누군가에게 이 구조를 쉽게 가르쳐야 하는 분들에게 특히 잘 맞습니다. 낯선 개념이 나와도 자판기, 전화기, 학교 방송, 냉장고 포스트잇 같은 이미 아는 장면부터 시작하도록 짜여 있어서, 실시간 서비스가 어디서부터 헷갈리는지 차분히 풀어 갑니다.

## 먼저 결론

- 실시간 서비스의 핵심은 웹소켓 하나가 아니라 **무엇을 저장하고, 무엇을 알리고, 무엇을 복원할지 나누는 일**입니다.
- HTTP와 WebSocket은 둘 중 하나를 고르는 관계가 아니라, 은행의 번호표와 전광판처럼 **역할을 나눠 함께 쓰는 관계**에 가깝습니다.
- 실제로 자주 터지는 문제는 연결 그 자체보다 **상태 저장, 중복 처리, 재연결, 시간 동기화**에서 많이 생깁니다.

# 실시간은 어떻게 만들어지는가

## 초보 개발자를 위한 실시간 서비스 구현 가이드북

> **누구를 위한 책인가**
> 실시간 퀴즈, 실시간 투표, 실시간 채팅 같은 걸 만들고 싶은데
> "웹소켓"이라는 단어 앞에서 멈춰 선 사람.
> 코드는 어떻게든 돌려봤지만 왜 되는지, 왜 안 되는지 설명하지 못하는 사람.
> 그리고 그런 사람에게 이걸 가르쳐야 하는 사람.

---

## 이 책을 읽는 법

이 책에는 규칙이 하나 있습니다.

**낯선 개념이 나오면, 반드시 여러분이 이미 아는 것으로 먼저 설명합니다.**

자판기, 전화, 학교 방송, 냉장고 포스트잇, 등기우편, 놀이공원 대기 표지판 —
여기 나오는 비유 20개는 전부 여러분이 이미 100% 이해하고 있는 것들입니다.
그 위에 기술 용어를 하나씩 얹습니다.

그래서 이 책을 다 읽고 나면, 여러분은 두 가지를 얻게 됩니다.

1. 실시간 서비스를 **만들 수 있게** 됩니다.
2. 실시간 서비스를 **누군가에게 설명할 수 있게** 됩니다.

두 번째가 더 중요합니다. 설명하지 못하는 건, 아직 이해한 게 아니니까요.

참고로, 이 책은 장(部)마다 제일 큰 제목(H1)을 다시 쓰는 구조를 의도적으로 사용합니다. 장 구분을 위한 형식이니 오타가 아닙니다.

# 프롤로그 — 정 선생님의 월요일

정 선생님은 고등학교 정보 교사입니다.

지난주에 AI 도구로 퀴즈 웹사이트를 하나 만들었습니다. 코드는 거의 몰랐지만
설명을 잘 써 주니 화면이 나왔고, 문제도 나왔고, 답도 저장됐습니다.
"오, 되네?" 그 기분으로 월요일 1교시에 학생 28명 앞에 섰습니다.

그리고 무너졌습니다.

- 선생님이 **[문제 시작]** 버튼을 눌렀는데, 학생 화면은 그대로였습니다.
- "새로고침 해 봐"라고 했더니 몇 명은 문제가 떴고, 몇 명은 안 떴습니다.
- 남은 시간이 어떤 학생은 28초, 어떤 학생은 31초였습니다.
- 뒷자리 학생이 손을 들었습니다. "선생님, 저 답 두 번 들어갔는데요?"
- 와이파이가 끊겼다 붙은 학생은 화면이 하얗게 비었습니다.

수업이 끝나고 정 선생님은 AI에게 물었습니다.
*"실시간으로 안 바뀌어요."*
AI가 답했습니다. *"WebSocket을 사용하세요."*

정 선생님은 그 단어를 검색했습니다. 그리고 이런 문장을 만났습니다.

> "WebSocket은 단일 TCP 연결 위에서 전이중(full-duplex) 양방향 통신을 제공하는 프로토콜이다."

정 선생님은 노트북을 덮었습니다.

**이 책은 그 덮은 노트북을 다시 여는 이야기입니다.**

그리고 결론부터 말하면, 정 선생님이 겪은 다섯 가지 사고는
전부 **"웹소켓을 안 써서" 생긴 게 아닙니다.**
정확히는 **"어떤 일을 어느 방식에 맡길지 나누지 않아서"** 생긴 일입니다.

이 문장이 이 책 전체의 뼈대입니다. 밑줄 그어 두세요.

# 1부 — 두 가지 대화 방식

## 1장. 자판기와 전화기

### 사례 ① 자판기 — 요청하고, 받고, 끝

자판기 앞에 섰습니다. 여러분은 이렇게 합니다.

1. 동전을 넣는다 (**요청**)
2. 버튼을 누른다 (**요청 내용**)
3. 음료가 나온다 (**응답**)
4. **대화 끝.**

여기서 중요한 건 4번입니다. 음료를 받는 순간, 자판기와 여러분의 관계는 **끝납니다.**
자판기는 여러분이 누구였는지 기억하지 않습니다.
여러분이 자리를 뜬 뒤에 자판기가 "저기요, 신제품 나왔어요!"라고 부르지 않습니다.
자판기는 **여러분이 말을 걸어야만 반응하는 기계**입니다.

이게 **HTTP**입니다.

> **HTTP** = 브라우저가 요청하고, 서버가 응답하고, 한 번의 통신이 마무리되는 방식.

웹의 거의 모든 것이 이렇게 동작합니다. 페이지 열기, 로그인, 검색, 결제, 글쓰기.
전부 "내가 요청 → 서버가 응답 → 끝"입니다.

### 사례 ② 전화 통화 — 연결을 붙잡고 있기

이번엔 친구와 통화 중입니다.

1. 전화를 건다 (**연결**)
2. 상대가 받는다 (**연결 성립**)
3. 이제부터 **둘 다 아무 때나 말할 수 있다.**
4. 끊기 전까지 그 상태가 **유지된다.**

3번이 핵심입니다. 통화 중에는 상대가 먼저 말을 걸 수 있습니다.
내가 질문하지 않아도 "야, 지금 밖에 비 온다"라고 알려 줄 수 있습니다.
회선이 **열려 있기 때문**입니다.

이게 **WebSocket**입니다.

> **WebSocket** = 한 번 연결한 뒤 그 연결을 유지하면서,
> 서버와 브라우저가 양방향으로 메시지를 주고받는 방식.

### 두 그림을 나란히

```text
[HTTP = 자판기]
브라우저 ──── 요청 ────▶ 서버
브라우저 ◀─── 응답 ───── 서버
 (연결 종료. 끝.)

[WebSocket = 전화 통화]
브라우저 ◀━━━ 연결 유지 ━━━▶ 서버
 (양쪽 다 아무 때나 말할 수 있음)
```

### 여기서 딱 하나만 기억한다면

**HTTP는 "물어봐야 대답한다". WebSocket은 "안 물어봐도 알려준다".**

정 선생님의 첫 번째 사고 — 버튼을 눌렀는데 학생 화면이 안 바뀐 것 —
는 바로 이 차이 때문입니다. 학생 브라우저는 자판기 앞에 서 있었습니다.
아무도 동전을 넣지 않았으니, 아무것도 나오지 않았죠.

## 2장. 우편함과 초인종

"근데요. HTTP로도 실시간처럼 만들 수 있지 않나요? 1초마다 계속 물어보면 되잖아요."

좋은 질문입니다. 실제로 많은 사람이 이렇게 시작합니다. 그리고 실제로 **어느 정도는 됩니다.**
왜 그게 좋은 방법이 아닌지, 비유로 봅시다.

### 사례 ③ 우편함 확인 vs 초인종

**A씨의 방법 (폴링, Polling)**
택배가 언제 올지 몰라서, 30초마다 현관에 나가 우편함을 확인합니다.
하루에 2,880번 나갑니다. 대부분은 빈 우편함입니다.
- 택배가 도착해도 **최대 30초 늦게** 압니다.
- 확인 간격을 1초로 줄이면? 더 빨리 알지만, 하루에 86,400번 나가야 합니다.
- 다리가 아픕니다. (= 서버 부하)

**B씨의 방법 (푸시, Push)**
초인종을 답니다. 택배가 오면 **택배기사가 벨을 누릅니다.**
- 도착하는 **즉시** 압니다.
- B씨는 아무것도 안 해도 됩니다.
- 벨이 안 울리면 안 온 겁니다. 확인할 필요조차 없습니다.

WebSocket이 초인종입니다.

이게 왜 중요하냐면, 여러분이 만들 서비스는 대개 **A씨 한 명이 아니라 학생 28명**이기 때문입니다.
28명이 각자 1초마다 서버를 두드리면, 서버는 1초에 28번 얻어맞습니다.
아무 일도 없는데도요. 300명이면 300번입니다.

> **핵심**: 실시간이 필요한 이유는 "빠르게"가 아니라
> **"여러 사람 화면에 같은 변화를 거의 동시에 보여 주기 위해서"** 입니다.

## 3장. 그런데 왜 둘 다 쓰나요?

여기서 대부분의 초보자가 함정에 빠집니다.

> ❌ "웹소켓이 더 좋은 거네? 그럼 전부 웹소켓으로 만들자!"

**아닙니다.** 그리고 이건 이 책에서 가장 중요한 교정입니다.

### 사례 ④ 은행 창구 — 번호표와 전광판

은행에 갔습니다. 두 가지 일이 벌어집니다.

**첫째, 번호표를 뽑습니다.**
- 내가 기계 앞에 가서 버튼을 누릅니다.
- 종이가 나옵니다. "37번".
- 이 종이는 **확실히 내 손에 쥐어져야** 합니다.
- 안 나오면 다시 누릅니다. **성공했는지 실패했는지 분명해야** 합니다.

→ 이건 **HTTP**의 일입니다.

**둘째, 전광판에 번호가 바뀝니다.**
- 나는 아무것도 안 했는데 "35번 → 36번"으로 바뀝니다.
- **대기실의 모든 사람에게 동시에** 보입니다.
- 은행이 먼저 알려 주는 정보입니다.

→ 이건 **WebSocket**의 일입니다.

은행은 둘 중 하나를 고르지 않았습니다. **역할을 나눴습니다.**
번호표를 전광판으로 발급하지 않고, 전광판을 번호표 기계로 만들지 않았습니다.

### 실시간 퀴즈에 그대로 대입하면

| 기능 | 권장 방식 | 왜 그런가 (은행 비유) |
|---|---|---|
| 퀴즈방 입장 | **HTTP** | 번호표 — 됐는지 안 됐는지 분명해야 함 |
| 학생 정보 등록 | **HTTP** | 번호표 — 저장 성공을 확인해야 함 |
| 문제 시작 알림 | **WebSocket** | 전광판 — 서버가 먼저 모두에게 |
| 남은 시간 동기화 | **WebSocket** (또는 서버 종료 시각 전달) | 전광판 — 기준을 서버가 쥠 |
| 정답 공개 | **WebSocket** | 전광판 — 동시에 보여야 함 |
| 순위 갱신 | **WebSocket** | 전광판 — 계속 바뀜 |
| 답안 저장 | **HTTP** 또는 *저장 확인 응답이 있는* WebSocket | 번호표 — 저장됐는지 알아야 함 |
| 최종 결과 조회 | **HTTP** | 번호표 — 내가 필요할 때 요청 |
| 새로고침 후 상태 복원 | **HTTP로 조회 → WebSocket 재연결** | 창구에 다시 물어보고, 전광판 다시 봄 |

> ⚠️ **모든 기능을 WebSocket으로 만들 필요는 없습니다.**
> 저장 성공 여부가 중요한 작업은 HTTP가 더 단순하고 안정적인 경우가 많습니다.

### 왜 저장은 HTTP가 편한가

HTTP는 요청 하나에 응답 하나가 **짝을 이룹니다.**
`200 OK`가 오면 성공, `500`이 오면 실패. 브라우저가 이걸 알아서 챙겨 줍니다.

WebSocket은 그냥 **메시지를 던지는** 방식입니다.
던진 메시지가 처리됐는지, 저장됐는지는 **프로토콜이 알려 주지 않습니다.**
알고 싶으면 여러분이 직접 "저장 완료" 메시지를 만들어서 돌려보내도록 설계해야 합니다.
(이걸 **ACK**라고 부릅니다. 3부에서 자세히 봅니다.)

즉 —

> **"보냈다"와 "저장됐다"는 다른 말입니다.**
> HTTP는 이 둘을 기본으로 묶어 주고, WebSocket은 묶어 주지 않습니다.

## 4장. 동시에 시작한다는 것

### 사례 ⑤ 운동회 출발 신호

100m 달리기. 선수 8명이 출발선에 섰습니다.

심판이 각 선수에게 다가가서 "너 출발", "너 출발", "너 출발" 하고 개별로 말한다면?
먼저 들은 선수가 먼저 뜁니다. **경기가 성립하지 않습니다.**

그래서 심판은 **총 한 방**을 쏩니다.
소리는 8명에게 사실상 동시에 도착합니다. 한 번의 신호, 여러 명의 수신.

실시간 퀴즈의 [문제 시작] 버튼이 정확히 이 총소리입니다.
교사가 한 번 누르면, 28명 화면이 거의 동시에 바뀌어야 합니다.

이게 **브로드캐스트(broadcast)** 이고, 2부에서 배울 **Group**의 존재 이유입니다.

### 문제 하나가 시작될 때 — 실제 흐름

```text
① 교사가 [문제 시작] 버튼 클릭
 ↓ (HTTP 또는 WebSocket 메시지)
② 서버가 "현재 문제 번호 = 3, 종료 시각 = 10:15:30" 을 저장 ← 상태 저장
 ↓
③ 서버가 WebSocket으로 학생들에게 "문제 시작" 이벤트 전송 ← 총소리
 ↓
④ 학생 화면이 거의 동시에 갱신
```

②번을 절대 건너뛰지 마세요.
③번만 하면 그 순간 접속 중인 학생에게만 전달됩니다.
화장실 갔다 온 학생, 와이파이가 끊겼던 학생은 **영원히 그 문제를 못 봅니다.**
②번이 있어야 나중에 들어온 학생도 "지금 3번 문제 풀고 있구나"를 알 수 있습니다.

**총소리는 지나가면 사라집니다. 그래서 칠판에도 적어 둬야 합니다.**
이 문장이 2부 전체의 예고편입니다.

---

## 5장. 사라지는 것과 남는 것

### 사례 ⑥ 택배 문자 vs 배송 조회 페이지

여러분 휴대폰에 이런 문자가 옵니다.
> "[택배] 상품이 배송 출발했습니다."

이게 **이벤트(Event)** 입니다. 그 순간 한 번 울리고 지나갑니다.

그런데 문자를 못 봤다면? 알림을 껐다면? 폰이 꺼져 있었다면?
그래도 괜찮습니다. **배송 조회 페이지**에 들어가면 됩니다.
거기엔 "현재 상태: 배송 중"이라고 적혀 있습니다.

이게 **상태(State)** 입니다. 물어보면 언제든 알려 주는, 남아 있는 정보입니다.

| | 이벤트 (Event) | 상태 (State) |
|---|---|---|
| 비유 | 택배 문자 알림 | 배송 조회 페이지 |
| 성격 | 그 순간 지나감 | 계속 남아 있음 |
| 놓치면 | 다시 못 봄 | 다시 물어보면 됨 |
| 담당 | WebSocket / Channel Layer | 서버 + DB |
| 퀴즈 예시 | "문제가 시작됨", "정답이 공개됨" | 현재 문제 번호, 종료 시각, 제출 여부 |

> ⭐ **상태는 서버가 관리하고, 이벤트는 WebSocket을 통해 전달합니다.**
> 그리고 **이벤트를 보냈다는 사실만으로 저장이 보장되지는 않습니다.**

정 선생님의 다섯 가지 사고 중 세 개(새로고침하면 화면이 빔, 남은 시간이 제각각,
답이 두 번 저장됨)가 전부 이 구분을 안 해서 생긴 일이었습니다.

## 1부 정리 — 한 문장씩

1. HTTP는 자판기다. 물어봐야 대답한다.
2. WebSocket은 전화다. 안 물어봐도 알려준다.
3. 1초마다 물어보는 건 우편함에 계속 나가는 것과 같다. 초인종을 달자.
4. 하지만 은행은 번호표와 전광판을 **둘 다** 쓴다. 역할을 나눠라.
5. 저장이 중요한 일은 HTTP, 동시에 알려야 하는 일은 WebSocket.
6. 총소리(이벤트)는 지나가고, 칠판(상태)은 남는다. **둘 다 필요하다.**

> **⭐ HTTP는 요청과 저장에 강하고, WebSocket은 실시간 전달에 강합니다.**

이제 정 선생님은 "무엇을 어디에 맡길지"를 알게 됐습니다.
다음 질문은 이겁니다. **"그래서 서버 안에서는 대체 무슨 일이 벌어지는데?"**

# 2부 — 서버라는 학교

정 선생님이 두 번째 벽을 만난 지점입니다.
"HTTP랑 WebSocket을 나눠 쓰라는 건 알겠어요. 근데 **서버 안**은요?
Redis는 뭐고 Channel Layer는 뭐예요? DB랑 뭐가 다른데요?"

이 장은 그 답입니다. 그리고 답은 여러분이 매일 출근하는 곳에 있습니다.

## 6장. 학교로 통째로 바꿔 보기

### 사례 ⑦ 학교 조직도 = 실시간 서비스 전체 구조

실시간 퀴즈 서버를 학교라고 생각해 봅시다.

| 실시간 서비스 | 학교로 치면 | 하는 일 |
|---|---|---|
| **브라우저** | 교실에 앉은 사람 | 화면을 보고, 버튼을 누름 |
| **앱 서버 / Consumer** | 교무실의 담당 선생님 | 요청을 받고, 판단하고, 기록하고, 방송을 부탁함 |
| **Group** | "2학년 3반"이라는 이름 | 누구에게 방송할지 정하는 **묶음의 이름** |
| **Channel Layer** | 교내 방송 시스템 | 교무실의 말을 여러 교실 스피커로 배달 |
| **Redis** | 방송 시스템의 배선·중계 장비 | 방송이 여러 건물까지 닿게 해 주는 설비 |
| **DB** | 학생부 서류함 | 나중에도 남아야 하는 기록을 보관 |
| **상태 관리** | 칠판에 적힌 "현재 3교시, 수학" | 지금 어느 단계인지에 대한 기준 |

이 표 하나가 2부의 전부입니다. 나머지는 이 표를 자세히 뜯어보는 것뿐입니다.

### 전체 그림

```text
교사 브라우저 ◀━ WebSocket ━▶ ┌───────────────┐
학생 브라우저 ◀━ WebSocket ━▶ │   앱 서버     │ ◀━▶ Channel Layer ◀━▶ Redis
학생 브라우저 ◀━ WebSocket ━▶ │  / Consumer   │      (방송 배선)     (중계 장비)
학생 브라우저 ◀━ WebSocket ━▶ └──────┬────────┘
                                     │
                                     ▼
                              ┌─────────────┐
                              │     DB      │ ← 문제, 답안, 점수, 진행 상태
                              └─────────────┘
```

> ⚠️ **가장 흔한 오해**:
> 교사 브라우저와 학생 브라우저가 **서로 직접 연결되는 게 아닙니다.**
> 모든 대화는 반드시 서버를 거칩니다.
> 교사가 학생에게 직접 말하는 게 아니라, 교사가 교무실에 말하고, 교무실이 방송하는 겁니다.

---

## 7장. 교무실 — 앱 서버와 Consumer

### 사례 ⑧ 콜센터 상담원

전화를 걸면 상담원 한 명이 배정됩니다.
그 상담원은 **내 전화 한 통을 처음부터 끝까지 담당**합니다.
- 전화를 받고 (연결)
- 내 말을 듣고 (수신)
- 조회하고, 처리하고 (로직)
- 끊습니다 (종료)

WebSocket 연결 하나마다 이런 담당자가 붙습니다.
이 담당자가 **Consumer**입니다.

> **Consumer** = WebSocket 연결과 이벤트를 처리하는 서버 쪽 코드 단위.
> 연결(`connect`), 수신(`receive`), 종료(`disconnect`), 그리고 그룹 이벤트 처리를 담당합니다.
> (Django Channels에서 주로 쓰는 용어입니다.)

학생 28명이 접속하면 Consumer도 28개가 만들어집니다.
각자 자기 학생 한 명씩 담당하는 상담원 28명이라고 보면 정확합니다.

### 코드로 보면 (Django Channels 기준)

```python
# consumers.py
import json
from channels.generic.websocket import AsyncWebsocketConsumer

class QuizConsumer(AsyncWebsocketConsumer):

    async def connect(self):
        # ① 전화를 받는 순간
        self.quiz_id = self.scope["url_route"]["kwargs"]["quiz_id"]
        self.group_name = f"quiz_{self.quiz_id}" # 예: quiz_123

        # ② "2학년 3반 스피커 목록에 나를 넣어 주세요"
        await self.channel_layer.group_add(self.group_name, self.channel_name)
        await self.accept()

    async def disconnect(self, close_code):
        # ③ 전화가 끊기면 스피커 목록에서 빠짐
        await self.channel_layer.group_discard(self.group_name, self.channel_name)

    async def receive(self, text_data):
        # ④ 학생이 보낸 메시지 처리
        data = json.loads(text_data)
        ...

    async def question_started(self, event):
        # ⑤ 방송이 도착했을 때 → 내가 담당한 브라우저에게 전달
        await self.send(text_data=json.dumps(event["payload"]))

```

지금 이 코드를 다 이해할 필요 없습니다. 딱 세 줄만 보세요.

- `group_add` → **"방송 목록에 나를 등록"**
- `group_discard` → **"방송 목록에서 나를 제거"**
- `self.send` → **"내가 담당한 브라우저에게 전달"**

## 8장. 방송실 — Group과 Channel Layer

여기가 초보자가 가장 많이 헷갈리는 곳입니다. 천천히 갑니다.

### 사례 ⑨ 단톡방 = Group

여러분 폰에 단톡방이 있습니다. "2학년 3반 학부모방" 같은 거요.

단톡방은 **무엇인가요?**
- 메시지를 **누구에게 보낼지 정해 주는 이름표**입니다.
- 단톡방 자체가 서버는 아닙니다.
- 단톡방이 회원들의 주민번호나 성적을 저장하는 곳도 아닙니다.
- 그냥 **"이 이름을 부르면 이 사람들에게 간다"** 는 규칙입니다.

이게 **Group**입니다.

> **Group** = 같은 퀴즈방의 여러 연결을 하나로 묶어, 한 번에 이벤트를 보내기 위한 **논리적 묶음**.
> 실제 이름은 `quiz_123`, `quiz_room_3` 같은 문자열입니다.

> ⚠️ **주의 (아주 중요)**
> Group은 **학생 목록이나 점수를 저장하는 공간이 아닙니다.**
> 실제로 Django Channels의 Group은 **순수한 브로드캐스트 시스템**이라서,
> "지금 이 그룹에 누가 들어 있는지" 목록을 뽑아 볼 수조차 없습니다.
> 누가 참여 중인지 알아야 한다면, 그건 **여러분이 DB에 따로 기록**해야 합니다.

이 경고 하나가 초보자 프로젝트의 버그 절반을 막아 줍니다.
"Group에 넣었으니까 참가자 명단은 되겠지"라고 생각하는 순간 무너집니다.
단톡방을 만들었다고 출석부가 자동으로 생기지 않는 것과 같습니다.

### 사례 ⑩ 교내 방송 시스템 = Channel Layer

교무실에서 마이크를 잡고 "2학년 3반, 지금 강당으로 모이세요"라고 말합니다.
그 소리는 어떻게 3반 교실 스피커까지 갈까요?

**배선과 앰프**가 있기 때문입니다.
교무실의 마이크 → 앰프 → 각 교실 스피커.
이 중간 설비가 없으면 교무실에서 아무리 소리쳐도 3반은 못 듣습니다.

이게 **Channel Layer**입니다.

> **Channel Layer** = 여러 Consumer와 여러 서버 프로세스 사이에서 이벤트를 전달하는 **통신 계층**.
> 주요 동작: `group_add`(목록에 추가), `group_send`(그룹에 방송), `group_discard`(목록에서 제거).

### 왜 이런 게 따로 필요한가 — 결정적인 이유

여기서 진짜 이유를 말씀드립니다. 이걸 알면 Redis가 왜 필요한지도 저절로 풀립니다.

학생이 28명이면 Consumer(상담원)도 28명입니다.
그런데 **이 28명이 전부 같은 건물에 있는 게 아닙니다.**

서비스가 커지면 서버 프로세스를 여러 개 띄웁니다.
1번 서버에 학생 10명, 2번 서버에 학생 10명, 3번 서버에 교사와 학생 8명.
이제 교사가 1번 서버에 붙어 있다면 —

**1번 서버는 2번, 3번 서버에 있는 학생들의 존재를 모릅니다.**

교무실에서 아무리 소리를 질러도 옆 건물은 안 들립니다.
그래서 **건물 사이를 잇는 배선**이 필요합니다. 그게 Channel Layer이고,
그 배선을 실제로 깔아 주는 설비가 **Redis**입니다.

### 사례 ⑪ 냉장고 포스트잇 vs 가계부 = Redis vs DB

이제 마지막 혼동을 정리합시다. "Redis가 있으면 DB는 필요 없나요?"

**냉장고 문에 붙인 포스트잇**을 떠올려 보세요.
- "엄마, 저 학원 갔다 올게요"
- 빠르게 붙이고, 읽고, 떼어냅니다.
- 3년 뒤에 다시 볼 일은 없습니다.
- 이사 가면 사라집니다.

**가계부(또는 통장 거래내역)**는 다릅니다.
- 3년 뒤에도 남아 있어야 합니다.
- 사라지면 큰일 납니다.
- 검색하고, 합계 내고, 증빙으로 씁니다.

| | Redis (포스트잇) | DB (가계부) |
|---|---|---|
| 목적 | 이벤트를 빠르게 **전달** | 데이터를 안전하게 **보관** |
| 남는가 | 지나가면 그만 | 계속 남아야 함 |
| 퀴즈 예시 | "문제 시작" 방송 배달 | 학생 답안, 점수, 문제 내용 |

> ⭐ **답**: 아니요. Redis는 Channel Layer의 이벤트 전달을 도울 수 있고,
> DB는 문제·답안·점수·현재 진행 상태처럼 나중에도 남아야 하는 확정 데이터를 저장합니다.
> **역할이 다릅니다.**

> 📌 참고: Redis는 WebSocket이 아닙니다.
> WebSocket은 **브라우저와 서버 사이의 통신 방식**이고,
> Redis는 **서버 내부**에서 이벤트 전달이나 데이터 처리를 돕는 별도 시스템입니다.
> 이 둘을 섞어서 이해하면 구조 전체가 뒤엉킵니다.

## 9장. 칠판 — 상태 관리

### 사례 ⑫ 교실 칠판

교실에 늦게 들어온 학생이 가장 먼저 하는 일은 **칠판을 보는 것**입니다.
칠판에 "p.42 3번 문제, 5분 남음"이라고 적혀 있으면
선생님이 아까 뭐라고 말했는지 못 들었어도 따라갈 수 있습니다.

칠판이 없다면? 옆 사람에게 물어봐야 합니다. 옆 사람이 잘못 알고 있으면 같이 틀립니다.

**칠판 = 서버가 관리하는 상태(State)** 입니다.

### 서버가 반드시 들고 있어야 할 것들

| 상태 항목 | 왜 필요한가 |
|---|---|
| 현재 문제 번호 | 늦게 들어온 학생에게 알려 주려고 |
| 문제 시작 시각 | 시간 계산의 기준 |
| 문제 종료 시각 | **모두가 같은 시계를 보게 하려고** |
| 정답 공개 여부 | 미리 보면 안 되니까 |
| 학생 제출 여부 | 중복 제출을 막으려고 |
| 학생 점수 | 결과를 내려고 |

> ⚠️ **절대 하면 안 되는 것**: 현재 상태를 **각 브라우저 화면에만** 저장하기.
> 브라우저는 새로고침하면 기억을 잃습니다. 학생 28명이 각자 다른 기억을 갖게 됩니다.
> **브라우저는 화면일 뿐, 기준이 아닙니다.**

### 사례 ⑬ 엘리베이터 층 표시등

엘리베이터를 기다릴 때, 각자 자기 시계로 "지금쯤 5층일 거야"라고 추측하지 않습니다.
**표시등**을 봅니다. 표시등은 엘리베이터 본체가 알려 주는 값입니다.

지금 이 순간 표시등을 처음 본 사람도, 10분째 기다린 사람도 **같은 숫자**를 봅니다.
"언제부터 봤는지"와 무관하게 현재 상태를 알 수 있습니다.

실시간 서비스는 이 표시등을 만들어야 합니다.
그래야 새로 들어온 사람도, 끊겼다 돌아온 사람도 즉시 합류할 수 있습니다.

### 학생이 새로고침하면 벌어지는 일 — 6단계

정 선생님을 가장 괴롭혔던 사고를 이제 해부해 봅시다.

```text
① WebSocket 연결이 끊긴다 (전화가 끊김)
② 브라우저가 앱 서버에 다시 연결한다 (다시 전화를 검)
③ "지금 상황이 어떻게 되나요?" 요청 (HTTP 또는 연결 직후 메시지)
④ 앱 서버가 DB에서 현재 문제와
 종료 시각을 조회한다 (칠판을 읽음)
⑤ 학생 화면에 현재 상태를 복원한다 (칠판 내용을 화면에 그림)
⑥ 해당 퀴즈 Group에 다시 참여한다 (스피커 목록에 다시 등록)
```

> ⭐ **여기가 핵심입니다.**
> **"다시 연결하는 것"과 "현재 상태를 복원하는 것"은 서로 다른 작업입니다.**

②번만 하고 ③④⑤를 빼먹는 게 초보자의 90% 실수입니다.
전화는 다시 걸었는데, 아까 무슨 얘기 중이었는지는 안 물어본 겁니다.
그러면 화면은 하얗게 빈 채로, 다음 방송이 올 때까지 하염없이 기다리게 됩니다.

**교실에 다시 들어왔으면, 칠판을 봐야 합니다.**

## 10장. 처음 설계할 때 지켜야 할 8가지 원칙

2부의 모든 내용을 실무 규칙으로 압축하면 이렇습니다.
프로젝트를 시작하기 전에 이 목록을 소리 내어 읽으세요.

1. ✅ **교사와 학생 브라우저는 각각 서버에 연결한다.** (브라우저끼리 직접 연결하지 않는다)
2. ✅ **브라우저가 현재 상태를 기억하게 하지 않는다.** (기억은 서버의 일)
3. ✅ **새로고침해도 서버 상태로 다시 복원되게 만든다.**
4. ✅ **문제 진행 상태는 DB에 저장한다.** (Group이나 메모리에 두지 않는다)
5. ✅ **여러 학생에게 동시에 보낼 이벤트는 Group 단위로 생각한다.**
6. ✅ **Group을 학생 정보나 점수 저장 공간으로 쓰지 않는다.**
7. ✅ **Redis와 DB를 같은 저장소처럼 다루지 않는다.**
8. ✅ **각 브라우저가 자기 시계를 세지 않고, 서버 종료 시각을 기준으로 계산한다.**

## 2부 정리

> ⭐ **앱 서버가 상태와 저장을 관리하고,
> Group과 Channel Layer가 여러 연결에 실시간 이벤트를 전달하도록 돕습니다.**

교무실이 판단하고 기록하고, 방송 시스템이 배달합니다.

# 3부 — 말이 통해야 코드가 보인다

정 선생님이 세 번째로 막힌 지점은 의외로 단순했습니다.
**튜토리얼 문장을 못 읽는 것.**

> "ASGI 서버에서 Consumer가 Channel Layer를 통해 Group에 이벤트를 보내고,
> 클라이언트는 ACK를 받은 뒤 상태를 갱신한다."

한 문장에 낯선 단어가 다섯 개입니다.
하지만 이 다섯 개만 정확히 구분하면, 튜토리얼 대부분이 갑자기 읽힙니다.

**그리고 더 중요한 건 이겁니다.
용어를 구분하면, 문제가 생겼을 때 "어느 단계에서 막혔는지" 훨씬 빨리 찾을 수 있습니다.**

## 11장. 용어 8개, 하나씩

### ① WebSocket — 전화 통화

- **쉬운 설명**: 서버와 브라우저가 연결을 유지하며 양방향으로 메시지를 주고받는 통신 방식.
- **실제로 볼 때**: 문제 시작 이벤트, 정답 공개, 순위 갱신.
- **주소 형태**: `ws://`(암호화 없음) 또는 `wss://`(TLS 암호화). 배포 환경에서는 **`wss://`를 씁니다.**

### ② ASGI — 콘센트 규격

#### 사례 ⑭ 220V 콘센트

한국의 콘센트는 220V, 둥근 핀 2개입니다. 이건 **규격**입니다.
- 규격은 **발전소가 아닙니다.**
- 규격은 **전기 그 자체도 아닙니다.**
- 규격은 "이렇게 생긴 구멍에 이렇게 생긴 플러그를 꽂으면 전기가 흐른다"는 **약속**입니다.

이 약속이 있어서, LG 냉장고든 삼성 TV든 아무 벽에나 꽂으면 됩니다.

**ASGI가 이 콘센트 규격입니다.**

- **전체 이름**: Asynchronous Server Gateway Interface (비동기 서버 게이트웨이 인터페이스)
- **쉬운 설명**: 파이썬 웹 서버와 애플리케이션이 HTTP나 WebSocket 같은 연결을
 비동기 방식으로 처리할 수 있게 하는 **인터페이스 규격**.
- **왜 생겼나**: 기존 표준이던 WSGI는 "요청 하나 → 응답 하나"만 다룰 수 있어서,
 연결이 오래 유지되고 메시지가 여러 번 오가는 WebSocket을 처리할 수 없었습니다.
 그래서 ASGI가 그 뒤를 잇는 규격으로 만들어졌습니다.

> ⚠️ **주의**: ASGI 자체가 WebSocket 서버 프로그램을 뜻하는 것은 **아닙니다.**
> 규격이 곧 발전소는 아닙니다.
> 실제로 서버를 돌리는 건 Daphne, Uvicorn 같은 **ASGI 서버 프로그램**입니다.

이 구분을 못 하면 배포할 때 반드시 사고가 납니다. (4부에서 다시 만납니다.)

### ③ Consumer — 콜센터 상담원 (사례 ⑧ 재사용)

- **쉬운 설명**: WebSocket 연결과 이벤트를 처리하는 서버 쪽 코드 단위.
- **실제로 볼 때**: `connect`, `receive`, `disconnect`, 그룹 이벤트 처리 함수들.
- **주의**: Django Channels에서 주로 쓰는 용어입니다.
 다른 프레임워크에서는 handler, gateway 등 다른 이름을 씁니다.

### ④ Event — 학교 종소리

#### 사례 ⑮ 종소리

"딩동댕동." 그 순간 학교 전체가 같은 의미를 이해합니다. "쉬는 시간이다."
종소리는 **한 번 울리고 사라집니다.** 녹음해 두지 않으면 다시 들을 수 없습니다.

- **쉬운 설명**: 서버와 클라이언트 사이, 또는 서버 내부에서 전달하는 **하나의 의미 있는 메시지.**
- **실제로 볼 때**: `question_started`, `answer_saved`, `leaderboard_updated`

이벤트 이름은 **과거형 동사**로 짓는 게 좋습니다.
"~해라"가 아니라 "~가 일어났다"로요.
`start_question`(명령)보다 `question_started`(사실 통보)가 훨씬 안전합니다.
명령은 두 번 실행되면 사고가 나지만, 사실 통보는 두 번 들어도 사실이 바뀌지 않으니까요.

### ⑤ Group — 단톡방 (사례 ⑨ 재사용)

- **쉬운 설명**: 같은 퀴즈방의 여러 연결을 묶어 한 번에 이벤트를 보내기 위한 논리적 묶음.
- **실제로 볼 때**: `quiz_room_3`, `quiz_123` 같은 Group 이름.
- **주의**: Group은 학생 목록이나 점수를 영구 저장하는 공간이 **아닙니다.**

### ⑥ Channel Layer — 교내 방송 배선 (사례 ⑩ 재사용)

- **쉬운 설명**: 여러 Consumer와 서버 프로세스 사이에 이벤트를 전달하는 통신 계층.
- **실제로 볼 때**: `group_add`, `group_send`, `group_discard`
- **알아 둘 것**: Django Channels에서 운영 환경용으로 공식 지원하는 Channel Layer는
 **Redis를 백엔드로 쓰는 `channels_redis`** 입니다.
 개발용 인메모리(InMemory) 방식도 있지만, 서버가 하나일 때만 동작합니다.
 (건물이 하나뿐인 학교의 확성기라고 생각하세요. 건물이 늘어나면 안 들립니다.)

### ⑦ Reconnect — 터널을 지나간 뒤

#### 사례 ⑯ 터널에서 끊긴 통화

고속버스에서 통화 중에 터널에 들어갑니다. 뚝. 끊깁니다.
터널을 나오면 여러분은 두 가지를 합니다.

1. **다시 전화를 겁니다.** ← 재연결
2. **"어디까지 얘기했지?" 하고 묻습니다.** ← 상태 복원

2번을 빼먹는 사람은 없습니다. 사람이라면요.
그런데 코드는 시키지 않으면 안 합니다.

- **쉬운 설명**: WebSocket 연결이 끊긴 뒤 다시 연결하는 과정.
- **실제로 볼 때**: 와이파이 끊김 후 재접속, 화면 복귀 후 다시 연결, 배포로 서버 재시작.
- **주의**: 다시 연결한 뒤에는 **현재 상태를 서버에서 다시 받아야 합니다.**

### ⑧ ACK — 등기우편 수령 서명

#### 사례 ⑰ 등기우편

일반 우편은 **보내면 끝**입니다. 도착했는지 모릅니다.
등기우편은 **받는 사람이 서명**합니다. 그 서명이 발신자에게 돌아옵니다.
그제서야 "확실히 전달됐다"고 말할 수 있습니다.

- **전체 이름**: Acknowledgement (확인 응답)
- **쉬운 설명**: 서버가 메시지를 정상적으로 받았거나 처리했음을 알려 주기 위해
 **애플리케이션에서 설계하는 확인 응답.**
- **실제로 볼 때**: 답안 제출 후 `saved`, `success`, `accepted` 같은 응답.

> ⚠️ **가장 중요한 주의**:
> **WebSocket 프로토콜이 "답안 저장 ACK"를 자동으로 만들어 주지 않습니다.**
> 이건 순전히 여러분이 직접 설계해야 하는 규칙입니다.
>
> 웹소켓은 우체통까지만 책임집니다. 서명 용지는 여러분이 만들어 넣어야 합니다.

## 12장. 비슷해 보이지만 완전히 다른 다섯 가지

시험 문제로 낸다면 이 표에서 냅니다.

| 용어 | 정체 | 한 줄 비유 |
|---|---|---|
| **WebSocket** | 연결을 유지하는 **통신 방식** | 전화 회선 |
| **Event** | 연결이나 Channel Layer를 통해 전달되는 **개별 메시지** | 종소리 한 번 |
| **Group** | 여러 연결을 묶는 **논리적 단위** | 단톡방 이름 |
| **Channel Layer** | 서버 내부에서 이벤트를 전달하는 **계층** | 방송실 배선 |
| **ACK** | 처리됐음을 알리기 위해 **직접 설계하는 확인 응답** | 등기 수령 서명 |

> ⭐ 문제가 생겼을 때 **어느 단계에서 막혔는지 구분하는 것**이 중요합니다.
> 이 다섯 개를 구분하지 못하면, 4부의 디버깅은 시작조차 할 수 없습니다.

## 13장. 용어 연결 흐름 — 한 편의 이야기로

이제 용어들을 한 줄로 꿰어 봅시다. 실제 순서입니다.

```text
① 브라우저가 WebSocket 연결을 요청한다
 ↓
② ASGI 환경에서 Consumer가 그 연결을 처리한다
 ↓
③ Consumer가 해당 퀴즈 Group에 참여한다 (group_add)
 ↓
④ Channel Layer가 Group 전체에 이벤트를 전달한다 (group_send)
 ↓
⑤ Consumer가 WebSocket으로 브라우저에 이벤트를 전송한다 (send)
 ↓
⑥ 중요한 요청은 서버가 ACK 응답을 반환한다
 ↓
⑦ 연결이 끊기면 Reconnect 후 현재 상태를 복원한다
```

같은 이야기를 학교 말로 번역하면:

> 학생이 교실에 들어와서(①) 담당 선생님을 만나고(②)
> "2학년 3반" 명단에 이름을 올립니다(③).
> 교무실이 방송을 하면(④) 3반 스피커로 나오고(⑤),
> 중요한 제출물은 선생님이 "접수했다"고 확인해 줍니다(⑥).
> 조퇴했다 돌아온 학생은 다시 들어와서 칠판을 봅니다(⑦).

용어를 뭉뚱그리면 오류도 뭉뚱그려집니다.
"웹소켓이 안 돼요"는 진단이 아닙니다. **증상 호소**일 뿐입니다.

> ⭐ **에러 메시지보다 먼저 "어느 종류의 문제인지" 나누는 것이 중요합니다.**

## 15장. 여덟 가지 실전 고장과 처방

### 🔴 고장 1. 연결이 아예 안 됨

**증상**: 브라우저가 WebSocket 연결 자체를 만들지 못함.

**먼저 볼 곳**
- `ws` 또는 `wss` **주소**가 맞는지 (https 사이트에서 `ws://`를 쓰면 브라우저가 막습니다)
- WebSocket **라우팅** 설정
- **ASGI 애플리케이션**과 실행 서버가 제대로 연결됐는지

**진단법**: 브라우저 개발자도구 → Network 탭 → WS 필터.
연결 성공이면 상태 코드 **101**이 뜹니다. (`101 Switching Protocols` = "이제부터 웹소켓으로 말하자"는 뜻)
101이 안 보이면, 그 뒤 코드를 아무리 고쳐도 소용없습니다.

### 🟠 고장 2. 로컬에서는 되는데 배포하면 안 됨

#### 사례 ⑱ 리허설과 실제 공연장

학교 강당에서 리허설할 땐 완벽했습니다. 그런데 시민회관 본 무대에서 소리가 안 납니다.
왜죠? **강당엔 앰프가 하나였고, 시민회관은 무대·객석·로비 스피커가 따로 있었기 때문입니다.**
장비 구성이 다른데 같은 세팅을 들고 간 겁니다.

이게 배포 사고의 정체입니다.

**먼저 볼 곳**
- **ASGI 서버가 실제로 실행 중인지** (WSGI로만 띄워 놓고 웹소켓을 기대하는 경우가 매우 많습니다)
- 배포 시작 명령 (`gunicorn` 단독? `uvicorn`/`daphne`로 ASGI를 띄우고 있나?)
- 환경 변수
- **Redis 또는 Channel Layer 연결** (로컬은 인메모리, 서버는 여러 프로세스 → 방송 불통)
- 리버스 프록시(nginx 등)가 `Upgrade` 헤더를 넘겨 주는지

> 3부의 콘센트 비유를 기억하세요. **ASGI는 규격이고, 서버는 발전소입니다.**
> 규격만 맞춰 놓고 발전소를 안 켜면 불은 안 들어옵니다.

### 🟠 고장 3. 일부 학생만 메시지를 못 받음

**먼저 볼 곳**
- **Group 이름**이 정확히 같은지 (`quiz_123` vs `quiz-123`은 완전히 다른 방입니다)
- Group **참여 여부** (`group_add`를 정말 호출했는가)
- **Channel Layer** 설정
- **여러 서버 프로세스 간** 전달 구조

**가장 흔한 진범**: 서버 프로세스가 2개 이상인데 Channel Layer가 인메모리인 경우.
1번 건물 방송이 2번 건물에 안 들리는 겁니다. 이건 코드 버그가 아니라 **설비 문제**입니다.

### 🟢 고장 4. 새로고침하면 상태가 사라짐

**먼저 볼 곳**
- 서버가 **상태를 저장**하고 있는가
- 현재 문제 번호 / 종료 시각 / 제출 여부가 DB에 있는가

**진짜 원인**: 브라우저 화면만 현재 상태를 기억하고 있었을 가능성이 큽니다.
**칠판이 없고, 학생 머릿속에만 있었던 겁니다.**

**처방**: 9장의 "새로고침 6단계"를 그대로 구현하세요.
재연결 직후 반드시 `sync_state` 같은 요청을 보내고, 서버가 현재 상태를 통째로 내려 주게 만듭니다.

### 🔴 고장 5. 답안이 두 번 저장됨

#### 사례 ⑲ 엘리베이터 버튼 두 번 누르기

엘리베이터 버튼을 두 번 눌러도 엘리베이터가 두 대 오지 않습니다.
이미 눌린 상태면 두 번째 입력은 **그냥 무시**됩니다.
(이 성질을 **멱등성**이라고 부릅니다 — 몇 번을 해도 결과가 같다는 뜻입니다.)

그런데 자판기는 다릅니다. 결제 버튼을 두 번 누르면 두 번 빠져나갑니다.

여러분의 서버는 지금 엘리베이터인가요, 자판기인가요?

**먼저 볼 곳**
- 클라이언트 쪽 **중복 제출 방지** (제출 버튼 즉시 비활성화)
- 요청에 **제출 고유 ID** 붙이기 (같은 ID면 두 번째는 무시)
- **DB 유니크 제약** (예: `학생 + 문제` 조합에 unique index)
- **ACK 처리** (응답이 늦어서 사용자가 다시 누르는 걸 막아야 함)

**진짜 원인**: 버튼 중복 클릭, 또는 **재연결 후 재전송을 막지 못한 경우.**
네트워크가 끊겼다 붙으면 클라이언트가 "아까 그거 안 갔나?" 하고 다시 보내는 일이 흔합니다.

> **가장 확실한 방어선은 DB 유니크 제약입니다.**
> 화면에서 막고, 서버에서 막고, DB에서 한 번 더 막으세요. 3중 잠금입니다.

### 🔵 고장 6. 남은 시간이 학생마다 다름

#### 사례 ⑳ 놀이공원의 대기 시간 표지판

놀이공원 대기줄에 이런 표지판이 있습니다. **"여기부터 40분"**.
줄 선 사람들이 각자 손목시계로 세지 않습니다. **공원이 정한 하나의 기준**을 봅니다.

만약 각자 자기 시계로 "나는 3시에 줄 섰으니까 3시 40분에 타겠지"라고 계산하면?
시계가 2분 빠른 사람, 3분 느린 사람이 생기고 줄은 엉망이 됩니다.

**먼저 볼 곳**
- 서버가 전달한 **종료 시각**을 쓰고 있는가
- 브라우저 간 **시차**
- 주기적인 **상태 재동기화**

**진짜 원인**: 각 브라우저가 서로 따로 카운트다운을 하고 있는 경우.

**처방 — 이렇게 바꾸세요**

```text
❌ 나쁜 방식: 서버가 "30초 남음"을 보낸다 → 브라우저가 30부터 센다
 → 메시지 도착 지연 + 브라우저 시계 오차 = 학생마다 다름

✅ 좋은 방식: 서버가 "종료 시각 = 10:15:30" 을 보낸다
 → 브라우저는 주기적(200ms)으로 "종료 시각 - 지금" 을 계산해서 표시
 → 기준이 하나라서 모두 같은 값에 수렴
```

`남은 시간` 대신 **`종료 시각`을 보내세요.** 이 한 줄이 고장 6을 거의 없앱니다.

### 🔴 고장 7. 연결이 자꾸 끊김

**먼저 볼 곳**
- **네트워크 상태** (교실 와이파이는 생각보다 자주 끊깁니다)
- **클라이언트 재연결 처리**가 구현돼 있는가
- **배포 재시작 여부** (배포로 서버가 재시작되면 모든 연결이 끊깁니다)
- 재연결 후 **상태 복원 흐름**

**처방**: 재연결은 **지수 백오프(exponential backoff)** 로.
1초 → 2초 → 4초 → 8초 (최대 30초) 식으로 간격을 늘려 가며 재시도합니다.
0.1초마다 무한 재시도하면 서버를 여러분이 직접 공격하는 꼴이 됩니다.

```javascript
let delay = 1000;

function connect() {
 const ws = new WebSocket(WS_URL);

 ws.onopen = () => {
 delay = 1000; // 성공하면 간격 초기화
 ws.send(JSON.stringify({type: "sync_state"})); // ★ 반드시 상태부터 요청
 };

 ws.onclose = () => {
 setTimeout(connect, delay);
 delay = Math.min(delay * 2, 30000); // 1→2→4→8…최대 30초
 };
}
connect();
```

★ 표시된 줄을 빼먹지 마세요. **전화를 다시 걸었으면 "어디까지 얘기했죠?"를 물어야 합니다.**

### 🟣 고장 8. 결과가 저장됐는지 확신이 안 듦

**먼저 볼 곳**
- 서버 **저장 결과**
- **ACK 응답**
- **DB 저장 성공 여부**
- **오류 응답** 처리

> ⭐ **"메시지를 보냈다"는 사실과 "서버가 저장했다"는 사실은 다릅니다.**

이건 이 책에서 세 번째로 반복하는 문장입니다. 세 번 반복하는 데엔 이유가 있습니다.
초보자 프로젝트에서 **가장 조용하고 가장 치명적인 버그**가 여기서 나옵니다.
에러도 안 나고, 화면도 멀쩡한데, 성적 데이터가 없습니다.

## 17장. 실제 점검 흐름 — 좁혀 가기

```text
① 브라우저의 WebSocket 연결 성공 여부 확인
 ↓ (열렸다면)
② 클라이언트 메시지가 서버 Consumer에 도착했는지 확인
 ↓ (도착했다면)
③ Group과 Channel Layer를 통해 이벤트가 전달됐는지 확인
 ↓ (전달됐다면)
④ DB에 필요한 상태와 답안이 저장됐는지 확인
 ↓ (저장됐다면)
⑤ 서버가 ACK 또는 오류 응답을 반환했는지 확인
 ↓
⑥ 새로고침과 재연결 후 상태가 복원되는지 확인
```

> ⭐ **처음부터 모든 부분을 보지 말고, 연결 → 전달 → 저장 → 복원 순서로 좁혀 갑니다.**

이건 전기가 안 들어올 때 정비사가 하는 일과 똑같습니다.
두꺼비집 → 배선 → 콘센트 → 기기 순으로 내려갑니다.
기기부터 뜯는 사람은 없습니다.

## 18장. 실전 팁

- 정답 제출처럼 중요한 작업은 **저장 성공 ACK를 받고**,
 현재 문제 상태는 **서버에서 다시 조회할 수 있게** 만들면 디버깅이 훨씬 쉬워집니다.
- **브라우저 콘솔 로그와 서버 로그를 나란히 놓고 보세요.** 원인의 대부분이 그 사이에 있습니다.
- 모든 이벤트에 **타임스탬프와 학생 ID**를 찍어 두면, 나중에 사고 재현이 가능해집니다.
- 새로고침·재접속 시나리오는 **개발 중에 일부러 테스트하세요.**
 개발자도구 Network 탭에서 Offline 체크 → 해제, 이 두 번의 클릭이 배포 후 사고를 막습니다.

> **상태 저장, Group 전달, 재연결, 중복 처리**에서 발생합니다.

## 19장. 설계 먼저 — 종이 한 장이면 됩니다

코드를 열기 전에, 표 세 개를 채우세요. 30분이면 끝납니다.

### 표 1. 기능별 통신 방식 나누기

| 기능 | HTTP | WebSocket | 이유 |
|---|:---:|:---:|---|
| 퀴즈방 입장 | ● | | 성공/실패가 분명해야 함 |

| 문제 시작 알림 | | ● | 모두에게 동시에 |

| 문제 종료 시각 | DB | 2026-07-25 10:15:30 |
| 정답 공개 여부 | DB | false |

| 이벤트 이름 | 방향 | 담을 내용 |
|---|---|---|
| `question_started` | 서버 → 전체 | 문제 번호, 내용, 보기, **종료 시각**, **server_time** |

AI에게 코드를 요청할 때도 이 표를 그대로 붙여 넣으면 결과물이 완전히 달라집니다.

## 20장. 뼈대 코드 — 최소한의 실시간 퀴즈

프레임워크는 Django Channels 기준입니다.
다른 스택(Node의 Socket.IO, FastAPI 등)을 쓰더라도 **구조는 동일합니다.**
이름만 바뀔 뿐, 연결·그룹·상태·ACK는 어디에나 있습니다.

### ① 설정 — 방송 배선 깔기

```python
# settings.py
INSTALLED_APPS = [
    "daphne", # ASGI 서버 (발전소)
    "channels",
    ...
]

ASGI_APPLICATION = "config.asgi.application"

CHANNEL_LAYERS = {
    "default": {
    # 운영 환경: Redis 백엔드 (건물 사이를 잇는 배선)
    "BACKEND": "channels_redis.core.RedisChannelLayer",
    "CONFIG": {"hosts": [("127.0.0.1", 6379)]},
    }
}

```

> 개발 중엔 `channels.layers.InMemoryChannelLayer`도 동작합니다.
> 하지만 **서버 프로세스가 하나일 때만** 입니다. 배포 전에 반드시 Redis로 바꾸세요.
> 이게 4부 고장 2·3의 예방주사입니다.

### ② 라우팅 — 어느 주소가 웹소켓인지 알려 주기

```python
# routing.py
from django.urls import re_path
```

```python
import json
from channels.generic.websocket import AsyncWebsocketConsumer
from channels.db import database_sync_to_async

class QuizConsumer(AsyncWebsocketConsumer):

    async def connect(self):
        self.quiz_id = self.scope["url_route"]["kwargs"]["quiz_id"]
        self.student_id = self.scope["url_route"]["kwargs"]["student_id"] # URL 신원 바인딩 (부록 E-1)
        self.group_name = f"quiz_{self.quiz_id}"

        await self.accept()
        # ★ 미join 학생은 방송 목록에 넣기 전에 걸러낸다 (스푸핑 차단)
        if not await self.is_joined_student(self.student_id):
            await self.send(text_data=json.dumps({"type": "error", "reason": "unknown_student"}))
            await self.close()
            return

        await self.channel_layer.group_add(self.group_name, self.channel_name)

        # ★ 연결하자마자 칠판을 보여 준다 (재연결 시에도 자동으로 복원됨)
        await self.send_state_snapshot()

    async def disconnect(self, code):
        await self.channel_layer.group_discard(self.group_name, self.channel_name)

    async def receive(self, text_data):
        # ⓪ malformed 게이트: 크기 → JSON → 구조 순으로 거르고, 저장은 절대 시도하지 않는다
        if len(text_data.encode("utf-8")) > 65536: # 64KB 초과 페이로드 (바이트 기준)
            await self.send(text_data=json.dumps({
                "type": "answer_saved", "ok": False, "reason": "malformed",
            }))
            return
        try:
            data = json.loads(text_data)
        except (json.JSONDecodeError, TypeError):
            data = None
        if not isinstance(data, dict) or "type" not in data: # 비-dict JSON, type 누락
            await self.send(text_data=json.dumps({
                "type": "answer_saved", "ok": False, "reason": "malformed",
            }))
            return

        if data.get("type") == "sync_state":
            await self.send_state_snapshot()

        elif data.get("type") == "submit_answer":
            required = {"question_id", "choice", "submission_id"}
            if not required <= data.keys() or any(data.get(k) is None for k in required):
                await self.send(text_data=json.dumps({ # 키 누락·null 값 모두 malformed
                    "type": "answer_saved", "ok": False, "reason": "malformed",
                }))
                return
            ok, reason = await self.save_answer(data) # DB 저장 시도 (부록 E-3 계약)
            # ★ ACK: "접수했습니다" 를 반드시 돌려준다 (실패 시 reason 포함)
            await self.send(text_data=json.dumps({
                "type": "answer_saved",
                "submission_id": data["submission_id"],
                "ok": ok,
                "reason": reason, # 성공이면 None, 실패면 malformed/closed/duplicate 등
            }))

        else:
            # 정의되지 않은 type은 저장 없이 오류만 돌려준다
            await self.send(text_data=json.dumps({
                "type": "error", "reason": "unknown_type",
            }))

    # --- Group 방송을 받았을 때 호출되는 핸들러 (type 이름 = 메서드 이름) ---
    async def question_started(self, event):
        await self.send(text_data=json.dumps(event["payload"]))

    async def answer_revealed(self, event):
        await self.send(text_data=json.dumps(event["payload"]))

    async def leaderboard_updated(self, event):
        await self.send(text_data=json.dumps(event["payload"]))

    async def quiz_finished(self, event):
        await self.send(text_data=json.dumps(event["payload"]))

    # --- 헬퍼 ---
    async def send_state_snapshot(self):
        state = await self.load_state()
        await self.send(text_data=json.dumps({
            "type": "state_snapshot",
            **state, # 현재 문제 번호, 종료 시각(ISO), 내 제출 여부
        }))

    @database_sync_to_async
    def load_state(self):

    @database_sync_to_async
    def save_answer(self, data):
        ... # 유니크 제약으로 중복이면 False 반환
```

# 부록 B — 세 문장 요약

이 책 전체를 세 문장으로 줄이면 이렇습니다.

> **1. HTTP는 요청과 저장에 강하고, WebSocket은 실시간 전달에 강하다.**
> 그래서 실시간 서비스는 둘을 함께 쓴다.

> **2. 앱 서버가 상태와 저장을 관리하고,
> Group과 Channel Layer가 여러 연결에 이벤트를 전달한다.**
> 이벤트는 지나가고 상태는 남는다.

> **3. 실시간 디버깅은 연결, 전달, 상태, 저장, 재연결을 분리해서 보는 것이 핵심이다.**
> "웹소켓이 안 돼요"는 진단이 아니다.

# 부록 C — 자주 나오는 질문

**Q1. 실시간이면 무조건 WebSocket만 써야 하나요?**
아니요. 실시간 알림은 WebSocket이 유리하지만,
저장과 조회는 HTTP가 더 단순하고 안정적인 경우가 많습니다.

**Q2. Redis가 있으면 DB는 필요 없나요?**
아니요. Redis는 Channel Layer의 이벤트 전달을 도울 수 있고,
DB는 문제·답안·점수·현재 진행 상태처럼 나중에도 남아야 하는 확정 데이터를 저장합니다.

**Q3. Redis는 WebSocket인가요?**
아니요. WebSocket은 브라우저와 서버 사이의 **통신 방식**이고,
Redis는 서버 **내부**에서 이벤트 전달이나 데이터 처리를 돕는 별도 시스템입니다.

**Q4. WebSocket만 잘 연결되면 다 해결되나요?**
아니요. 실시간 문제의 상당수는 연결 자체보다
상태 저장, Group 전달, 재연결, 중복 처리에서 발생합니다.

**Q5. Group에 몇 명 있는지 어떻게 아나요?**
Group으로는 알 수 없습니다. Django Channels의 Group은 순수한 브로드캐스트 시스템이라
참여자 목록을 조회하는 기능이 없습니다.
참여자를 알아야 한다면 **DB에 직접 기록**하세요.

**Q6. Django 말고 다른 걸 써도 이 내용이 통하나요?**
네. 이름만 바뀝니다.
Node.js의 Socket.IO에서는 Group을 room이라 부르고, Consumer 대신 이벤트 핸들러를 씁니다.
**연결 · 그룹 · 상태 · ACK · 재연결**이라는 다섯 축은 어느 스택에서나 동일합니다.

**본문 중 다음 사실들의 근거**

- WebSocket은 단일 TCP 연결 위의 양방향 통신이며, HTTP 업그레이드 핸드셰이크(`101 Switching Protocols`)로 시작한다 → RFC 6455
- `ws://`는 기본 포트 80, `wss://`는 TLS로 기본 포트 443을 쓴다 → RFC 6455
- ASGI는 WSGI의 후속 규격이며, WSGI의 단일 콜러블 구조로는 오래 유지되는 연결과 여러 번의 수신 이벤트를 다룰 수 없어서 만들어졌다 → ASGI Documentation, Introduction
- Django Channels의 Group은 브로드캐스트 시스템으로, 그룹 내 채널을 열거하거나 목록으로 볼 수 없다 → Channels, Channel Layers
- `channels_redis`가 Django가 공식 유지보수하는, 운영 환경에서 지원되는 유일한 Channel Layer다 → Channels, Channel Layers
