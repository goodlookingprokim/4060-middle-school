안녕하세요. 오늘은 'Hermes'를 함께 살펴봅니다. 시작 전 분명히 — 이 시간은 '설치하는 법'이 아닙니다. 설치는 10분이면 끝나요. 우리가 할 일은, 설치 버튼을 누르기 전에 이게 어떤 종류의 물건인지 머릿속에 넣는 것. 7개 모듈, 30분 남짓 걸립니다. // 표지는 30초 안에 "오늘은 설치가 아니라 이해"만 박고 넘어가세요.
들어가며 / 01

이 자료는 “설치 가이드”가 아닙니다

Hermes를 아직 써 보지 않은 사람이 — 먼저 이해하도록 돕습니다.

다 읽고 나면 다음을 스스로 판단할 수 있습니다.

  • Hermes가 내 상황·업무에 맞는 도구인가
  • 맞다면 어떤 마음가짐과 순서로 시작해야 하는가
  • 사람들이 어디서 실수하는가 — 나는 그 함정을 어떻게 피할 것인가
쉽게 말하면새 가전제품을 살 때 “설명서대로 켜는 법”보다 “이게 어떤 제품이고 우리 집에 맞는지”를 먼저 보는 게 낫습니다. 이 자료는 바로 그 “먼저 볼 것”을 모은 것입니다.
다 듣고 나면 세 가지를 판단할 수 있습니다 — 내게 맞는 도구인가, 맞다면 어떤 순서로 시작하나, 어디서 실수하나. 아래 박스: 설치는 명령어 몇 줄이지만 잘 쓰는 것은 개념 이해에서 시작된다. 개념을 건너뛰고 설치하면 작동은 하지만 곧 구조가 엉킵니다.

Module 00 / 왜 이해가 먼저인가

왜 설치보다 이해가 먼저인가

학습 목표이 시스템을 “무작정 설치하면 안 되는” 이유를 이해한다.
대부분의 AI 도구

설치 → 바로 사용

잘못 써도 손해가 작다. 마음에 안 들면 지우면 그만.

Hermes

구조가 쌓이는 시스템

기억이 누적되고, 기능이 축적되고, 에이전트가 서로 의존한다. 초반 구조를 잘못 잡으면 바로잡는 비용이 매우 크다.

쉽게 말하면메모장 앱은 마음에 안 들면 지우면 끝입니다. Hermes는 “이사”에 가깝습니다 — 짐이 쌓인 뒤에 집 구조를 바꾸려면 훨씬 힘듭니다. 그래서 처음 배치가 중요합니다.
스스로 점검
  • 모범답안기억·기능·에이전트 간 의존이 시간이 지나며 누적되어, 초반에 잘못 잡은 구조를 나중에 바로잡는 비용이 매우 크기 때문이다.
평소 AI 도구는 설치하고 바로 쓰죠 — 부담이 없습니다. Hermes는 다릅니다. 시간이 지날수록 구조가 쌓입니다. 메모장은 지우면 끝이지만 Hermes는 '이사' — 짐이 쌓인 뒤 구조를 바꾸기 어렵습니다. Hermes를 오래 써 온 운영자 Shann도 "맨바닥에서 쓰려다 주말 몇 번을 태웠다"고 했어요.
Module 01 / 어떤 시스템인가

Hermes는 어떤 종류의 시스템인가

학습 목표Hermes를 “챗봇”이 아니라 “지속적으로 일하는 Operator”로 인식한다.
익숙한 AI 도구 (챗봇)Hermes
질문하면 답한다워크플로를 처음부터 끝까지 실행한다
세션이 끝나면 잊는다세션이 끝나도 살아남는 기억을 가진다
매번 다시 가르쳐야 한다일하면서 스스로 학습한다
쉽게 말하면Operator(오퍼레이터)는 “운영자·작업자”입니다. 한 번 묻고 답을 받는 상대가 아니라, 계속 옆에서 일을 처리해 주는 직원이라고 보면 됩니다. “세션”은 한 번의 대화 묶음을 말합니다.
한 줄 정의 (공식 문서)Hermes는 오래 돌릴수록 더 유능해지는 자율 에이전트다.
오늘 가장 중요한 멘탈 전환입니다. 챗봇은 질문하면 답하고, 세션이 끝나면 잊습니다. Hermes는 워크플로를 끝까지 실행하고, 기억이 살아남고, 일하며 스스로 학습합니다. 'Operator'는 계속 옆에서 일하는 직원. 한 줄 정의 — 공식 문서도 "오래 돌릴수록 더 유능해지는 자율 에이전트"라고 합니다. 꼭 가져가세요.
Module 01 / 비유

자판기 vs. 신입 직원

챗봇 = 자판기

동전 넣으면 음료가 나온다

질문하면 답한다. 다음 사람에게는 당신이 뭘 샀는지 기억이 없다.

Hermes = 신입 직원

지켜보며 배운다

처음엔 서툴지만 일하는 방식을 배운다. 다음 주엔 다시 설명할 필요가 없고, 쓸수록 당신의 방식과 선호에 맞춰진다.

흔한 오해“그냥 더 좋은 ChatGPT 아닌가?” → 핵심은 모델 성능이 아니라 지속성(기억이 남고 능력이 쌓이는 것)이다.
스스로 점검
  • 모범답안자판기(챗봇)는 매번 기억 없이 처음으로 돌아가지만, 신입 직원(Hermes)은 일하며 배우고 기억을 쌓아 점점 더 유능해진다.
  • 모범답안오래 돌릴수록 더 유능해지는 자율 에이전트.
챗봇은 자판기 — 동전 넣으면 음료, 다음 사람은 기억 못 함. Hermes는 신입 직원 — 처음엔 서툴지만 지켜보며 배우고, 쓸수록 당신의 방식에 맞춰집니다. 흔한 오해: "더 좋은 ChatGPT?" 아닙니다 — 핵심은 모델 성능이 아니라 지속성입니다.
Module 01 / 구성

에이전트 한 개는 무엇으로 이루어지는가

학습 목표Hermes 에이전트 하나가 “기억 · 성격 · 능력” 세 가지로 이루어짐을 안다.

앞에서 Hermes를 “신입 직원”에 비유했습니다. 그 직원 한 명을 열어 보면, 딱 세 부분입니다.

기억 · Memory

잊지 않는 부분

세션이 끝나도 살아남는다. 사실(무엇을 아는가)을 저장 — 사업·나에 대한 정보가 대화 시작 때마다 불려 온다.

성격 · SOUL.md

말투와 분위기

간결하게·격식 있게·직설적으로. 같은 기억 위에 다른 성격을 얹어 여러 에이전트를 만들 수 있다.

능력 · Skill

할 줄 아는 일

절차(어떻게 하는가)를 저장한다. 기본 Skill이 다수 제공되고, 일하면서 스스로 더 늘린다.

쉽게 말하면신입 직원 한 명을 떠올리면 됩니다 — 겪은 일을 기억하고(기억), 자기만의 말투가 있고(성격), 할 줄 아는 업무가 있죠(능력). 공식 문서의 구분: 기억은 ‘사실’(무엇을 아는가), 능력은 ‘절차’(어떻게 하는가)를 저장합니다.
신입 직원 한 명은 무엇으로 이루어질까요? 셋입니다. 기억 — 세션이 끝나도 남는 부분, '사실'을 저장. 성격 — 말투와 분위기, 같은 기억 위에 다른 성격을 얹어 여러 에이전트도. 능력 — 할 줄 아는 일, '절차'를 저장. 공식 문서의 구분: 기억은 사실, 능력은 절차.
Module 01 / 실전 사례

Hermes로 실제 무엇을 하나

학습 목표추상적 개념을 “실제로 돌아가는 것”의 구체적 그림으로 바꾼다.

공식 문서·공식 가이드가 소개하는 대표적인 활용 — 전부 실제로 문서화된 사용 사례입니다.

01CLI 코딩 어시스턴트
터미널에서 코드를 쓰고·리뷰하고·실행한다
02팀 메신저 어시스턴트
Telegram·Discord 봇 — 팀원이 함께 쓰는 공유 에이전트, 사용자별 권한
03데일리 브리핑 봇
매일 아침 관심 주제를 조사·요약해 메신저로 전달 (웹 검색 + cron)
04GitHub PR 리뷰 에이전트
레포를 지켜보며 새 PR을 자동 리뷰하고 요약을 보낸다
05작업 자동화
cron으로 반복 작업을 예약 — 정기 점검·리포트·리마인더
06멀티에이전트 협업
Kanban으로 리서치 분류·엔지니어링 파이프라인을 여러 에이전트가 분담
이 사례들의 공통점은 하나 — 전부 “반복되는 워크플로”다. Hermes의 가치는 일회성 질문이 아니라 반복에서 나온다.
스스로 점검
  • 모범답안정해진 답은 없습니다 — 본인 업무를 여섯 사례에 대입해 보는 질문입니다.
  • 모범답안Hermes가 진가를 발휘하는 건 반복되는 워크플로입니다. 일회성 작업이라면 모듈 07에서 적합성을 다시 따져 보세요.
모듈 1의 정의가 아직 손에 안 잡히죠? 공식 문서·가이드가 소개하는 대표 활용을 봅니다 — CLI 코딩 어시스턴트, 팀 메신저 봇, 데일리 브리핑 봇, GitHub PR 리뷰, cron 작업 자동화, Kanban 멀티에이전트 협업. 전부 실제로 문서화된 사용 사례입니다. 공통점: 전부 반복되는 워크플로 — Hermes의 가치는 반복에서, 모듈 7에서 다시 나옵니다. // "본인 업무랑 닮은 게 있나요?" 물어보세요.
Module 02 / 닫힌 학습 루프

왜 오래 쓸수록 강해지는가

학습 목표Hermes가 스스로 강해지는 메커니즘을 이해한다.
STEP 1

관찰

자기 작업을 지켜본다

STEP 2

Skill 작성

반복 패턴을 스스로 기능으로 만든다

STEP 3

틀린 건 고치고 사실은 정리한다

STEP 4

맥락 호출

다음에 과거 내용을 다시 불러온다

설치 직후부터 풍부한 기본 Skill을 갖추고 있다. 일을 시킬수록 그 위에 나만의 기능 모음이 저절로 쌓인다.

쉽게 말하면Skill(스킬)은 에이전트가 할 줄 아는 “기술 하나”입니다. 핵심은 — 이 스킬을 사람이 미리 쓰는 게 아니라 에이전트가 일하며 스스로 만든다는 것. 이것이 Hermes의 공식 동작(자율 스킬 생성)입니다.
"오래 쓸수록 강해진다"의 메커니즘 = 닫힌 학습 루프. 관찰 → Skill 작성 → 기억 정제 → 맥락 호출 → 다시 1번. Skill은 에이전트가 할 줄 아는 기술 하나. 핵심은 — 사람이 미리 쓰는 게 아니라 에이전트가 일하며 스스로 만든다는 것. Hermes의 공식 동작입니다. 설치 직후부터 기본 Skill이 풍부합니다.
Module 02 / 운영자 Shann의 조언

Day 1에 Skill을 직접 만들지 마라

“직접 Skill을 미리 짜지 마라. 실제 작업을 돌리고, 에이전트가 일하며 스스로 쓰게 하라.” — 운영자 Shann
비유운동 루틴을 처음부터 100페이지 계획서로 쓰지 않는다. 일단 시작하고, 몸이 반응하는 걸 보며 루틴이 잡힌다. Skill도 — 미리 쓰는 게 아니라 일하면서 자라난다.
흔한 오해“Skill을 미리 많이 만들어 두면 빠르겠지” → 반대다. 검증 안 된 Skill은 짐이 된다.
스스로 점검
  • 모범답안① 관찰 → ② Skill 작성 → ③ 기억 정제 → ④ 맥락 호출, 그리고 다시 ①로.
  • 모범답안Skill을 미리 직접 많이 만드는 것. 검증 안 된 Skill은 짐이 되고, Skill은 일하면서 자라나야 하기 때문.
큰 글씨 — '에이전트가 일하며 스스로 Skill을 쓰게 하라'. 운영자 Shann의 조언입니다. 입문자는 의욕이 앞서 워크플로를 다 Skill로 미리 정의하려는데, 설계 방향과 정반대. 운동 계획서를 100페이지 먼저 쓰지 않죠 — 일단 시작하면 루틴이 잡힙니다. Skill도 일하면서 자라납니다. // "Day 1에 Skill 만들지 마라" — 한 박자 쉬고 강조.

Module 03 / 보관과 이전

비밀은 한곳에, 통째로 이식 가능

API 키 같은 비밀은 .env 한 파일에 모입니다. 흩어져 있지 않습니다. 덕분에 에이전트를 옮기거나 공유할 때 비밀만 따로 다룰 수 있습니다.

hermes backup

전체를 압축

비밀 포함. 내 다른 기계로 이사할 때 — 그대로 복원된다.

hermes profile export

단일 에이전트를 압축

비밀 제외. 남에게 공유해도 안전 — 자격증명이 빠진다.

비유에이전트 하나 = 책상 서랍 하나. 서류(설정·기억·능력)는 같이 있지만, 열쇠(.env)는 잠긴 한 칸에 따로. 그래서 서랍째 옮기거나, 열쇠 칸만 빼고 남에게 건넬 수 있다.
흔한 오해“설정·비밀이 시스템 여기저기 흩어져 있겠지?” → 아니다. 한 폴더에 모이고 비밀은 .env로 격리된다. 이 단순함이 백업·이전·보안을 쉽게 만든다.
스스로 점검
  • 모범답안config·.env(비밀)·SOUL.md·memories·skills·세션·state.db — 에이전트의 모든 것이 한 폴더에.
  • 모범답안backup은 전체를 압축하고 비밀을 포함한다(내 이사용). profile export는 단일 에이전트를 압축하되 비밀을 제외한다(공유용).
비밀은 .env 한 파일에 모입니다 — 흩어져 있지 않아요. 그래서 두 가지 내보내기가 깔끔합니다. hermes backup은 전체+비밀 포함, 내 다른 기계로 이사할 때. profile export는 단일 에이전트인데 비밀을 빼서, 남에게 공유해도 안전. 책상 서랍 비유 — 서류는 같이, 열쇠는 잠긴 칸에 따로.
Module 04 / 하나에서 여럿으로

하나에서 여럿으로 — Profile

학습 목표한 에이전트로 부족할 때, Profile로 격리된 여러 에이전트를 운영하는 방식을 안다.

에이전트 하나에 코딩·개인 비서·리서치를 다 시키면 — 기억이 뒤섞이고, 성격이 충돌하고, 권한을 깔끔하게 못 나눕니다. 공식 해법은 Profile입니다.

완전 격리

섞이지 않는다

프로필끼리 기억도 세션도 섞이지 않는다.

자체 HERMES_HOME

집을 하나 더

자기만의 config·.env·SOUL.md·기억·스킬을 통째로 가진다.

자체 명령

이름이 명령이 된다

hermes profile create coder → coder chat.

비유Profile = 직원 한 명. 코더 직원, 리서처 직원, 비서 직원 — 각자 자기 책상(HERMES_HOME)과 자기 권한. 한 사람에게 모든 역할을 몰아주지 않는 것과 같다.
쉽게 말하면Profile = 격리된 에이전트 한 마리. hermes profile create <이름>으로 만들고, <이름> chat으로 대화합니다. 역할이 다르면 프로필을 나누세요.
에이전트 하나에 코딩·비서·리서치를 다 시키면 기억이 섞이고 성격이 충돌합니다. 공식 해법은 Profile — hermes profile create coder 한 줄이면 'coder'라는 완전 별개 에이전트가 생깁니다. 자체 config·키·성격·기억·스킬, 즉 HERMES_HOME 하나를 통째로 더. 프로필끼리 완전 격리. 직원 한 명 = 프로필 하나.
Module 04 / 판단

언제 새 프로필을 만드나

상황판단
자체 자격증명(다른 API 키)이 필요하다새 프로필
자체 장기 기억이 필요하다새 프로필
별도 역할로서 반복되는 일이다새 프로필
그 외기존 것을 그대로
흔한 오해“에이전트 하나에 전부 몰아주면 편하지 않나?” → 그게 피해야 할 패턴(메가 에이전트)이다. 격리를 잃고, 접근 권한을 깔끔하게 회수할 수 없으며, 에이전트가 어떤 역할로 행동할지 혼란스러워한다.
스스로 점검
  • 모범답안자체 config·.env·SOUL.md·기억·세션·스킬 — 완전히 격리된 별도의 HERMES_HOME 하나.
  • 모범답안자체 자격증명이 필요할 때, 자체 장기 기억이 필요할 때, 별도 역할로서 반복되는 일일 때.
언제 새 프로필을 만드나 — 자체 자격증명이 필요할 때, 자체 장기 기억이 필요할 때, 별도 역할로 반복되는 일일 때. 그 외엔 기존 것 그대로. 피해야 할 패턴: 메가 에이전트 — 모든 키·기억을 한 에이전트에 몰아주면 격리를 잃습니다.
Module 05 / 협업

여럿이 협업하는 법

학습 목표여러 에이전트·작업이 협업하는 공식 방법을 안다.
delegate_task

잠깐 도우미를 부른다

서브에이전트를 즉석에서 띄워 일을 맡기고 결과만 받는다. 빠른 fork-join, 부모는 기다린다.

Kanban

함께 보는 작업 게시판

지속되는 멀티에이전트 보드. 여러 프로필이 작업을 집어 처리 — 재시도·사람 개입·재시작 생존.

Cron

정해진 시각에 자동 실행

“매일 9시 뉴스 요약” 같은 예약 작업. 자연어로 만들 수 있다.

쉽게 말하면 — 공식 구분delegate_task는 함수 호출(빠르고 일시적). Kanban은 작업 큐(지속·복구·사람 개입). 빠른 답이 필요하면 delegate_task, 작업이 에이전트 경계를 넘고 살아남아야 하면 Kanban.
에이전트가 여럿이 되면 협업이 필요. 공식 세 도구 — delegate_task: 서브에이전트를 잠깐 띄워 일 맡기고 결과만 받음, 빠른 fork-join. Kanban: 지속되는 멀티에이전트 작업 보드, 여러 프로필이 처리, 재시도·사람 개입 가능. Cron: 정해진 시각 자동 실행. 공식 구분 — delegate_task는 함수 호출, Kanban은 작업 큐.
Module 05 / 가장 큰 함정

서두르지 마라

“평범한 대화 하나를 제대로 끝내지 못하면, 기능을 더 얹지 마라. 깨끗한 대화 하나를 먼저 — 그다음 한 겹씩.” — 공식 Quickstart
비유한 곡도 제대로 못 치면서 오케스트라 지휘부터 배우지 않는다. 에이전트 하나가 제 몫을 한다는 게 증명되기 전에는, 협업·자동화가 할 일이 없다.
쉽게 말하면운영자 Shann도 같은 경고를 합니다 — “전문 에이전트가 유용하다는 것이 증명되기 전에 오케스트레이터부터 만들지 마라.” 입문자가 가장 자주 하는 실수가 바로 이것입니다.
흔한 오해“처음부터 멀티에이전트·자동화로 가야 진짜 시스템이지” → 아니다. 평범한 대화 하나가 안정적으로 도는 것이 먼저. 그 위에 한 겹씩 얹는다.
스스로 점검
  • 모범답안delegate_task는 함수 호출(빠르고 일시적, 부모가 결과를 기다림). Kanban은 작업 큐(지속·복구·사람 개입, 여러 프로필이 처리).
  • 모범답안에이전트 하나가 평범한 대화를 안정적으로 끝내는 것. 그 위에 게이트웨이·cron·스킬을 한 겹씩 얹는다.
가장 큰 함정 — 에이전트 하나도 제대로 안 되는데 협업·자동화부터 손대는 것. 공식 Quickstart: "평범한 대화 하나를 제대로 못 끝내면 기능을 더 얹지 마라. 깨끗한 대화 먼저, 그다음 한 겹씩." 운영자 Shann도 같은 경고. 악기 하나도 못 다루며 지휘부터 배우지 않죠. // 발표의 클라이맥스 — 한 박자 멈추고 눈 맞춤.
Module 06 / 키우는 것

에이전트는 “키우는” 것이다

학습 목표처음부터 완벽을 노리지 않는 자세를 갖춘다.

워크플로는 머릿속에서 완성된 형태로 나오지 않습니다 — 돌려 보면서 발견됩니다. 운영자 Shann이 권하는 4단계입니다.

STEP 1

프로토타입

시도하게 둔다. 첫 실행엔 대부분 틀린다 — 괜찮다.

STEP 2

2–3회 반복

매번 교정. 학습 루프가 지켜보며 Skill을 쌓는다.

STEP 3

파인튜닝

전용 공간에서 지시·흐름을 조인다.

STEP 4

배포

한 주 버텨 내면 cron 등 자동화로 넘긴다.

비유분재 — 완성된 나무를 사 오는 게 아니라, 심고 자라는 대로 다듬는다. 첫 실행 실패는 버그가 아니라 학습의 입력이다.
흔한 오해“첫 실행에서 안 되면 도구가 별로인 것” → 첫 실패는 설계된 과정이다.
스스로 점검
  • 모범답안① 프로토타입 → ② 2~3회 반복 교정 → ③ 전용 공간에서 파인튜닝 → ④ 스케줄(cron) 배포.
  • 모범답안첫 실패는 버그가 아니라 학습 루프의 입력. 2~3회 교정이 곧 에이전트가 배우는 과정이기 때문.
"완벽한 에이전트를 한 번에 설계해 배포" — 불가능합니다. 워크플로는 돌려 보면서 발견됩니다. 운영자 Shann이 권하는 네 단계 — 프로토타입(첫 실행 틀려도 OK), 2~3회 반복 교정, 파인튜닝, 배포. 공식 Quickstart의 "한 겹씩"과 같은 이야기. 분재 같죠 — 심고 다듬는다. 첫 실패는 버그가 아니라 학습의 입력.
Module 07 / trade-off

솔직한 trade-off 3가지

학습 목표Hermes의 한계를 알고, 자신에게 맞는 도구인지 판단한다.
  • 번들 기본값은 곧 “의견”이다. 첫날부터 생산적이지만, 모든 단계를 직접 제어하고 싶은 사람에겐 무겁다.
  • 협업·자동화 단계엔 실제 학습 곡선이 있다. 에이전트 하나는 가볍지만, 여러 프로필을 Kanban으로 묶거나 VPS에서 24시간 돌리려면 Docker·서버 지식이 필요해 시간이 든다.
  • 모델은 여전히 중요하다. Hermes는 좋은 모델을 훌륭하게 만들 뿐, 작은 모델을 전략가로 만들지는 못한다. 창작·전략엔 강한 모델, 단순 반복엔 싼 모델 — 작업에 맞춰 고른다.
쉽게 말하면 — 운영자 Shann의 비유“Hermes는 레일(rails)” = 옵션이 미리 채워진 패키지 여행. 모든 걸 직접 조립하고 싶은 사람에겐 자유 여행 성향의 도구가 더 맞습니다. 둘 다 유효하니, 자기 취향에 맞는 쪽을 고르면 됩니다.
좋은 교육자료는 단점도 말합니다. 운영자 Shann이 인정하는 셋 — ① 번들 기본값은 곧 '의견'(완전한 제어 원하면 무겁다). ② 협업·자동화 단계의 학습 곡선(Docker·서버 운영). ③ 모델은 여전히 중요 — 창작엔 강한 모델, 단순 작업엔 싼 모델. Hermes는 '레일'(패키지 여행), 반대는 '자유 여행' — 취향에 맞는 쪽.
Module 07 / 자기 판단

Hermes가 나에게 맞는가

다시 생각해 볼 경우잘 맞는 경우
일회성·단발성 질문만 한다반복되는 워크플로가 있다
지금 당장 완성형 결과만 원한다오래 쓰며 시스템을 키울 의향이 있다
모든 단계를 직접 제어해야 마음이 놓인다“첫 실행 실패”를 학습으로 받아들인다
쉽게 말하면왼쪽이라고 “틀린” 게 아닙니다. 설치하기 전에 자기가 어느 쪽인지 정직하게 아는 것이 핵심입니다. 왼쪽이면 “Hermes는 내 도구가 아니다”도 충분히 좋은 결론입니다. 게다가 Hermes 자체는 오픈소스(MIT)이고 무료라, 망설여지면 LLM 사용료만으로 — 로컬 모델이면 그마저 없이 — 직접 굴려 보고 정해도 됩니다.
스스로 점검
  • 모범답안① 번들 기본값은 곧 의견(완전한 제어를 원하면 무겁다) ② 협업·자동화 단계의 학습 곡선 ③ 모델은 여전히 중요하다.
  • 모범답안개인 판단입니다 — 반복 워크플로가 있고, 오래 키울 의향이 있고, 첫 실패를 학습으로 받아들이면 오른쪽.
솔직하게 자기에게 대입. 오른쪽(잘 맞음) — 반복 워크플로 있음, 오래 키울 의향, 첫 실패를 학습으로 수용. 왼쪽(다시 생각) — 일회성 질문, 당장 완성형, 모든 단계 직접 제어. 어느 쪽이든 OK — 중요한 건 설치 전에 정직하게 아는 것. 게다가 Hermes 자체는 오픈소스(MIT)·무료라, LLM 사용료만으로 가볍게 굴려 보고 정해도 됩니다.
부록 A / 한 운영자의 방식

한 운영자의 운영 방식 — Shann Holmberg

이 과정의 본문은 공식 문서를 따랐습니다. 그런데 출발점이 된 글이 있습니다 — 운영자 Shann Holmberg는 공식 기능 위에 자기만의 관례를 얹었습니다. 알아두면 유용하지만, 이것은 공식 기능이 아닙니다 — 공식 문서엔 아래 용어가 없습니다.

Shann의 용어공식 Hermes에서는
Control Room — 에이전트 관리용 문서·거버넌스 폴더별도 개념 없음 — 모든 것이 HERMES_HOME에. “관리 문서를 한곳에” 발상 자체는 합리적
Level 1 → 4 — 에이전트 1개→전문 에이전트들→오케스트레이터→자동화공식 단계 taxonomy 없음 — 모듈 3~5의 “하나 → Profile → 협업·자동화” 흐름이 대응
Task Bus — 오케스트레이터↔전문 에이전트 작업 전달 창구Kanban·delegate_task가 그 역할을 한다
정리그의 마음가짐(서두르지 마라·키워라·역할별로 격리하라)은 공식 문서와도 잘 통합니다. 하지만 그의 구조 용어(Control Room·Level·Task Bus)는 그의 것이지 Hermes의 것이 아닙니다. 공식 문서를 읽을 때 이 점을 기억하세요. — 그의 공개 템플릿: github.com/shannhk/hermes-agent-control-room
부록입니다. 이 과정 본문은 공식 문서를 따랐는데, 출발점이 된 글의 저자 Shann은 공식 기능 위에 자기 관례를 얹었습니다 — Control Room, Level 1→4, Task Bus. 공식 문서엔 이 용어가 없어요. Control Room은 공식엔 없고 모든 게 HERMES_HOME에, Level은 모듈 3~5 흐름이 대응, Task Bus는 Kanban·delegate_task가 그 역할. 그의 마음가짐은 공식과 통하지만 구조 용어는 그의 것 — 공식 문서 읽을 때 헷갈리지 마세요. // 빠르게 짚고 넘어가세요.
부록 B / 도구 비교

Hermes vs openclaw — 사용 관점

“Hermes가 나에게 맞나”를 따질 때 자주 나오는 비교 상대가 openclaw(구 Clawdbot/Moltbot)입니다. 공식 migrate-from-openclaw 가이드를 근거로 사용 관점에서 정리합니다.

사용 관점openclawHermes
핵심 에이전트 모델persona·기억·스킬·MCP·메시징거의 동일 — 마이그레이션이 1:1로 옮김
기본값파일이 잘게 나뉨(IDENTITY·TOOLS·HEARTBEAT·BOOTSTRAP), 명시적내장으로 통합 — 설정 적음, 첫날 생산적
시작 느낌부품을 직접 조립조립된 채로 와서 바로 사용
전환공식 hermes claw migrate 명령이 openclaw 설정(persona·기억·스킬·모델·메시징)을 Hermes로 가져옵니다 — 한쪽을 골라도 갇히지 않습니다.
어느 쪽이 나에게 맞나설정을 최소화하고 빠르게 생산적이고 싶으면 Hermes, 모든 단계를 직접 정의·제어하고 싶으면 openclaw 성향. 둘 다 유효합니다 — 모듈 7의 “레일 vs 자유 여행”과 같은 선택입니다.
openclaw(구 Clawdbot/Moltbot)는 Hermes와 자주 비교되는 또 다른 에이전트 프레임워크입니다. 공식 migrate-from-openclaw 가이드 기준 — 핵심 에이전트 모델(persona·기억·스킬·MCP)은 거의 동일해 마이그레이션이 1:1. 차이는 기본값 — openclaw는 파일이 잘게 나뉘어 명시적, Hermes는 내장으로 통합. hermes claw migrate로 전환 가능해 한쪽을 골라도 갇히지 않습니다. 둘 다 유효 — 모듈 7의 레일 vs 자유 여행. // 공식 문서는 마이그레이션 절차 문서라 Hermes에 우호적 — 균형 잡아 전달하세요.
